## 1. Что делает продукт

Система находит B2B-компании в Казахстане, обогащает их данными и сигналами и выдаёт
готовые профили лидов: кто, по какому каналу с ними связаться и почему им нужна
лидогенерация именно сейчас.

Это первая из трёх систем. Система №2 (AI-персонализация сообщений) и Система №3
(инфраструктура доставки) описываются отдельно. Здесь фиксируется только то, какие
идентификаторы и сигналы собирать, чтобы №2 и №3 могли работать.

**Контракт с Системой №2** — таблица `mart.lead_profiles`: `company_id`, `contact_id`,
`segment_id`, `fit_score`, `intent_score`, `best_channel`, `why_now`, `profile`.

**Состояние Системы №3.** Очередь исходящих (`outbox`), воркер с гейтами окна
10:00–18:00 Asia/Almaty и режимы `autopilot` (`off | manual | replies | full`, файл-переключатель
— kill switch; умолчание `manual` — уходит только поставленное оператором) реализованы; доставка по кнопке оператора и при `full` идёт через один
путь (`sender/services/queue.py`). Входящие (вебхук с дедупом по `provider_id` и
стоп-словами до модели), агент-продавец (`conversations`, один вызов со structured output, #36; три
предохранителя в `sender/services/incoming.py`) и каденция follow-up
(`[3, 7]` в `sender/config.toml`, текст рождается в момент срока) реализованы
2026-08-30.

## 3. Пользовательские сценарии

**С1. Набрать базу по сегменту.** Оператор выбирает рубрику 2GIS и город, запускает
сбор и получает список организаций с идентификаторами и метаданными.

**С2. Получить контакты.** По собранным организациям система забирает карточки и
извлекает телефон, сайт, email, Instagram и WhatsApp.

**С3. Найти повод для разговора.** Система собирает тексты вакансий и ищет в них
признаки нехватки клиентов — прежде всего вакансии в продажах.

**С4. Отсеять неподходящих.** Компании вне ICP и прямые конкуренты отсекаются
автоматически, до того как на них потрачены деньги.

**С5. Получить готовый список.** Оператор получает топ компаний с обоснованием
`why_now` — цитатой и ссылкой — и начинает переписку.

**С6. Не написать дважды.** Компания, пришедшая из нескольких источников, остаётся
одной записью. Отписавшиеся и пожаловавшиеся не получают касаний никогда.

## 4. Функциональные требования

Статус: ✅ — реализовано, ⛔ — снято, ◐ — частично. Где — модуль, в котором живёт
правило.

### 4.1 Сбор первичных данных

| # | Требование | Статус |
|---|---|---|
| F1 | Перечислять организации по категориям справочника 2GIS с указанием города | ✅ `companies` — сегменты «город × рубрика» |
| F2 | Извлекать из карточки телефон, сайт, email, Instagram, WhatsApp | ✅ `companies/domain.py::parse_firm_card` |
| F3 | Получать справочник категорий с иерархией | ◐ справочник 36 рубрик B2B-услуг и двух городов — константа `companies/domain.py`; иерархия не нужна |
| F4 | Собирать полные тексты вакансий с работодателем и датой публикации | ⛔ hh.kz отклонён (TRD §8); вакансии ищутся на сайте компании (`site_hiring_sales`) |
| F5 | Выполнять поисковые запросы Google и отдавать URL, заголовок, сниппет | ⛔ снято в #13: служило только ручной разведке |
| F6 | **Обнаруживать молчаливую подмену содержимого источником и останавливаться** | ✅ `currentPage` списка рубрики; адрес сайта вне интернета не читается |

| F8 | Каждая запись несёт происхождение: источник, рубрика или slug, город | ✅ сегменты филиала, ссылка и источник у каждой зацепки |

### 4.2 Нормализация и обогащение

| # | Требование | Статус |
|---|---|---|
| F9 | Складывать сырые ответы в неизменяемое хранилище, из которого нормализованный слой пересобирается сколько угодно раз | ◐ страницы хранятся (`backend/data/pages/`), повторное исследование читает их без сети; пересборки всей базы разом больше нет (ADR 0002) |
| F10 | Склеивать одну компанию, пришедшую из разных источников, по домену, телефону, БИН или Instagram; по имени — только с ручной проверкой | ◐ склейка филиалов 2GIS по org_id, телефону, домену и похожему имени; правило и уверенность видны у филиала |
| F11 | Отсеивать не-ICP по дешёвым полям **до** платных этапов | ✅ выбор сегментов и приоритет партии: недостижимые компании модель не видит |
| F12 | Извлекать из текста отрасль, размер, наличие отдела продаж и сигналы одним вызовом модели на компанию | ✅ один вызов `research` (без размера — TRD §9) |
| F13 | Находить CRM-виджеты, пиксели и рекламные системы детерминированно, без модели | ✅ `crm_widget`, `ads_platform`, `inbound_widget` по разметке |
| F14 | Хранить сигналы как события с датой, а не как флаги | ✅ таблица `signals` |

### 4.3 Скоринг и выдача

| # | Требование | Статус |
|---|---|---|
| F15 | `fit_score` — соответствие ICP, по правилам | ◐ отдельного числа нет: соответствие ICP задаёт выбор сегментов |
| F16 | `intent_score` — потребность в лидогенерации сейчас, с затуханием по времени | ✅ оценка с периодом полураспада, считается при чтении |
| F17 | Оба скоринга объяснимы: для каждого лида видно, какие сигналы и с каким весом сработали | ✅ разбивка «сигнал — вклад — цитата — ссылка» |
| F18 | Проверять работоспособность каналов **до** ранжирования | ◐ канал — WhatsApp или казахстанский мобильный (городские номера отсеяны); проверки номера в WhatsApp нет |

| F21 | Глобальный список отказов (`refusals`), проверяемый до каждого касания, никогда не очищается; отказ по любому контакту компании закрывает её целиком | ✅ `refusals`; проверяется при чтении лидов и перед отправкой |

## 5. Нефункциональные требования

| # | Требование | Обоснование |
|---|---|---|
| N1 | Сбор детерминирован; модель в нём не участвует | Воспроизводимость и отладка. Модель недетерминирована и неотлаживаема |
| N2 | Любой этап переживает повторный запуск без порчи данных | Прогоны прерываются, источники моргают |
| N3 | Ошибка источника видна оператору, а не поглощается | Тихая порча данных — главный риск проекта |
| N4 | Ни одному источнику v1 не нужен браузер, аккаунт или прокси | Проверено; убирает потолок 200–400 стр/час и $20/мес |
| N5 | Масштаб — тысячи компаний, не сотни тысяч | Потолок отправки 50–60 сообщений в день |
| N6 | Сырые данные не удаляются никогда | Нормализация меняется еженедельно, перекачать нельзя: вакансия закрывается, страница удаляется |

## 6. Границы

**Не входит в v1:** мультитенантность, второй ICP, Россия, Instagram как источник,
Meta Ad Library, интеграции с CRM.

**Осознанно отложено:** срез 2GIS по районам для обхода потолка охвата; поиск ЛПР
агентом с инструментами (ADR 0001).

## 7. Приёмка

Продукт готов, когда выполнены все критерии:

| # | Критерий | Как проверяется |
|---|---|---|
| П1 | 30 компаний из отрасли «бизнес-услуги», Алматы или Астана | выгрузка |
| П2 | У каждой — проверенный канал из `[whatsapp, phone, email]` | статус канала |
| П3 | У каждой — `why_now` с цитатой и ссылкой на источник | ручной просмотр всех 30 |
| П4 | С компаниями начата переписка | факт отправки |
| П5 | Сбор воспроизводим: повторный запуск даёт тот же результат | повторный прогон |
| П6 | Ни одна запись не пришла из подменённой источником страницы | проверки коннекторов зелёные |
