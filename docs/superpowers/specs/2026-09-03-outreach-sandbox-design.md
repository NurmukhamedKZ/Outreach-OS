# Песочница аутрича: подменный транспорт, роль лида, машина времени

Статус: спека, реализация не начата.

**Проблема.** Три системы собраны и покрыты тестами, но целиком, от черновика
до встречи, продукт никто не проходил. Проверить его сегодня нельзя ничем,
кроме живого WhatsApp на живом лиде:

1. **Роли лида нет.** Единственный способ увидеть, что ответит агент-продавец
   на «дорого» или на «пришлите КП», — написать это с настоящего телефона в
   настоящий номер пула. Первый же неудачный ход стоит номера и лида.
2. **Время не проходит.** Каденция `[3, 7]` дней, `passive_days = 3`,
   `cold_start_day = 11`, окно 10:00–18:00 и джиттер 2–15 минут означают, что
   follow-up руками проверяется трое суток, а прогрев — две недели.
3. **Аварии не воспроизводятся.** `sent: false` с ретраем 1/5/30, `stuck`,
   недоставленное сообщение, отвалившийся номер — всё это ветки, которые видел
   только pytest. Как они выглядят у оператора в интерфейсе, не видел никто.
4. **Чистого контекста нет.** Второй прогон по тому же лиду упирается в тот же
   `thread_id` (это номер телефона, PK таблицы `threads`), и агент видит
   историю прошлого сценария. Сравнить две ветки одного диалога нечем.

**Решения, принятые на брейншторме 3 сентября 2026:**

| Вопрос | Решение |
|---|---|
| Что прогоняем | всё: первое касание, диалог, follow-up, прогрев |
| Форма песочницы | подменный Node внутри того же бэкенда, контракт ручка в ручку |
| LLM | настоящий, как в бою; заглушки нет |
| Интерфейс | страница `/sandbox`: слева чат в роли лида, справа пульт |
| Изоляция данных | отдельная база под флагом `SANDBOX`, боевая не трогается |
| Прогоны | старые остаются и читаются; новый прогон — чистый контекст |
| Аварии | четыре тумблера в пульте |

**Не входит.** Автоматические сценарии («лид отвечает по скрипту»), запись и
воспроизведение прогонов, групповые чаты и медиа от лида сложнее метки
`[медиа]`, вторая копия дизайн-системы, второй фронтенд.

**Готово, когда:** оператор открывает `/sandbox`, создаёт прогон по настоящей
компании из выдачи, получает черновик, ставит его в очередь, двигает часы на
открытие окна, видит доставку, отвечает как лид, получает ответ продавца,
двигает часы на три дня и получает follow-up — не отправив в WhatsApp ни
одного сообщения.

## 1. Прогон — это файл базы

### 1.1 Почему не флаг на треде

`thread_id` — номер телефона и первичный ключ `threads`. Пометить тестовые
треды колонкой значило бы: второй прогон по тому же лиду невозможен (ключ
занят), «чистый контекст» изображается фильтром в каждом запросе агента, а
воронка `/analytics` и инбокс `/threads` учатся про тестовые треды забывать —
то есть фильтр появляется в пяти местах, и однажды одно из них его забудет.

Прогон — это файл: `backend/collector/data/sandbox/<run>.db`, где `<run>` —
`YYYYMMDD-HHMM-<company_id>`. Схема та же самая: `threads`/`messages` создаёт
`writer/db/thread_store.py`, `outbox`/`numbers` — `sender/db/migrate.py`,
`suppression`/`jobs`/`activity` — STATE-блок `collector/db/schema.sql`. Все
трое уже умеют `CREATE TABLE IF NOT EXISTS`, поэтому новая база наполняется
теми же миграциями, что боевая, — второй схемы в проекте не появляется.

Чистота контекста обеспечена физически: агент читает историю из базы прогона,
и прошлого сценария там нет, потому что его нет в файле.

### 1.2 `backend/paths.py` — единственный владелец пути

Сейчас путь к `state.db` называют пять мест:

| Место | Что делает |
|---|---|
| `collector/services/store.py:17` | константа `STATE`, ATTACH к `derived.db` |
| `writer/services/config.py:17` | `threads_db` из `writer/config.toml` |
| `sender/services/config.py:26` | `state_db` из `sender/config.toml` |
| `writer/db/leads_source.py:41` | `Path(path).parent / "state.db"`, ATTACH ro |
| `collector/services/metrics.py:101` | через конфиг writer'а |

Пять «если песочница» — это пять шансов забыть. Появляется модуль верхнего
уровня `backend/paths.py` (тот же приём, что `config.py` и `activity.py`):

```python
def state_db() -> Path:
    """Куда пишется невосстановимый слой: боевая база или активный прогон."""
```

Все пятеро зовут его. Ключи `state_db` и `threads_db` из `sender/config.toml`
и `writer/config.toml` удаляются: два конфига, называющие один файл, — это уже
два источника правды, и повод их слить наступил.

`derived.db` в песочнице остаётся боевой и открывается только на чтение. Лид в
прогоне — настоящая компания с настоящим досье и настоящим поводом: черновик
по выдуманной компании проверять незачем.

### 1.3 Создание и переключение прогона

Создание прогона — четыре шага в одной ручке: создать файл, применить три
миграции, записать мету, засеять пул.

Мета живёт в таблице `sandbox_meta (key TEXT PRIMARY KEY, value TEXT)` внутри
самой базы прогона — по правилу «владелец таблицы доливает её сам»: владелец
здесь `backend/sandbox/`. В ней `company_id`, `created_at`, `note` и сдвиг
часов (см. §2).

Пул засевается одним номером `+77000000001`, и у создания прогона есть
единственный параметр — **прогрет он или нов**. Прогретый (`status = active`,
`started_at` в прошлом за пределами `cold_start_day`) нужен, чтобы проверять
аутрич; новый (`status = new`, `started_at` = «сейчас» прогона) — чтобы
проверять прогрев. Без этого выбора первый же прогон упёрся бы в календарь
прогрева и не отправил бы ничего.

Переключение активного прогона — присвоение переменной в `paths.py` плюс
повторный вызов швов `activity.use()` и `analytics.use()`, которые
`collector/api.py` уже дёргает при сборке приложения. Соединения к базе везде
короткие (`with closing(connect())`), поэтому живой процесс переключается без
перезапуска.

## 2. Машина времени

`datetime.now()` в системах 2 и 3 живёт ровно в шести местах, и каждое уже
вынесено в отдельную функцию — шов готов заранее:

`sender/routes/sender.py:51`, `sender/routes/webhook.py:95`,
`sender/services/warmup.py:261`, `sender/services/worker.py:337`,
`sender/db/conversation.py:265`, `writer/db/thread_store.py:74`.

Появляется `backend/clock.py`:

```python
def now() -> datetime:
    """«Сейчас» продукта. В бою — системное время, в песочнице — сдвинутое."""

def shift(delta: timedelta) -> None:
    """Двинуть часы активного прогона. Вне песочницы — ошибка, а не тишина."""
```

Шесть мест зовут `clock.now()`. Два последних возвращают строку — у них
меняется только источник момента, формат прежний.

**Сдвиг принадлежит прогону, а не процессу.** Он лежит в `sandbox_meta` и
читается при активации. Иначе прогон, начатый вчера со сдвигом «+3 дня», после
перезапуска бэкенда откатился бы назад во времени, и уже отработавший
follow-up снова стал бы будущим — то есть база прогона рассказывала бы про
время не то, что часы.

В бою сдвиг всегда ноль: ручка `POST /api/sandbox/clock` не монтируется без
флага, а `clock.now()` без песочницы — это буквально `datetime.now(utc)`.
Существующие тесты об этом не узнают.

Пресеты в пульте: «+15 минут» (пережить джиттер), «+1 час», «+1 день», «к
открытию окна» — 10:00 Asia/Almaty ближайшего рабочего дня. Тики остаются
реальными (воркер — 20 секунд, прогрев — 10 минут): прыгает не расписание, а
то, что система считает «сейчас», и созревшая строка уезжает на ближайшем
тике.

## 3. Подменный транспорт

### 3.1 Контракт ручка в ручку

`backend/sandbox/node.py` отдаёт ровно те пять ручек, что `sender/node/index.js`
— `POST /send`, `POST /check`, `POST /pair`, `POST /qr`, `GET /health` — и
знает ровно столько же, сколько настоящий Node: ни лидов, ни тредов, ни
лимитов. `SENDER_NODE_URL` в `backend/.env` указывает на него
(`http://127.0.0.1:8787/api/sandbox/node`), и `sender/transport.py` не меняется
ни строкой.

`/send` уважает ключ идемпотентности так же, как настоящий: повтор с тем же
`key` возвращает `provider_id` первой отправки и второго сообщения не создаёт.
Дубликат в холодном аутриче — прямой повод нажать Report, и проверять эту
защиту на боевом номере поздно.

Отправленное кладётся в ленту прогона и тут же уезжает статусом в свой же
`POST /api/sender/webhook` — тем же HTTP, с тем же заголовком
`X-Sender-Secret`, через тот же дедуп по `provider_id`. Путь события в
песочнице не короче боевого ни на шаг: сокращать его — значит проверять не ту
систему.

### 3.2 Четыре тумблера

Аварии — настройка стенда, а не факт истории, поэтому живут в памяти модуля и
не переживают перезапуск (в отличие от часов, которые принадлежат прогону):

| Тумблер | Значения | Что проверяет |
|---|---|---|
| Отправка | `ок` / `не ушло` / `неизвестно` | `sent:false` → ретрай 1/5/30 → `failed`; 500 → `TransportError` → `stuck` человеку |
| Доставка | `доставлено` / `прочитано` / `тишина` | коды 3 и 4 будят тред в `active`; тишина оставляет его в `queued` и роняет `min_delivered_rate` |
| Номер | `connected` / `loggedOut` / `stalled` | что видит `GET /health` и часовой монитор: карантин пула |
| `/check` | есть WhatsApp / нет | ветка «номер не в WhatsApp» до отправки |

### 3.3 Входящее от лида

«Ответить как лид» — та же ручка `POST /api/sender/webhook` с
`kind: "incoming"`, которую настоящий Node дёргает на `messages.upsert`, с тем
же `from` в виде JID и тем же `provider_id`. Значит боевыми остаются: проверка
стоп-слов регуляркой до модели, отказ через шов `refusal.refuse`, дедупликация
повторного события, гашение расписания треда одной транзакцией, эскалация на
пустом тексте, оживление треда из `exhausted` и три попытки на входящее.
Пустое поле текста в пульте — это медиа: та же метка `[медиа]`, та же
эскалация.

## 4. Пульт и чат

### 4.1 Страница `/sandbox`

Восьмая страница дашборда, та же дизайн-система, та же SSE-подписка
`components/live.tsx`. Сверху — селектор прогона и «Новый прогон». Ниже два
столбца.

**Слева чат.** Оператор в роли лида: наши сообщения слева, его — справа. Под
каждым нашим пузырём стоит его настоящая судьба, а не украшение мессенджера:
«черновик» (серым), «в очереди», «отправлено», «доставлено», «прочитано», «не
ушло — попытка 2 из 3, следующая в 14:05», «stuck — разбирает человек»,
«отменено: лид ответил». Время — по часам прогона. Разница
`draft_text`/`queued_text`/`sent_text` видна прямо в ленте: это единственная
бесплатная разметка для калибровки промпта, и в песочнице она должна быть
первым, что видно.

**Справа пульт**, шесть блоков:

1. **Прогон** — компания со ссылкой на `/leads/[id]`, номер лида, `stage`,
   `status`, израсходованные касания и `next_touch_at`.
2. **Часы** — «сейчас» прогона и четыре пресета сдвига.
3. **Сбои** — четыре тумблера из §3.2.
4. **Пул** — номера прогона: состояние, день и фаза прогрева, дневной лимит и
   расход.
5. **Журнал** — хвост `activity` прогона: почему тик ничего не отправил (окно,
   лимит, джиттер), что ответил транспорт, когда просыпался прогрев.
6. **Автопилот** — `off` / `replies` / `full`.

Автопилот песочница переключает тем же файлом `sender/autopilot`, что и бой:
это и есть боевой kill switch, второй копии ему заводить незачем. Бой и
песочница — один процесс в двух режимах и одновременно не работают.

### 4.2 Ручки

Семь, все под `/api/sandbox`:

| Ручка | Что делает |
|---|---|
| `GET /runs` | прогоны: id, компания, создан, сообщений, активен ли |
| `POST /runs` | новый прогон: `company_id` + прогрет ли номер |
| `POST /runs/{run}/activate` | переключить активный прогон |
| `POST /clock` | сдвиг часов: `{"seconds": …}` или пресет |
| `POST /faults` | тумблеры аварий |
| `GET /chat` | лента активного прогона: пузыри из `messages` + судьба из `outbox` |
| `POST /incoming` | «ответить как лид» — вебхук самому себе |

Плюс пять ручек подменного Node под `/api/sandbox/node`.

Кнопки «Черновик» и «Поставить в очередь» зовут существующие ручки writer'а
(`POST /api/threads/{company_id}/draft`) и sender'а (`POST /api/sender/queue`).
Второй точки входа в постановку сообщения песочница не заводит — иначе гейты
проверялись бы не те, что в бою.

Живость — на существующей подписке: после каждого действия и каждого вебхука
песочница публикует `refresh`, страница перечитывает `GET /api/sandbox/chat`.
Своего стрима она не открывает.

## 5. Границы

**Роутеры песочницы монтируются только при `SANDBOX=1`.** Без флага их не
существует вовсе — тот же принцип, которым `rebuild` лишён возможности сходить
в сеть: невозможность, а не дисциплина.

**Один предохранитель на старте.** Если `SANDBOX=1`, а `SENDER_NODE_URL`
смотрит не на подменный транспорт — приложение падает с внятным сообщением.
Иначе тестовый прогон ушёл бы живым людям с боевых номеров. Обратная ошибка
конструктивно невозможна: базу и транспорт переключает один и тот же флаг.

**`backend/sandbox/` не импортирует никто.** Песочница знает про системы, они
про неё — нет; сторожит тест графа импортов, как `sender/tests/test_import_graph.py`.

**Тесты.** `clock` (сдвиг, ноль без песочницы, переживает переключение
прогона), `paths.state_db()` (какой путь при каком флаге), подменный транспорт
(идемпотентность по `key`, три режима отправки, вебхук уходит), создание
прогона (три миграции применились, пул засеян, боевая база не тронута), граф
импортов. Модули верхнего уровня тестируются в `collector/tests/` — прецедент
`test_activity.py`.

Существующие тесты о песочнице не узнают: `clock.now()` с нулевым сдвигом —
это прежний `datetime.now(timezone.utc)`, а `paths.state_db()` без флага — тот
же файл, что раньше называла константа.

**Цена прогона.** LLM настоящий: каждый ход продавца, каждый черновик и каждый
follow-up оплачены. Это осознанный выбор — проверяется в том числе то, что
модель говорит, — но песочница не место для холостых прогонов пачками.

## 6. Порядок работ

1. `backend/paths.py` и перевод пяти мест на него; удаление `state_db` и
   `threads_db` из двух конфигов.
2. `backend/clock.py` и перевод шести мест на него.
3. `backend/sandbox/runs.py` — создание, активация, мета, засев пула.
4. `backend/sandbox/node.py` — пять ручек контракта, идемпотентность, вебхук.
5. Тумблеры аварий и `POST /api/sandbox/incoming`.
6. `GET /api/sandbox/chat` — сборка ленты из `messages` и `outbox`.
7. Монтирование под флагом, предохранитель на старте, тест графа импортов.
8. Страница `/sandbox` во фронтенде.
