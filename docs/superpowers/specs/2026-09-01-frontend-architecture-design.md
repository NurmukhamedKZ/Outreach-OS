# Архитектура фронтенда: страницы по сущностям, видимые процессы, прозрачный LLM

Статус: спека, реализация не начата.

## Проблема

**1. Страницы повторяют границы бэкенда, а не работу оператора.** Сайдбар —
это три системы (`collector`, `writer`, `sender`), и две из трёх страниц
собраны из одних и тех же кусков: `PipelineActions` + `JobMonitor` +
`split(список | LeadCard)`. Справа на обеих рендерится **тот же самый**
`LeadCard` с той же секцией «Переписка» внутри. Отличается только левая
колонка: лиды по скору против тредов по дате.

**2. Фоновые процессы невидимы.** В `lifespan` крутятся четыре задачи
(`queue.worker_loop`, `sender.monitor_numbers`, `sender.warm_numbers`,
`sender.send_queue`), и следов они почти не оставляют:

- `worker.tick()` возвращает исход строкой (`sent`, `escalated`, `touched`…)
  и **выбрасывает его** — на вебе виден только `heartbeat`;
- тик, решивший ничего не делать, не виден нигде;
- `monitor_numbers` переводит номер в карантин, и *когда* это случилось и
  *почему* — узнать неоткуда: в `numbers` есть только `note`;
- автоответ продавца и планирование follow-up происходят молча: оператор
  узнаёт постфактум, открыв тред.

**3. Данных о лиде видно меньше, чем есть.** `LeadDetail.breakdown` приезжает
с бэкенда и **нигде не рисуется** — мёртвое поле в контракте. Досье модели
(`dossiers_all`: `summary`, `approach`, `hooks`) уходит в промпт, но на вебе
его нет. Свежесть сырья (`fetches_all`: `final_url`, `status`, `fetched_at`) и
оплаченные ответы модели (`state.llm_answers`) не показаны вовсе.

**4. Запрос в модель нигде не сохраняется.** `agent.draft()` собирает
`[("system", …), ("human", …)]`, отправляет и выбрасывает. В базе остаётся
только `draft_text`. Ответить на вопрос «почему модель написала это» нечем:
`seed` и история с тех пор изменились, а реконструкция покажет не то, что
ушло.

## Область

Фронтенд целиком, плюс минимальный бэкенд под него: журнал событий, сохранение
промпта, три новых ручки и расширение карточки лида.

**Не входит:** логика гейтов, каденции, прогрева и скоринга — они только
показываются, а не меняются. Дизайн-система (`globals.css`, токены, шрифты,
иконки) остаётся как есть. Прямая отправка мимо `outbox` не появляется.

## Готово, когда

1. Ни одна страница не дублирует другую: `LeadCard` существует в одном месте,
   `JobMonitor` — в одном.
2. Любое действие фонового демона видно на вебе с указанием времени и причины,
   включая тик, который решил ничего не делать, и включая то, что случилось
   ночью при закрытой вкладке.
3. По клику на лида открывается страница, где видно всё, что система о нём
   знает: разбор скора, досье модели, сигналы, каналы, сырьё с датой, ответы
   модели, переписка.
4. У холодного письма есть свой экран: текст правится, ставится в очередь, и
   рядом раскрывается **полный запрос, реально ушедший в модель**.

## 2. Журнал процессов

### 2.1 `backend/activity.py` — новый общий модуль

Верхний уровень `backend/`, рядом с `config.py` и `observability.py`, по той же
причине: писать в журнал должны и система 1, и система 3, а импортировать друг
друга они не имеют права (`sender/tests/test_import_graph.py`,
`collector/tests/test_operations.py`).

Путь к базе приходит швом — тем же приёмом, каким `collector/api.py` уже
подключает `sender_refusal.use(...)`:

```python
def use(path: Path) -> None:
    """Шов: где лежит state.db, знает сборщик приложения, а не журнал."""
```

`record()` открывает **своё короткоживущее соединение** и коммитит сразу, а не
пишет в транзакцию вызывающего. Это не оптимизация, а требование: тик может
откатиться, а запись «пытались и вот что вышло» обязана остаться. Записей мало
(тик раз в 20 секунд — верхняя граница), цена соединения на запись
пренебрежима.

Если `use()` не вызывали, `record()` поднимает `RuntimeError`, а не молчит:
тихо проглоченный журнал — ровно та теневая работа, которую эта спека убирает.
`conftest.py` систем 1 и 3 зовёт `use(tmp_path / "state.db")`.

### 2.2 Схема (STATE-часть `collector/db/schema.sql`)

```sql
CREATE TABLE IF NOT EXISTS activity (
  id      INTEGER PRIMARY KEY,
  at      TEXT NOT NULL,           -- когда случилось впервые
  last_at TEXT NOT NULL,           -- когда в последний раз
  repeats INTEGER NOT NULL DEFAULT 1,
  actor   TEXT NOT NULL,           -- sender.tick | sender.monitor | sender.warmup | jobs | webhook
  outcome TEXT NOT NULL,           -- sent | idle | quarantined | answered | escalated | …
  subject TEXT,                    -- номер, thread_id, job_id
  detail  TEXT                     -- почему: «delivered 41%», «окно закрыто до 10:00»
);
CREATE INDEX IF NOT EXISTS activity_recent ON activity (last_at DESC);
```

**Схлопывание подряд идущих одинаковых.** Если последняя строка журнала
совпадает с новой по `(actor, outcome, subject)`, вместо вставки идёт
`UPDATE … SET repeats = repeats + 1, last_at = ?`. Без этого тик раз в
20 секунд даёт ~4300 строк мусора в сутки и топит в них единственное важное
событие; со схлопыванием «воркер жив, 380 тиков подряд делать было нечего» —
одна строка с честным счётчиком. Сравнивается именно **последняя** строка, а
не любая похожая: иначе чередование `sent`/`idle` слилось бы в две вечные
строки и порядок событий пропал бы.

### 2.3 Точки записи

Исход везде уже вычислен — добавляется по одной строке:

| Файл | Что пишем |
|---|---|
| `sender/services/worker.py::loop` | `idle`, когда `tick()` вернул `None`, — и больше ничего |
| `sender/services/worker.py::_send`, `_postpone`, `_retry`, `sweep_stuck` | `sent`/`rescheduled`/`retry`/`stuck` с номером, тредом и причиной |
| `sender/services/worker.py::_process` | `cancelled` с причиной от гейта |
| `sender/routes/sender.py::monitor_numbers` | итог `health.check` — карантин с причиной, освобождение `rescue_stranded` |
| `sender/services/warmup.py::loop` | исход `warmup.tick`: кому написали или почему нет |
| `collector/services/jobs.py::run_pending` | старт и финал джобы, `subject` — `job_id` (сама джоба уже в `jobs`, здесь только событие ленты) |
| `sender/routes/webhook.py` | входящее принято / дубликат по `provider_id` / стоп-слово закрыло тред |

**Почему не одной записью в `loop`.** `tick()` возвращает исход **строкой**
(`"sent"`, `"retry"`, …), и ни номера, ни треда, ни причины в этой строке нет.
Менять её на структуру значило бы править десятки существующих утверждений в
`sender/tests/` ради данных, которые у самих шагов уже под рукой: `_send` знает
номер и тред, `_process` — причину отказа гейта. Поэтому детали пишет тот, кто
их знает, а `loop` отвечает ровно за одно — «жив, и делать было нечего».

Автоответ продавца и планирование follow-up **отдельно не пишутся**: они уже
приходят исходами тика (`answered`, `escalated`, `touched`, `exhausted`). Две
записи на одно событие дали бы два разных времени одного и того же.

### 2.4 Ретенция

`activity.prune(days=14)` — `DELETE WHERE last_at < ?`. Зовётся из
`monitor_numbers`, который и так тикает раз в час; своего таймера журнал не
заводит.

### 2.5 Heartbeat выводится из журнала

Отдельного механизма пульса больше нет. `SELECT actor, MAX(last_at), COUNT(*)
FROM activity GROUP BY actor` отвечает на «жив ли демон» точнее, чем
глобальная переменная, и переживает перезапуск процесса.

Следствие: `worker._last_tick` и `worker.heartbeat()` удаляются.
`GET /api/sender` продолжает отдавать поле `heartbeat` — контракт
`SenderStatus` не меняется, — но берёт его из журнала.

### 2.6 API

```
GET /api/activity?limit=200&actor=sender.tick
    -> {"events": [...], "workers": [{"actor", "last_at", "events"}]}
```

Плюс событие `activity` в существующий SSE (`collector/routes/events.py`),
чтобы лента шла живой. `components/live.tsx` подписывается на новый тип и
кладёт хвост в контекст — второго `EventSource` страница `/activity` не
открывает (правило «одна SSE-подписка на всё дерево»).

## 4. Полный запрос в модель

### 4.1 Схема

Две колонки в `messages`:

```
prompt TEXT   -- json: [["system", "…"], ["human", "…"]]
model  TEXT   -- чем сгенерировано
```

Добавляются в `SCHEMA` (`writer/db/thread_store.py` и `collector/db/schema.sql`)
**и** через `ensure_column` — базы у всех уже созданы, а `CREATE TABLE IF NOT
EXISTS` их не тронет. Приём уже применяется в `sender/db/migrate.py`;
`ensure_column` оттуда переиспользуется, вторая копия не заводится.

### 4.2 `writer/services/agent.py`

`draft()` сегодня собирает `messages` локально и возвращает только `Draft`.
Будет возвращать:

```python
@dataclass(frozen=True)
class Attempt:
    draft: Draft
    prompt: list[tuple[str, str]]
    model: str
```

Три вызова обновляются: `writer/routes/threads.py::_writer_move`,
`writer/services/operations.py` (пайплайн `write`),
`sender/services/followup.py`.

### 4.3 Две функции `add_draft`

`writer/db/thread_store.py::add_draft` и `sender/db/conversation.py::add_draft`
(вторая — намеренная копия, см. её докстринг) получают необязательные
`prompt` и `model`. Обе пишут json как есть.

### 4.4 Покрытие

- холодное касание и follow-up — промпт сохраняется гарантированно;
- автоответ продавца (`writer/services/seller.py`, `create_agent`) — промпт
  собирает langgraph. Если он достаётся из результата без хирургии —
  сохраняем; если нет, поле остаётся пустым, а UI пишет «собран агентом, см.
  Langfuse» и **не** рисует прочерк, будто промпта не было;
- черновики, созданные до этой правки, промпта не имеют — UI пишет
  «сгенерирован до включения журнала». Задним числом не реконструируем: это
  была бы догадка под видом факта.

### 4.5 API

```
GET /api/threads/{company_id}/messages/{message_id}/prompt
    -> {"prompt": [["system", "…"], ["human", "…"]], "model": "…"}
```

Отдельной ручкой, а не полем в списке: промпт весит 2–4 КБ, и тащить его в
каждую строку инбокса незачем.

## 5. Страница «Холодные» (`/cold`)

```
слева                                справа
  27 ждут проверки                     ООО «Ромашка» · Алматы · intent 8.4 · [карточка →]
  [Сгенерировать черновики топ-N]      ┌────────────────────────────────────┐
  ▸ Ромашка         8.4                │ текст, редактируемый               │
    Астана-Тех      7.9                └────────────────────────────────────┘
    …                                  угол: crm_widget · deepseek-v4-flash
                                       ▾ Полный запрос в модель
                                          system: …
                                          human:  …
                                       [Отправить] [Перегенерировать]
                                       [Пропустить] [Больше не писать]
```

- **Отправить** — `POST /api/sender/queue`, существующий. Прямой отправки мимо
  очереди и гейтов в системе нет; под кнопкой подпись «уйдёт с +7700… не
  раньше 10:00» — та же, что сейчас в `Thread`.
- **Перегенерировать** — `POST /api/threads/{id}/draft`, стоит денег, подписано.
- **Пропустить** — только переход к следующему, ничего не пишет.
- **Больше не писать** — `RefusalForm`, тот же юридический контур (F21).
- **Полный запрос** — `<details>`, моноширинный, обе роли раздельно.

Новая ручка:

```
GET /api/threads/drafts?kind=cold
    -> {"drafts": [{"company_id", "company_name", "city", "intent_score",
                    "thread_id", "message_id", "draft_text", "angle",
                    "model", "has_prompt"}]}
```

Отбирает треды с `pending_draft` и ни одним `sent_text` — то есть именно
первое касание. Сортировка по `intent_score`: проверять черновики выгоднее с
самых сильных лидов.

## 6. Страница «Диалоги» (`/threads`)

Существующий инбокс, три изменения:

1. **Сортировка по срочности**: эскалированные → ответившие → молчащие. Сейчас
   `thread_store.inbox` сортирует по дате последнего сообщения; порядок задаёт
   бэкенд, страница его не пересчитывает.
2. У каждого нашего сообщения — кнопка промпта (та же ручка из §4.5).
3. У каждого нашего сообщения — вид касания из `outbox.kind`: `cold`,
   `followup`, `reply`. `reply` и `followup` ставит только автомат
   (`incoming.py`, `followup.py`), и они подписаны «отправлено автоматом».
   `cold` ставит либо кнопка оператора, либо автопилот в режиме `full` — их
   `kind` неразличим, и выдумывать различие незачем: режим виден на
   «Отправке».

Правая колонка — переписка + `MessageComposer`, без карточки лида: на неё
ссылка в шапке треда.

## 7. Карточка лида (`/leads/[id]`)

Секции сверху вниз:

1. **Шапка** — имя, отрасль, город, домен, intent/fit.
2. **Почему сейчас** — `why_now` + цитата + метка «от модели / по шаблону».
3. **Разбор скора** — `breakdown`: правило, вклад, цитата, ссылка, дата.
   Данные уже приезжают, нужен только рендер.
4. **Досье модели** — `summary`, `approach`, `hooks` (цитата + угол + источник).
   Ровно то, что уходит в промпт через `seed`.
5. **Сигналы** и **Каналы** — как сейчас.
6. **Сырьё** — по каждому источнику: `final_url`, HTTP-статус, `fetched_at`.
   Отвечает на «эти данные не протухли?». `final_url` показывается всегда, а не
   только при расхождении с `url`: подмена страницы источником — единственное,
   что о ней вообще сообщает.
7. **Ответы модели** — записи `state.llm_answers` по этой компании: `kind`,
   модель, промпт, сырой ответ. Ключ подбирается так же, как при записи
   (`analyze.py`): `f"{name} | {city}"` для `reviews`/`site`/`dossier`,
   инстаграм-логин для `instagram`.
8. **Переписка** — краткая сводка со ссылкой на `/threads`, без композера.
9. **Отказ** — `RefusalForm`.

Данные добавляются в существующий `GET /api/leads/{company_id}`
(`collector/services/leads.py::card`): одна карточка — один запрос. Досье
читается из view `dossiers`, сырьё — из `fetches`, ответы модели — из
`state.llm_answers` через уже существующий ATTACH.

## 8. Тесты

Бэкенд, `pytest`, без сети:

- `activity`: схлопывание подряд идущих одинаковых, **не**-схлопывание при
  чередовании исходов, `prune` по дате, `RuntimeError` без `use()`.
- Тик оставляет след: успешная отправка пишет в журнал номер и тред, пустой
  тик пишет `idle`, а два пустых подряд не создают второй строки.
- Промпт: `draft()` возвращает `Attempt` с теми же сообщениями, что ушли в
  `invoke`; `add_draft` их сохраняет; ручка отдаёт; старый черновик без
  промпта отдаёт пусто, а не падает.
- Ручки: `GET /api/activity` (события + воркеры), `GET /api/threads/drafts`
  (только первое касание, порядок по скору), карточка лида (досье, сырьё,
  ответы модели присутствуют).
- Heartbeat: `GET /api/sender` отдаёт `heartbeat` после записи тика в журнал —
  контракт не сломан удалением `worker._last_tick`.

Фронтенд: тестов в проекте нет, и эта спека их не заводит.

## 9. Порядок работ

1. **Журнал + `/activity`** — гасит «теневые процессы», самая ценная часть, ни
   от чего не зависит.
2. **Промпт в базе + `/cold`** — зависит от миграции `messages`.
3. **`/leads/[id]`** — расширение карточки, независимо от 1 и 2.
4. **`/threads` + снос дублей + редиректы** — последним, когда новым страницам
   есть куда ссылаться.

Каждый этап оставляет приложение рабочим: страницы удаляются только на
четвёртом, когда замены уже стоят.

## 10. Чего не делаем

- Не трогаем `globals.css`, токены, шрифты и иконки.
- Не трогаем логику гейтов, каденции, прогрева и скоринга — только показываем.
- Не заводим прямую отправку мимо `outbox`.
- Не реконструируем промпты старых черновиков.
- Не заводим второй `EventSource`: лента процессов идёт через существующую
  подписку `LiveProvider`.
