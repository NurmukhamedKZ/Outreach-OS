# Хранилище и операционный слой системы 1

Статус: дизайн, одобренный в brainstorming-сессии 2026-08-18.
Первая из двух спек. Здесь — фундамент: две базы вместо четырёх хранилищ,
версионирование прогонов вместо перезаписи, адаптер хранилища сырья, замена
CLI-скриптов на HTTP-операции, переезд проверок на pytest.

Продуктовая часть — в `2026-08-18-ai-signals-design.md`, она опирается на эту.

**Продуктового результата эта работа не даёт намеренно.** Меняется способ
хранения и запуска, не содержание выдачи.

## Горизонт

Инструмент для одного оператора на одной машине. SQLite и локальная папка
остаются; Postgres и объектное хранилище не берутся, но доступ к сырью идёт
через адаптер, чтобы переезд был правкой одного модуля.

Пороги, при которых к этому решению придётся вернуться:

```
raw/ > ~100 ГБ           локальный диск дороже R2
нужна вторая машина      папка не шарится
параллельный сбор        несколько писателей упираются в SQLite
```

Сейчас: 464 МБ, один оператор. Не близко.

## Проблема

### 1. Данные разбросаны по четырём хранилищам

```
db/leads.db          производная, пересобирается через DROP
db/ops.db            джобы
writer/threads.db    переписка
data/suppression.csv отказы
db/llm_cache.db      кэш ответов модели — планировался пятым
```

Это не четыре решения, а одна граница, обнаруженная заново четыре раза: как
только появляется факт, который нельзя вывести из `raw/`, его приходится
выносить, потому что пересборка сносит таблицы.

Следы того же: `companies.first_seen` объявлен в схеме, но `resolve.py:166`
пишет туда `NULL` всегда — вынести забыли.

```
companies: всего 1660, first_seen заполнено 0
```

Цена: три объекта бэкапа вместо одного, невозможность соединить переписку с
лидами запросом, двухфазная запись отказа (сначала файл, потом база) с
отдельным тестом на то, что они не разъехались.

### 2. Результат прошлого прогона затирается

Пересборка перезаписывает всё. Поправили regex формы заявки — старые 604
срабатывания исчезли, сравнить не с чем. Покрутили веса в `config.toml` —
предыдущая выдача не сохранилась.

Это делает калибровку слепой. Между тем именно ради калибровки веса и держатся
в конфиге: когда ответят первые лиды, надо будет понять, какие сигналы
сработали. Без истории прогонов узнать это нечем.

### 3. Слой джобов запускает скрипты через subprocess

| что | где | следствие |
|---|---|---|
| прогресс парсится из stdout по префиксу `#progress ` | `jobs.py:_parse_progress` | в docstring честно: «Скрипты таких строк пока не пишут; парсер ждёт их» — **прогресс-бар в UI не работает вообще** |
| результат шага = `process.returncode` | `_run_step` | «нет `OPENROUTER_API_KEY`» и «сеть отвалилась» неразличимы |
| отмена = `os.killpg(SIGKILL)` | `cancel` | убивает на середине записи файла в `raw/` |
| проверка пайплайна = `argv[:2] == ["uv","run"]` | `check_pipelines` | проверяется форма строки, а не существование операции |
| `uv run` на каждый из 4 шагов | `STEPS` | ~2с оверхеда и зависимость от `uv` внутри контейнера |

### 4. Проверки — самописный скрипт

```
collector/scripts/check.py   837 строк, 30 функций, 10 разделов
writer/scripts/check.py      226 строк
```

Всё или ничего по разделам, без изоляции состояния между проверками.

## 1. Две базы по классу данных

```
data/state.db     порождённое: suppression, jobs, threads, messages, llm_answers
data/derived.db   вычислимое: runs, current_run, fetches, orgs, contacts,
                  companies, company_links, signals, scores, dossiers
data/raw/         сырьё: страницы и ответы API, через адаптер хранилища
```

Исчезают `leads.db`, `ops.db`, `threads.db`, `suppression.csv` и не заводится
`llm_cache.db`. Обе базы в режиме WAL.

Всё, что является данными, лежит в `data/` — и сырьё, и базы. В `db/` остаются
только `schema.sql` и `lead.py`, то есть описание схемы и запросы: код, а не
данные. Папка переименовывается в `store/` при реализации, чтобы имя не обещало
баз, которых там больше нет.

`.gitignore` правится соответственно: `data/state.db`, `data/derived.db` и их
`-wal`/`-shm` спутники.

Граница проходит по одному правилу: **выводится из `raw/` и `config.toml` —
значит вычислимое; не выводится — порождённое.** Правило перестаёт быть устным
и становится физическим: файлом. Проверяется тестом.

| | `state.db` | `derived.db` |
|---|---|---|
| можно потерять | нет, невосстановимо | да, пересчитается из `raw/` |
| удаление строк | запрещено | не делается, но допустимо (ретенция прогонов) |
| размер | десятки МБ | растёт с числом прогонов |
| бэкап | часто | редко, вместе с `raw/` |
| схема | `CREATE TABLE IF NOT EXISTS` | то же, плюс версионирование по `run_id` |

### Почему `runs` лежат в `derived.db`, а не в `state.db`

Прогон описывает, **как построено вычислимое**, и в отрыве от него
бессмысленен. Но решает не смысл, а ограничение SQLite:

```
CREATE VIEW companies AS ... JOIN state.current_run USING (run_id)
→ ОТКАЗ: view companies cannot reference objects in database state
```

View не может ссылаться на присоединённую базу. Поскольку весь читающий код
держится на view текущего прогона (раздел 2), указатель обязан лежать в одном
файле с версионированными таблицами.

### Почему не один файл

Один файл рассматривался и отвергнут по замеру. Пересборка держит write-lock на
своей базе; если переписка лежит там же, отправка сообщения ждёт конца сборки:

```
                                     один файл    две базы
запись системы 2 во время сборки       2.85 с      0.002 с
```

Блокировки просто не пересекаются: пересборка пишет в `derived.db`, система 2 —
в `state.db`.

Вторым доводом идёт надёжность: повреждение файла с лидами не задевает
невосстановимую переписку и юридический список отказов.

### Межбазовые запросы

Соединение открывается к `derived.db` с `ATTACH DATABASE state.db AS state` —
это делает один модуль `services/store.connect()`. Проверено, что работает:

```
JOIN переписки с лидами:   [('ответ лида', 'Компания раз')]
отбор с suppression:       []
```

Появляется то, чего не было: переписку можно соединить с лидами запросом —
раньше это были две базы в разных процессах.

### Единственное ограничение

**Транзакция через две базы в WAL не атомарна**, поэтому ни одна операция не
пишет в обе сразу. По построению таких и нет:

| операция | пишет в |
|---|---|
| пересборка | только `derived.db` |
| отказ | только `state.db` |
| переписка | только `state.db` |
| ответы модели | только `state.db` |
| джобы | только `state.db` |

Проверяется тестом: ни одна функция записи не открывает обе базы.

### Отказы переезжают в базу

`suppression.csv` удаляется. Обоснование файла было «переживёт `DROP`» — теперь
таблица не удаляется, и обоснование исчезло. Второй довод (версионируется в
git) сегодня защищает файл с одним заголовком и нулём записей.

Отказ становится одной записью в одну таблицу вместо двухфазной. Тест
`check_refusal_reaches_both_stores` исчезает вместе с проблемой, которую он
сторожил.

Исчезает и дублирование: сегодня отказ пишется в таблицу дополнительно, «чтобы
выдача обновилась без пересборки». Выдача теперь фильтрует `state.suppression`
через `ATTACH` на лету, и дублировать нечего.

Для юриста и регулятора остаётся `GET /api/suppression/export.csv` — выгрузка
по требованию, а не второй склад.

### Переписка в общей базе

`threads` и `messages` переезжают в `state.db` — туда же, где отказы и
оплаченные ответы модели: всё это одинаково невосстановимо.
`writer/thread_store.py` меняет путь к базе; схема и логика не трогаются.
Система 2 остаётся отдельным uv-проектом со своими зависимостями — разделение
проектов было про пакеты Python, а не про файл базы.

`state.db` становится единственным, что требует частого бэкапа. Он маленький и
не растёт от пересборок.

## 2. Версионирование прогонов

Ничего не удаляется. Каждая пересборка — новый прогон.

```sql
CREATE TABLE IF NOT EXISTS runs (
  run_id       INTEGER PRIMARY KEY,
  started_at   TEXT NOT NULL,
  finished_at  TEXT,
  code_version TEXT,     -- git sha: каким кодом собрано
  config_hash  TEXT,     -- sha256 config.toml: какими весами
  note         TEXT      -- «поправил regex формы заявки»
);

CREATE TABLE IF NOT EXISTS current_run (run_id INTEGER NOT NULL);
```

Вычислимые таблицы получают `run_id` в первичный ключ:

```sql
CREATE TABLE IF NOT EXISTS orgs_all (
  run_id    INTEGER NOT NULL,
  branch_id TEXT NOT NULL,
  ...
  PRIMARY KEY (run_id, branch_id)
);
```

### View сохраняет весь читающий код

Физическая таблица называется `orgs_all`, а **view — `orgs`**:

```sql
CREATE VIEW orgs AS SELECT o.* FROM orgs_all o JOIN current_run USING (run_id);
```

Отсюда главное свойство этой правки: `report.py`, `routes/`, `services/leads.py`
и `writer/leads_source.py` **не меняются вовсе** — они как читали `orgs`, так и
читают. Меняется только запись, то есть пересборка.

### Переключение выдачи — одна строка

```sql
BEGIN IMMEDIATE;
  INSERT INTO runs (started_at, code_version, config_hash) VALUES (...);
  -- наполнение таблиц с новым run_id
  UPDATE runs SET finished_at = ... WHERE run_id = ?;
  UPDATE current_run SET run_id = ?;      -- ← подмена выдачи
COMMIT;
```

Это заменяет приём «собрать в `leads.building` и подменить файл через
`replace()`». Атомарность та же, проверено на живом SQLite:

```
orgs во время пересборки        [('старые данные',)]   читатель видит снапшот
suppression во время            [('+77010000000',)]    не тронут
orgs после COMMIT               [('новые данные',)]
```

Промежуточных состояний не существует: читатели видят прошлый прогон до
`COMMIT` и новый после.

Побочно появляется откат: `UPDATE current_run SET run_id = 17` возвращает
прошлую выдачу мгновенно, без пересборки.

### Что это даёт

```sql
-- что сделала правка regex
SELECT run_id, count(*) FROM signals_all WHERE type='inbound_widget' GROUP BY run_id;
--   17 | 604
--   18 | 210      ← поправили, ложные ушли

-- какие веса дали больше ответов от лидов
SELECT r.note, count(m.id) FROM runs r JOIN messages m ... GROUP BY r.run_id;
```

`first_seen` чинится сам собой: это первый прогон, в котором компания
появилась, а не колонка, которую забыли заполнить.

### Объём

```
полный снимок базы  ≈ 16 тыс. строк
100 прогонов        ≈ 1.6 млн строк
1000 прогонов       ≈ 16 млн строк
```

SQLite это держит. Ретенция не делается: когда прогонов станет столько, что это
начнёт мешать, правило удаления будет видно из данных, а не угадано сейчас.

### Цена

Запись системы 2 во время пересборки **ждёт её завершения**. Замерено:

```
пересборка длилась        3.0 с
запись системы 2 ждала    2.85 с   ← не отказ, ожидание с busy_timeout
```

Сейчас пересборка занимает секунды — оператор не заметит. Порог, за которым это
надо решать иначе, — примерно 10 секунд.

## 3. Адаптер хранилища сырья

Сырьё остаётся в файлах: по содержимому страниц запросов не делают, читают по
ключу. Класть 464 МБ гzip'а в базу значило бы раздуть её и сломать бэкап, ничего
не получив взамен. Паттерн «блобы отдельно, метаданные в таблице `fetches`» —
тот же, что в production с объектным хранилищем.

Меняется только то, что доступ идёт через модуль, а не через `Path` по всему
коду:

```python
# services/storage.py
def put(url, body, meta) -> str        # -> sha
def get(sha) -> str                     # распакованный текст
def exists(url) -> bool
def iter_pages()                        # сайдкары снимка
```

Единственная реализация — локальная папка, ровно с нынешним поведением
(`<sha1(url)>.html.gz` + сайдкар JSON). Переезд на R2 или MinIO станет вторым
файлом рядом, схема и разбор не тронутся.

## 4. Операции вместо скриптов

### Структура

```
services/storage.py      адаптер сырья
services/store.py        подключение (data/derived.db + ATTACH state), прогоны, запись
services/pipeline/
    collect.py     gis, sites, instagram
    analyze.py     profile, ig_signals        (существующие два слоя, 1:1)
    rebuild.py     пересборка (сюда переезжает build.py)
    export.py      выгрузка CSV (сюда переезжает report.py)
services/jobs.py         очередь + воркер: зовёт функции, не процессы
routes/pipeline.py       HTTP
```

Удаляются: `scripts/collect.py`, `scripts/classify.py`, `scripts/classify_ig.py`,
`build.py`, `report.py`, `scripts/check.py`, `services/probes/*`.

### Контракт операции

Три механизма (stdout, exit code, SIGKILL) заменяются одним объектом:

```python
class RunContext:
    def progress(self, current, total, label): ...   # callback → SSE
    def log(self, message): ...                      # структурный лог
    def check_cancelled(self): ...                   # кооперативная отмена

def sites(ctx: RunContext) -> dict:
    domains = store.domains_without_page()
    for number, domain in enumerate(domains, 1):
        ctx.check_cancelled()
        fetch_home(domain)
        ctx.progress(number, len(domains), "главные страницы")
    return {"collected": len(domains), "skipped": 0}
```

Операция возвращает результат, а не код возврата: он ложится в `jobs.result` и
уходит в SSE — оператор видит «собрано 1088 страниц», а не «exit 0».

Отмена кооперативная: флаг проверяется между единицами работы, запись файла в
`raw/` не рвётся на середине. Отменённый прогон остаётся в `runs` без
`finished_at` и не становится текущим.

### Реестр

```python
OPERATIONS = {
    "collect.gis": collect.gis,
    "collect.sites": collect.sites,
    "collect.instagram": collect.instagram,
    "analyze.profile": analyze.profile,
    "analyze.ig_signals": analyze.ig_signals,
    "rebuild": rebuild.run,
    "export": export.run,
    "probe.gis_list": probe.gis_list,
    "probe.gis_firm": probe.gis_firm,
    "probe.gis_rubrics": probe.gis_rubrics,
    "probe.serp": probe.serp,
}
```

Белый список argv был защитой от инъекции в shell. Реестр функций — та же
защита по построению: имени нет в словаре, вызывать нечего.

`services/probes/*` становятся операциями: они нужны на случай «источник
поменял вёрстку, посмотреть глазами». Ответ — то же, что они печатали, только
JSON вместо `print`.

### Эндпоинты

```
GET  /api/pipeline                 каталог пайплайнов и операций
POST /api/pipeline/{kind}          пайплайн целиком        → 202 {job}
POST /api/operations/{name}        одна операция           → 202 {job}
GET  /api/jobs/{id}                состояние, прогресс, результат
POST /api/jobs/{id}/cancel         кооперативная отмена
GET  /api/runs                     история прогонов
POST /api/runs/{id}/activate       откат выдачи к прогону
GET  /api/suppression/export.csv   выгрузка отказов по требованию
GET  /api/events                   SSE: snapshot | job | log | refresh
```

Операции синхронные (сеть, sqlite), воркер зовёт их через `asyncio.to_thread`:
event loop uvicorn не блокируется, SSE раздаёт события во время многочасового
сбора.

Воркер один. Раньше причиной был `DROP`; теперь — то, что SQLite допускает
одного писателя. Очередь при этом честная.

### Что теряется

Subprocess давал изоляцию бесплатно: упавший скрипт не мог уронить API.
In-process исключение — может. Компенсация: воркер ловит всё, пишет тип и текст
в `jobs.error`, статус `failed`, прогон остаётся незавершённым. Взамен
появляется типизированная ошибка вместо номера.

### Граница «пересборка не ходит в сеть»

Сегодня держится проверкой в `check.py:360` — счётом файлов в `raw/` до и
после. Проверка поведенческая, переезд файла её не трогает.

Усиливается статической: разбором графа импортов убеждаемся, что `rebuild.py`
не тянет `services.fetch` и `scrapling` даже транзитивно.

## 6. Критерий приёмки

Прогон на том же сырье и том же конфиге даёт **то же содержимое**, что нынешняя
`leads.db`: 1660 компаний, 1867 организаций, 7226 контактов, 1876 сигналов, 40
профилей, тот же порядок выдачи.

Сравнение делается разово, скриптом миграции: старая база против view нового
прогона. Расхождение — работа не принята, независимо от того, насколько
красивее стал код.

Дополнительно: два прогона подряд на неизменном сырье дают идентичное
содержимое (нынешний `check_rebuild_is_identical`, переписанный на прогоны).

## 7. Миграция

Одноразовый скрипт, удаляемый после применения:

| откуда | куда |
|---|---|
| `db/leads.db` | `data/derived.db`, прогон №1 с `note = 'миграция'` |
| `db/ops.db` | `data/state.db`, таблица `jobs` |
| `writer/threads.db` | `data/state.db`, таблицы `threads` и `messages` |
| `data/suppression.csv` | `data/state.db`, таблица `suppression` |
| `data/raw/*.llm.json` | `data/state.db`, таблица `llm_answers`; `kind` и `subject` восстанавливаются тем же разбором первой строки промпта, что делает сегодня `fill_profiles` |

157 ответов модели переносятся, а не переспрашиваются: они оплачены. Ответ, для
которого компания не нашлась, не переносится — сегодня он всё равно молча
игнорируется.

`data/raw/` не трогается: файлы остаются на месте, адаптер читает их как есть.

## 9. Риски

- **Нет атомарности между базами.** Операция, которой понадобится записать и в
  `state.db`, и в `derived.db`, не получит транзакции. Сегодня таких нет, и тест
  это сторожит — но требование запомнить придётся.
- **In-process исключение может уронить воркер.** Снимается обработчиком, но это
  единственное место, где нужна дисциплина вместо структурной гарантии.
- **Объём.** 1063 строки проверок, пять точек входа, смена схемы и миграция
  четырёх хранилищ. Работа механическая, но не маленькая, и продуктовой отдачи
  не даёт до следующей спеки.

## Что НЕ делаем

- Postgres и объектное хранилище — по решению о горизонте; адаптеры закладываем.
- Ретенцию прогонов — правило удаления будет видно из данных, а не угадано.
- Несколько параллельных воркеров — SQLite допускает одного писателя.
- Celery, RQ, Redis — очередь на sqlite работает и переживает перезапуск.
- Новые продуктовые операции — они в следующей спеке.
- Изменения содержания выдачи — критерий приёмки требует того же результата.
