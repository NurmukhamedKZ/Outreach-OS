# Система 3 (sender): автоматическая переписка в WhatsApp

Статус: дизайн, одобренный в brainstorming-сессии 2026-08-23.

## Проблема

Конвейер продукта обрывается на человеке. Система 1 находит лида с каналом
`whatsapp`, система 2 пишет черновик — и дальше оператор руками копирует текст
в телефон, отправляет, руками отмечает `sent`, руками вбивает ответ лида
обратно в `messages`. Пропускная способность продукта равна свободному времени
оператора, а не качеству лидов.

Система 3 замыкает разрыв в кольцо:

```
collector: лид с каналом whatsapp
   -> writer.draft (холодное касание)
   -> sender: очередь -> отправка -> подтверждение доставки
   -> вебхук: ответ лида -> messages
   -> агент-продавец: ответ своими словами ИЛИ классификация
   -> sender отправляет / эскалирует человеку
   -> follow-up по расписанию, пока лид молчит
```

Sender — это не «отправлялка», а **транспорт, планировщик и петля обратной
связи**. Описание системы 3 в CLAUDE.md («домены и DNS для холодных писем,
прогрев ящиков, deliverability») относилось к email-каналу и настоящим
дизайном отменяется целиком: главный канал — WhatsApp, и вместо DNS там
номера, лимиты и бан-риск.

## Решения, принятые в brainstorming

| Вопрос | Решение | Почему |
|---|---|---|
| Транспорт | Baileys (неофициальный клиент WhatsApp Web multi-device) за швом `sender/transport.py` | Официальный Cloud API разрешает свободный текст только 24 часа после того, как лид написал первым; холодное касание там — шаблон, одобренный Meta, в который AI-персонализация не помещается |
| Почему не Green API | Аккаунт есть, но Baileys даёт прямой доступ к событиям (presence, статусы, реконнекты), не тянет помесячную плату за инстанс на каждый номер-расходник и делает взаимный прогрев тривиальным | Цена: второй рантайм (Node) и сессии как третий невосстановимый слой — принято осознанно |
| Гибрид с Cloud API (вариант «C») | В бэклог | Требует канала первого касания, которого у продукта пока нет; `thread_id` под мульти-транспорт **не переделываем** |
| Хостинг | Весь backend переезжает на VPS, где уже стоит Langfuse | Вебхуку нужен постоянный публичный HTTPS, планировщику — тик без ноутбука. Sender отдельным сервисом при локальном backend'е дал бы два источника правды на одну переписку |
| Граница автономии | Автопилот до сигнала интереса | ~90% входящих в холодном аутриче — отказ, тишина или «что это?»; их авто-обработка и есть вся экономия. Живые диалоги о деньгах уходят человеку до того, как модель что-то пообещает |
| Механизм петли | Таблица `outbox` + собственный asyncio-цикл в том же процессе | Очередь `state.jobs` исполняет одну операцию за раз (rebuild пересобирает derived) — при многоминутной пересборке ответ лида ждал бы в очереди |
| Холодные касания и follow-up | Существующий `writer/services/agent.py` + схема `Draft` | Нужны `angle` (иначе `used_angles` перестанет разводить follow-up по поводам) и `stop`; диалога нет, цикл крутить не над чем |
| Ответы в диалоге | `create_agent` (langchain 1.3), роль sell manager, единственный инструмент `classify(return_direct=True)` | Есть собеседник и нужен свободный текст; сюда же лягут будущие инструменты (прайс, кейсы, слоты календаря) |
| Классификация входящего | Инструмент агента, а не отдельный вызов модели | Один вызов вместо двух, и решение принимает тот, кто прочитал диалог |
| Стоп-слова («не пишите», «спам», «жалоба») | Регуляркой **до** модели, в обработчике вебхука | `suppression` — юридический контур (F21), он не может зависеть от вероятностной классификации |
| Follow-up | Срок планируется заранее, текст генерируется в момент наступления срока | Заранее сгенерированный текст пролежит в очереди десять дней и уйдёт устаревшим; агент же просыпается только на входящее, а молчащего лида будить некому |
| Уведомления | Telegram-бот + метка в инбоксе, получатель один | Заморозка треда бесполезна, если человек узнаёт о ней, только открыв вкладку |
| Объём | 50 холодных касаний в сутки, 2 рабочих номера + 1 в прогреве | При таком объёме SQLite и один воркер избыточны с запасом; новый слой данных не нужен |
| Режим автопилота | Один флаг `autopilot` = `off` \| `replies` \| `full`, он же kill switch | Ручное подтверждение и автомат кладут строку в **один и тот же** outbox: путь отправки ровно один |

## Границы системы

**Sender делает:** держит соединения с WhatsApp, решает кому/когда/с какого
номера уйдёт сообщение, отправляет, принимает входящие и статусы доставки,
ведёт расписание касаний, следит за здоровьем номеров и прогревает новые,
эскалирует тред человеку.

**Sender не делает:** не решает, что такое «интерес» и какой текст правильный —
это writer; не выбирает лидов — это collector; не оформляет отказ сам, а зовёт
`services/suppression.py` collector'а; не хранит текстов сообщений — они живут
в `messages`.

## 1. Машина состояний треда

Состояние треда не выводится из текстов сообщений: «выдохся», «заморожен» и
«номер забанен» в `messages` не записаны. Поэтому `threads` получает колонку
`status`.

```
  queued  --доставлено-->  active  --молчит 3 касания-->  exhausted
     |                       |
     |                       |--интерес/вопрос-------->  escalated  (тупик для автомата)
     |                       |--отказ----------------->  closed_refused  (+ suppression)
     |                       |--не тот номер---------->  closed_junk
     |
     |--нет WhatsApp-->  unreachable

  наш номер забанен -->  blocked_channel -->  холодный тред: новый номер, назад в queued
                                          \->  тред с ответами: escalated
```

Двигать `status` имеют право ровно четыре актора: планировщик первых касаний,
воркер outbox, обработчик входящего, монитор здоровья номеров.

**Три правила, которые не смягчаются:**

1. **Из `escalated` автомат не выходит.** Только человек, руками, из инбокса.
   Это единственный предохранитель между моделью и живым разговором о деньгах.
2. **`status` меняется в одной транзакции с записью в `messages`/`outbox`.**
   Иначе после падения процесса получаем тред в `active` без отправленного
   сообщения — лида, которому мы «уже написали», а он ничего не получал.
3. **`unreachable` — это тред, а не отсутствие треда.** Городской номер из 2GIS
   проверяется один раз, и результат хранится; иначе планировщик будет каждый
   день долбить проверку по одним и тем же мёртвым номерам.

Контракт writer'а это не ломает: `draft_text` — что предложила модель,
`sent_text` — что реально ушло. Sender просто становится вторым, кто вызывает
`thread_store.confirm()`, и **только после подтверждения доставки** от
транспорта.

## 2. Схема данных

Всё в `state.db` — невосстановимый слой. Новых файлов баз нет.

```sql
-- Очередь исходящих. Текста здесь нет: он в messages.draft_text.
CREATE TABLE IF NOT EXISTS outbox (
  outbox_id    INTEGER PRIMARY KEY,
  message_id   INTEGER NOT NULL REFERENCES messages (message_id),
  thread_id    TEXT NOT NULL,
  our_number   TEXT NOT NULL,
  send_after   TEXT NOT NULL,   -- не раньше этого времени, UTC
  status       TEXT NOT NULL,   -- pending | sending | sent | failed | cancelled | stuck
  attempts     INTEGER NOT NULL DEFAULT 0,
  provider_id  TEXT,            -- id сообщения у транспорта
  delivered_at TEXT,
  read_at      TEXT,
  error        TEXT,
  created_at   TEXT NOT NULL,
  updated_at   TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS outbox_due ON outbox (status, send_after);
CREATE UNIQUE INDEX IF NOT EXISTS outbox_one_per_message ON outbox (message_id);

-- Пул наших номеров.
CREATE TABLE IF NOT EXISTS numbers (
  number      TEXT PRIMARY KEY,
  session_dir TEXT NOT NULL,
  status      TEXT NOT NULL,   -- new | warming | active | quarantined | banned
  started_at  TEXT NOT NULL,   -- дата регистрации: от неё считается день прогрева
  note        TEXT
);
```

**`UNIQUE(message_id)` — не оптимизация, а структурный запрет двойной
отправки.** Одно сообщение — максимум одна строка очереди; повторная постановка
падает на уровне базы, а не на уровне «мы вроде проверяли».

Дневной расход по номеру не денормализуется: считается `count(*)` по outbox за
сутки. При 50 сообщениях в день это бесплатно, а отдельный счётчик рано или
поздно разъедется с реальностью.

**ALTER в существующих таблицах:**

| Таблица | Колонка | Назначение |
|---|---|---|
| `threads` | `status` | состояние из §1, **DEFAULT `'escalated'`** |
| `threads` | `our_number` | с какого нашего номера ведётся чат |
| `threads` | `auto_replies` | сколько раз автомат отвечал своими словами |
| `threads` | `next_touch_at` | когда генерировать следующее касание |
| `threads` | `touch_no` | номер касания, 1..3 |
| `messages` | `provider_id` | id сообщения у транспорта |
| `messages` | `handled_at` | когда входящее обработано агентом; NULL = ждёт тика |

```sql
CREATE UNIQUE INDEX IF NOT EXISTS messages_provider
  ON messages (provider_id) WHERE provider_id IS NOT NULL;
```

**`DEFAULT 'escalated'` для `threads.status` выбран сознательно.** Треды,
существовавшие до системы 3, вёл человек. Миграция не имеет права внезапно
отдать их роботу — они остаются в состоянии, из которого автомат не пишет.

Уникальный индекс по `provider_id` закрывает повтор вебхука: транспорт
повторяет доставку события, если мы не ответили 200, и без индекса в треде
появлялись бы два одинаковых ответа лида, а агент видел бы собеседника,
дважды сказавшего одно и то же.

**Подводный камень миграции.** В SQLite `ALTER TABLE ADD COLUMN` не
идемпотентен, а схема здесь создаётся на каждом старте (`DROP` в
невосстановимом слое запрещён). Второй запуск процесса упал бы с
`duplicate column name`. Решение — `sender/db/migrate.py::ensure_column()`,
которая смотрит `PRAGMA table_info` и добавляет колонку, только если её нет.
Alembic в проект не тащим.

## 3. Транспорт: граница Python и Node

**Node — тупая труба.** Он держит сокеты, шлёт текст, принимает события. Он не
знает про лидов, треды, лимиты и расписание. Причина не эстетическая: Node —
единственная часть системы, которую нельзя протестировать без живого WhatsApp,
поэтому всё, что содержит решение, обязано жить там, где есть база и pytest.

```
POST /send   {number, to, text, type, key}  -> {ok, sent, provider_id}
POST /check  {number, to}                   -> {has_whatsapp}
POST /pair   {number}                       -> pairing code / QR
GET  /health                                -> по номеру: connected | loggedOut | qr_needed,
                                               счётчики реконнектов и re-auth
     webhook -> Python                      : входящее | статус доставки | смена состояния сокета
```

- `key` — ключ идемпотентности (`outbox_id`).
- `sent` — честный флаг «фрейм ушёл в сокет». Именно он отличает безопасный
  ретрай от неопределённости (§4).
- `type` = `text | audio | image`. В боевой отправке используется только
  `text`; `audio`/`image` нужны пассивному прогреву, которому требуется
  разнообразный контент.

Прогрев планирует Python: он решает, какой номер кому пишет и когда, и дёргает
тот же `/send`. Для Node внутренняя переписка неотличима от боевой.

`sender/transport.py` — единственный модуль системы, который ходит в сеть. В
тестах он подменяется целиком; тест графа импортов сторожит, что второй такой
точки не появилось.

## 4. Воркер outbox: гейты и идемпотентность

Одна asyncio-задача в lifespan FastAPI, тик раз в 20 секунд, **одна строка за
тик**. Параллелизма нет: при двух сообщениях в час последовательная обработка
бесплатно снимает все гонки между воркером и вебхуком.

```
pending, send_after <= now
   -> гейты
   -> UPDATE outbox SET status='sending' WHERE outbox_id=? AND status='pending'
   -> transport.send(...)
   -> одной транзакцией: outbox.status='sent', provider_id=..., messages.sent_text=текст
```

Условие `WHERE status='pending'` в третьей строке — захват строки: ноль
обновлённых строк значит, что её взял кто-то другой, и мы молча уходим. Дешевле
любого лока.

**Гейты, в этом порядке — от юридического к техническому:**

1. **suppression (F21).** Лид мог отказаться за те три дня, что follow-up лежал
   в очереди. Проверяется **перед каждой отправкой**, а не при постановке →
   `cancelled`.
2. **Состояние треда.** `escalated` или `closed_*` → `cancelled`: человек уже
   взял тред, автомат в него не пишет.
3. **Окно отправки** (10:00–18:00 Asia/Almaty, пн–пт) → **перенос**:
   `send_after` = начало ближайшего окна.
4. **Номер:** `active` и дневной лимит не выбран, иначе перенос на завтра или
   на другой номер, если тред ещё холодный.
5. **Джиттер:** с прошлой отправки с этого номера прошло меньше случайных
   2–15 минут → перенос.

Различие `cancelled` и переноса принципиально: первое — «это сообщение уже не
нужно», второе — «нужно, но не сейчас». Смешать их значит либо спамить, либо
тихо терять follow-up.

**Идемпотентность.** Процесс может умереть между `transport.send()` и записью
результата. Строка останется в `sending`, и мы не знаем, ушло сообщение или
нет. Оба выхода плохи, но не одинаково: **дубликат в холодном аутриче — прямой
повод нажать Report, потеря сообщения — минус один лид из пятидесяти.** Правило
по умолчанию: не переотправлять автоматически.

- **Структурный уровень.** `UNIQUE(message_id)`: планировщик физически не
  может поставить одно сообщение дважды.
- **Безопасный ретрай.** Только `sent: false` от Node (сокет отвалился, номер
  разлогинен — сообщение точно не ушло) возвращает строку в `pending` с
  backoff 1 / 5 / 30 минут; после трёх попыток `failed` + Telegram.
- **Неопределённость — человеку.** Строка в `sending` дольше пяти минут
  (отправка занимает секунды) уходит в `stuck` + Telegram: «проверь в телефоне,
  ушло или нет». Exactly-once здесь сознательно не строится — при нашем объёме
  это единицы случаев в год. Комментарий `# ponytail:` в коде называет путь
  апгрейда: сверять с историей чата, которую Baileys отдаёт при реконнекте.

**Постановка в очередь.** Создание черновика **никогда** не ставит строку в
outbox само. Ставят двое: кнопка оператора (в любом режиме) и тик воркера — но
только то, что разрешено текущим `autopilot`:

| `autopilot` | Кто уходит сам | Кто ждёт кнопки |
|---|---|---|
| `off` | ничего | всё |
| `replies` | ответы в диалоге | холодные касания, follow-up |
| `full` | всё | — |

**Kill switch.** `autopilot = off` проверяется каждым тиком, кнопка есть в UI.
Автопилот, который нельзя остановить одним нажатием за секунду, — не автопилот,
а происшествие.

**Воркер не должен уметь умирать молча.** Упавшая asyncio-задача исчезает без
строки в логе, и ноль отправок обнаруживается через сутки. Тело цикла целиком в
`try/except`: исключение логируется, спим, продолжаем. Плюс heartbeat — время
последнего тика в базе.

## 5. Входящие: вебхук и агент-продавец

**Вебхук делает только быстрое и детерминированное** и отвечает 200 за
миллисекунды:

1. Дедуп по `provider_id` — вставка падает на уникальном индексе, отвечаем 200
   и молчим.
2. Треда по номеру нет — значит написал тот, кому мы не писали: уведомление в
   Telegram, автомат не трогает.
3. `thread_store.add_incoming(..., provider_id)`.
4. **Отмена запланированных follow-up этого треда** (`outbox -> cancelled`).
   Лид ответил, и «напоминаю о своём сообщении» через три дня станет
   издевательством. Забыть эту строку легко, и именно она превращает систему в
   ту, на которую жалуются.
5. Стоп-слова регуляркой («не пишите», «отпишите», «удалите мой номер», «спам»,
   «жалоба») → `suppression` + `closed_refused` + одно короткое подтверждение.
6. 200. Всё остальное — не здесь.

**Почему стоп-слова до модели.** Классификатор вероятностный, и его проценты
ошибок приходятся ровно на раздражённые короткие сообщения — то есть на тех,
кто и жмёт Report. Правило до модели стоит десять строк и не ошибается никогда.

**Медленное и вероятностное — на тике воркера.** Входящее с
`handled_at IS NULL` подхватывается тем же циклом (отдельной очереди не
заводим), задержка реакции — до 20 секунд.

```python
agent = create_agent(model, tools=[classify], system_prompt=SELL_MANAGER)
```

Контекст: карточка компании (`thread.seed`), текст оффера, диалог из
`thread_store.history()`. Холодное сообщение — просто первое `outgoing` в этом
диалоге: отдельное поле для него было бы вторым представлением того же текста.

Два исхода, третьего нет:

- **Текст** → `messages.draft_text` + постановка в outbox (или ожидание кнопки,
  по режиму), `auto_replies += 1`.
- **Вызов `classify(status, reason)`** → `return_direct=True` обрывает цикл,
  текста нет, и это правильно: все четыре статуса терминальны для автомата.
  `interested` → `escalated` + Telegram; `refusal` → suppression +
  `closed_refused`; `wrong_number` / `junk` → `closed_junk`. `reason` пишется в
  лог — по нему потом видно, за что агент закрывал треды.

Проверено по документации langchain: `@tool(return_direct=True)` короткозамыкает
цикл `create_agent` и возвращает вывод инструмента как финальный ответ. Если
модель за ход вызвала несколько инструментов, замыкание срабатывает, только
когда `return_direct=True` у всех — у нас инструмент один.

**Три предохранителя поверх агента — все `if`, ни один не промпт:**

1. `auto_replies >= 1` → тред уходит в `escalated`, агента не зовём вовсе.
   Автомат имеет право ответить своими словами максимум один раз за тред.
2. `recursion_limit` на цикл: инструмент один и терминальный, больше двух шагов
   там делать нечего.
3. Ответ длиннее `max_reply_chars` или содержащий цифру с валютой →
   эскалация вместо отправки. Дешёвая сетка под самый дорогой класс ошибки —
   придуманную цену.

**Langgraph и чекпойнтер.** `langchain 1.3.15` и `langgraph 1.2.11` уже стоят в
venv (langgraph приезжает транзитивно), новых зависимостей `create_agent` не
требует. Запрет из CLAUDE.md касался **чекпойнтера** как второго источника
правды рядом с `messages`; агент без чекпойнтера его не нарушает — историю
по-прежнему собираем из `messages` руками.

## 6. Follow-up

Срок планируется заранее, текст генерируется в момент наступления срока.

Против «сгенерировать сразу три»: текст пролежит в очереди десять дней, за это
время поправится промпт или сменится оффер — а уйдёт старьё. Против «пусть
решает агент»: агента будит входящее, и молчащего лида будить некому.

Реализация — две колонки, не таблица. Тик берёт треды
`status='active' AND next_touch_at <= now`, зовёт `agent.draft(kind='followup')`,
пишет `messages` + строку outbox, двигает `next_touch_at` по каденции
`[+3д, +7д]`. После третьего касания без ответа → `exhausted`. Любое входящее
обнуляет расписание; `used_angles` не даёт повторить повод.

## 7. Пул номеров и прогрев

Статусы: `new` (сессия есть, молчит) → `warming` (только свои) → `active`
(боевой) → `quarantined` (пауза, возврат на половинном лимите) → `banned`.
**`banned` — терминальный: при блокировке прогрев обнуляется полностью, и
вернувшийся номер по репутации является новым.**

**Календарь прогрева** (источник: рекомендации Green API по прогреву номера,
применимы к любому клиенту того же протокола):

```toml
[warmup]
socket_delay_hours = 24                        # Baileys не привязываем сутки после регистрации
passive_days      = 3                          # дни 2-4: только входящие, ~1 в 2 часа
internal_ramp     = [6, 12, 20, 30, 45, 60]    # дни 4-10, сообщения своим
cold_start_day    = 11
cold_ramp         = [5, 10, 15, 20, 25, 30]
ceiling           = 30
```

Три вещи, в которых календарь строже интуиции:

1. **Первые дни — только входящие.** Новый номер принимает сообщения с уже
   активных и сам молчит. Исходящие начинаются с дня 4, по одному в два часа и
   только контактам.
2. **Холодные касания — примерно с 11-го дня**, не с четвёртого. Полное доверие
   — через 25–30 дней.
3. **Пауза 24 часа — это «не подключать», а не «не отправлять».** Привязка
   сокета сама по себе событие, которое WhatsApp видит.

**Открытие треда.** Тред по-прежнему открывает пайплайн `write` системы 2,
но теперь при открытии он дополнительно зовёт `transport.check()` и
`pool.assign()`: номер без WhatsApp сразу получает тред в состоянии
`unreachable` и больше не проверяется, остальные — `our_number` и `queued`.
Проверка платная только по времени, но делается ровно один раз на лида.

**Выбор номера.** `our_number` присваивается один раз при первом касании и
дальше не меняется: для лида сообщение с другого номера — новый чат без
истории. Выбирается наименее загруженный сегодня `active`; все выбрали лимит →
перенос на завтра, а не отправка через `warming`.

**Монитор здоровья** — раз в час, скользящее окно 7 дней:

| Сигнал | Порог | Действие |
|---|---|---|
| `loggedOut` от Node | — | `banned` немедленно |
| Всплеск реконнектов и запросов повторной аутентификации | из конфига | `quarantined` **до** бана |
| delivered / sent | < 80% при 20+ отправках | `quarantined` |
| replies / sent | < 5% при 20+ отправках | `quarantined` + Telegram |

Строка про реконнекты — единственная метрика, срабатывающая заранее: delivered
и reply rate констатируют задним числом. Отключение связанных устройств и
частые запросы повторной авторизации — задокументированный ранний признак
приближающейся блокировки, а не бытовой сбой сети. Туда же попадают временные
ограничения (задержка отправки, запрет создавать группы): они приходят как
ошибки на `/send` и должны учитываться как метка здоровья номера, а не как
случайный сбой.

Для этого outbox и ведёт `delivered_at`/`read_at`: без них мониторить нечего —
«отправлено» само по себе не значит ничего.

**Бан → треды.** Холодные без ответа переезжают на новый номер и возвращаются в
`queued`: лид, скорее всего, сообщения и не читал. Треды с ответами — в
`escalated`: продолжение с чужого номера выглядит как «кто это?».

**Регистрация номера — ручная операция.** Кнопка в UI → Node отдаёт pairing code
→ код вводится на телефоне → сессия в `sessions/<number>/`. SIM физическая,
автоматизировать нечего. На самой SIM нужно сохранить в контакты остальные наши
номера: прогрев требует общения именно с контактами, а в multi-device контакты
подтягиваются с телефона.

**Проблема курицы и яйца при первом запуске.** Пассивный прогрев требует
входящих от разных контактов, а на старте активных номеров ноль. Первый номер
греется руками — личные телефоны, коллеги; дальше пул греет сам себя.

**`sessions/` попадает в тот же бэкап, что `state.db`.** Потерянная сессия — это
номер, который надо заново подключать телефоном, и в худшем случае разлогин на
живом номере.

## 8. Наблюдаемость

**Langfuse** уже подключён: сессия по `thread_id`, теги `sender.reply` и
`sender.followup`, ссылка на трейс в логе через `observability.log_trace`. Для
агента-продавца это критичнее, чем для холодных касаний: когда лид скажет «вы
обещали X», ответ должен находиться за десять секунд.

**SSE** — тот же `/api/events`; страница «Отправка» перестаёт быть заглушкой на
501 и показывает пул номеров с днём прогрева и здоровьем, очередь, последние
отправки, эскалации.

**`/api/stats`** получает счётчики sender: в очереди, отправлено сегодня, ждут
ответа, эскалировано, номера по статусам, heartbeat воркера и длину очереди
«созревших, но не отправленных» — единственный симптом, по которому одинаково
видно и вставший воркер, и наглухо закрытые гейты.

**Telegram — только события, требующие человека:** эскалация, карантин или бан
номера, застрявшая строка, три неудачных попытки. Одно сообщение на событие.
Уведомление на каждый тик превращается в шум, который перестают читать за
неделю, — а вместе с ним перестают читать и эскалации.

## 9. Тесты

Всё, кроме Node, тестируется без сети: воркер получает `transport` и «сейчас»
аргументами.

- **Гейты:** suppression отменяет, `escalated` отменяет, вне окна переносит,
  лимит номера переносит. Отмена и перенос проверяются раздельно — их подмена
  друг другом и есть тот баг, который либо спамит, либо теряет follow-up.
- **Идемпотентность:** повторная постановка падает на `UNIQUE(message_id)`;
  повторный вебхук с тем же `provider_id` не создаёт второй `incoming`; строка
  в `sending` на старте уходит в `stuck`, а не переотправляется.
- **Машина состояний:** все переходы §1 и отдельным тестом — что из
  `escalated` нет автоматического выхода.
- **`auto_replies = 1`:** второе входящее эскалирует независимо от того, что
  вернул классификатор.
- **Агент с заглушкой модели:** `classify` → правильный переход; текст →
  outbox; текст с валютной цифрой → эскалация вместо отправки.
- **Прогрев:** день от `started_at` → лимит; номер в `warming` не получает
  боевых отправок ни при каких условиях.
- **Бан:** холодные треды переезжают, треды с ответами эскалируются.
- **Граф импортов:** `transport.py` — единственная точка выхода в сеть, по
  образцу теста, который сторожит отсутствие сети в `rebuild.py`.

Живой WhatsApp — отдельный ручной смоук-чеклист, не pytest.

## 10. Порядок выката и стоп-правила

**Этап 0 — начинается до единой строки кода.** Купить три SIM,
зарегистрировать, заполнить профили, сохранить в контакты телефоны команды.
Прогрев — критический путь длиной около двух недель, и он не зависит от
разработки. Начать его в день готовности кода значит заставить продукт ждать
номера.

**Этап 1.** Node-сервис и `transport.py`. Проверка одна: отправить сообщение
самому себе.

**Этап 2.** outbox, воркер, вебхук, `autopilot: off`. Работает только автомат
прогрева — пассивный, затем внутренний. Боевых касаний ноль.

**Этап 3 (примерно день 11).** Первые холодные: один номер, пять в день, каждое
уходит по кнопке. Оператор читает каждое сообщение и правит промпт — ровно то,
ради чего ручное подтверждение и заведено. Ответы разбираются через инбокс:
агент пишет черновик, но не отправляет.

**Этап 4.** `autopilot: replies` на одном номере. Langfuse смотрится ежедневно,
эскалации приходят в Telegram.

**Этап 5.** Три номера, ramp до 30 в сутки, целевые 50 касаний.
`autopilot: full` — не раньше, чем две недели пройдут без сюрпризов.

**Стоп-правила, записанные заранее:**

- Любой бан на этапах 3–4 — остановка и разбор, а не замена номера.
- Reply rate ниже 5% — проблема в тексте; масштабировать её нельзя.
- Хоть одна цифра, которой нет в оффере, ушедшая лиду, — `autopilot`
  возвращается в `off` до выяснения.
