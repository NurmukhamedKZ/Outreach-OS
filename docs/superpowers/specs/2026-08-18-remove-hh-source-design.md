# Удаление источника hh.kz из системы 1 — дизайн

**Дата:** 18 августа 2026
**Статус:** согласован, готов к плану реализации
**Относится к:** [ARCHITECTURE.md](../../ARCHITECTURE.md) §6 «Источники данных», [TRD.md](../../TRD.md) §8, [plans/002-decide-hh-branch.md](../../../plans/002-decide-hh-branch.md) — вариант D

---

## 1. Задача и границы

Убрать hh.kz из конвейера системы 1 целиком: сбор, разбор, таблицу, сигналы, веса,
шаблоны обоснований, разделы проверок, фикстуры и упоминания в документации.

**Почему.** Ветка не даёт ни одного сигнала, и потолок у неё структурный, а не
настроечный. Замеры на текущем `data/raw/`:

| Величина | Значение |
|---|---|
| страниц hh забрано в `raw/` | 458 |
| вакансий разобрано | 384 |
| уникальных работодателей | 321 |
| вакансий привязано к компании | 4 |
| работодателей, достижимых при любом смягчении сравнения имён | 15 (~5%) |
| строк `signals` типа `vacancy_sales` | 0 |
| строк `signals` типа `vacancy_stale` | 0 |

Причина — две почти непересекающиеся популяции. Вакансии собираются с общегородских
SEO-страниц профессий (`[hh].slugs`), то есть по всем, кто нанимает в городе: топ
работодателей — Andersen, BI Group, Itransition, «Этажи». Компании собираются по 36
узким рубрикам B2B-услуг 2GIS. Настройка порога сходства имён их не сведёт: 5% —
это потолок ветки после любой починки, включая точный путь `/employer/{id}` → сайт
→ домен из открытого вопроса №1 TRD.

При этом веса `vacancy_sales = 3.0` и `vacancy_stale = 3.0` — самые высокие в системе,
и они не применяются ни к одному лиду.

**Не входит в эту работу:**

- пересчёт весов по редкости сигнала;
- сбор и разбор отзывов 2GIS (вес `reviews_missed_lead = 3.0` остаётся в
  `config.toml` без производителя — это следующая работа, отдельной спекой);
- любое изменение выдачи. Приёмка требует обратного: `data/leads.csv` обязан
  остаться побайтово тем же.

---

## 2. Инвариант: выдача не меняется

Сигналов `vacancy_*` в базе ноль, значит удаление ветки не сдвигает ни один
`intent_score`. Это делает изменение проверяемым жёстко, а не на глаз.

Снять эталон **до первой правки**, из каталога `collector/`:

```bash
shasum -a 256 data/leads.csv
sqlite3 db/leads.db "select count(*) from signals;"
ls data/raw | wc -l
```

Значения на момент написания спеки:

```
fa96f54ede4cbe07faa06f62275fb7171268ba22932955600cb7486fe115f093  data/leads.csv
1876
7834
```

После работы `uv run build.py && uv run report.py 30` обязан дать те же три числа.
Расхождение означает, что удалено лишнее, — это условие остановки, а не повод
подогнать эталон.

## 3. Что удаляется

### 3.1 `collector/config.toml`

Секция `[hh]` целиком — 21 slug и комментарий о непроверенных фразах. Из
`[scoring]` — `stale_vacancy_days`. Из `[scoring.intent]` — `vacancy_sales`,
`vacancy_stale`.

`vacancy_growth = 3.0` тоже удаляется: он объявлен, но производителя у него нет
и не было ни одного — единственный код, который считал рост числа вакансий, жил
бы в удаляемой ветке.

### 3.2 `collector/scripts/collect.py`

Константы `VACANCY_LIST`, `VACANCY`. Функции `collect_vacancies`, `vacancy_list`,
`vacancy_page`. Ключ `slugs` в `load_plan`, аргумент `--slugs` в `parse_args`.
Возврат `substituted` и блок отказа «ОТКАЗ: N slug'ов подменены общим списком
города» в `main` — вместе с ним уходит `sys.exit` в конце `main`.

Ветки `--sites` и `--instagram` не трогаются. Основная ветка становится
двухшаговой: списки рубрик → карточки филиалов.

### 3.3 `collector/services/sources.py`

`parse_vacancy_ids`, `parse_job_posting`, константы `JSON_LD`, `VACANCY_ID`.

`services/probes/hh_vacancies.py` — файл целиком (единственный внешний потребитель
этих двух функций).

### 3.4 `collector/build.py`

`fill_vacancies`, `vacancy_origins`, вызов `fill_vacancies` в сборке, `"vacancies"`
из кортежа таблиц дампа, регулярки `HH_LIST_URL`, `HH_VACANCY_URL`, константа
`VACANCY_URL`.

Чтение конфига перестаёт возвращать `stale_vacancy_days`: функция отдаёт только
`config["intent"]`, вызов `enrich(...)` теряет последний аргумент.

### 3.5 `collector/services/resolve.py`

`link_employers` и её вызов из `resolve()`. `NAME_SIMILARITY` **остаётся** — её
использует `join_similar_names` при склейке филиалов 2GIS.

### 3.6 `collector/services/enrich.py`

`vacancy_signals`, `stale_vacancies`, `VACANCY_MARKERS`, `quote_around`
(единственный потребитель — `vacancy_signals`), параметр `stale_vacancy_days` у
`enrich()` и её вызов `vacancy_signals`.

Шапка модуля переписывается: «Три источника» → два (сайт компании, лента
инстаграма). Строка про вакансию hh из шапки уходит.

### 3.7 `collector/db/schema.sql`

Таблица `vacancies` вместе с комментарием про `match_confidence`. Комментарий в
шапке «На Ф3 наполняются четыре таблицы: fetches, orgs, contacts, vacancies» →
три. Схема пересобирается через `DROP`, миграций не нужно.

### 3.8 `collector/report.py`

Шаблоны `vacancy_sales` и `vacancy_stale` из `WHY_TEMPLATES`.

### 3.9 `collector/scripts/check.py`

- `check_hh_parsing` и её вызов из `check_parsers`;
- `check_vacancies` и её вызов из `check_build`;
- `check_slug_guard` и её вызов из `check_collect`;
- блок `LINKED_VACANCIES_FLOOR` в `check_resolve` (введён планом 001 как метрика
  решения по этой ветке — вместе с решением он и уходит).

Состав `SECTIONS` не меняется: разделы `parsers`, `build`, `collect`, `resolve`
остаются, просто с меньшим числом проверок внутри.

### 3.10 `collector/fixtures/`

`hh_list.html.gz`, `hh_vacancy.html.gz` — удаляются из git вместе с проверкой,
которая их читала.

### 3.11 `frontend/app/api.ts`

Подписи `vacancy_sales: "Ищет продажников"` и `vacancy_stale: "Вакансия висит
давно"` из словаря типов сигналов.

## 4. Что остаётся намеренно

### 4.1 `data/raw/` не трогаем

458 hh-страниц остаются на диске, и `fetches` продолжает их индексировать после
пересборки. Причины две. Первая — правило проекта: `raw/` невосстановимое сырьё,
а не кэш, и удаление противоречило бы ему сильнее, чем помогло бы место. Вторая —
решение остаётся обратимым без нового похода в сеть: если через полгода появится
способ связать работодателя с компанией, материал для проверки уже лежит.

### 4.2 Единственный `hh` в коде, который выживает

`scripts/check.py`, проверка минимального размера страницы в `check_raw`:

```python
if "2gis.kz" in meta["url"] or "hh.kz" in meta["url"]:
```

Условие остаётся ровно потому, что страницы физически лежат в `raw/` и их размер
по-прежнему надо проверять. Это ожидаемое совпадение при финальном `grep`, а не
недоделка.

### 4.3 Прочее

Ключи `[llm]`, `[rubrics]`, `cities`, остальные веса `[scoring.intent]` и
`[scoring.fit]` — без изменений. `half_life_days` остаётся: затухание применяется
ко всем сигналам, а не только к вакансиям.

## 5. Система 2 (`writer/`)

Единственный выход за пределы `collector/`. Система 2 знает `vacancy_sales` как
угол захода:

- пример типа в промпте — `writer/agent.py:36`, `writer/schemas/outreach.py:32`;
- синтетический сигнал в фикстурах — `writer/scripts/check.py`, семь мест
  (строки 41, 79-80, 104, 110, 129, 143-145, 155, 170, 174, 186-187).

После удаления это тип, который не может появиться никогда: промпт учит модель
несуществующему углу, а проверки прогоняют мёртвую ветку. Заменяется на
`crm_widget` — живой тип, 126 компаний в базе. В `writer/scripts/check.py:80`
вместе с типом меняется и цитата с URL: `"https://hh.kz/vacancy/1"` →
адрес сайта компании, `"нужен менеджер по продажам"` → `"виджет Bitrix24"`.

`writer/` не читает таблицу `vacancies` и не зависит от неё структурно —
`leads_source.py` работает с `companies`, `contacts`, `signals`, `scores`.
Пересборка `leads.db` без `vacancies` систему 2 не ломает.

**Это можно вырезать из работы** без ущерба остальному: тогда система 2 останется
с примером мёртвого типа в промпте, но соберётся и пройдёт проверки.

## 6. Мелкая правка `services/fetch.py`

Функция `demo()` (строки 145-163) строит тестовые адреса из
`https://hh.kz/vacancies/AI_engineer`. Проверяется там логика определения
редиректа, а не hh, — адреса меняются на 2GIS, чтобы тест не ссылался на удалённый
источник.

Вместе с адресами правится текст ассерта «проверка подмены слепа»: он ссылается
на `check_slug_guard`, который удаляется в §3.9. `final_url` продолжает служить
проверке подмены страницы у 2GIS (`check_pagination_guard`), поэтому сама
самопроверка остаётся — меняется только её формулировка. Логика и структура
ассертов не трогаются.

Правятся места, где hh описан как действующий источник: строка про подмену slug'а

Правятся только места, где hh назван действующим источником системы 1. В

самой компании. Умер источник, а не гипотеза. Ревизия BRD — отдельное продуктовое
решение, и подменять его технической уборкой нельзя.

понадобился, владелец продукта выбрал вариант D, числа перенесены в TRD.

## 9. Критерии приёмки

Из каталога `collector/`, после `uv run build.py && uv run report.py 30`:

1. `shasum -a 256 data/leads.csv` совпадает с эталоном §2;
2. `sqlite3 db/leads.db "select count(*) from signals;"` = 1876;
3. `ls data/raw | wc -l` = 7834;
4. `uv run -m scripts.check` — выход 0 на всех десяти разделах;
5. `uv run -m scripts.check parsers` проходит на чистом клоне (раздел не требует
   ни базы, ни `raw/`) — то есть удаление фикстур hh не оставило висящей ссылки;
6. `grep -rn -e vacanc -e 'hh\.kz' collector/ --include='*.py'` даёт ровно одно
   совпадение — `scripts/check.py`, условие размера в `check_raw` (§4.2);
7. `sqlite3 db/leads.db "select name from sqlite_master where name='vacancies';"`
   пусто;
8. из `writer/`: `uv run -m scripts.check` — выход 0;
9. `npm run build` во `frontend/` — успешно.

## 10. Условия остановки

Остановиться и отчитаться, не импровизируя, если:

- `data/leads.csv` после пересборки отличается от эталона. Это значит, что вместе
  с веткой hh задет чужой код: сигналов `vacancy_*` в базе нет, и выдача меняться
  не может;
- `count(*) FROM signals` отличается от 1876 по той же причине;
- в `data/raw/` пропал хоть один файл;
- обнаружился потребитель `vacancies`, не перечисленный в §3, — тогда карта
  удаления неполна, и её надо дополнить до продолжения, а не дорезать по ходу.
