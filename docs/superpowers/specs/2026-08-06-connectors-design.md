**Дата:** 6 августа 2026
**Статус:** согласован, готов к плану реализации
**Относится к:** [ARCHITECTURE.md](../../../ARCHITECTURE.md) §6 «Источники данных», §8 «Пайплайн»

## 1. Задача и границы

Собрать первичные данные о компаниях Казахстана из четырёх каналов детерминированными
скриптами. Каждый скрипт запускается руками, читает аргументы из командной строки и
дописывает JSONL-файл.

**ИИ в сборе не участвует.** Ни один скрипт не обращается к модели. Извлечение
структурированных данных из неструктурированного текста — следующий слой, отдельный от
этого. Причина — правило §11 архитектуры: ИИ недетерминирован, невоспроизводим и
неотлаживаем, а сбор должен быть повторяем побайтово.

**Не входит:** склейка компаний между источниками, скоринг, вызовы LLM, Postgres,
оркестрация, отправка сообщений. Скрипты не знают ни друг о друге, ни о базе.

## 2. Проверенные факты

Всё ниже проверено живыми запросами 6 августа 2026. Это не предположения.

### 2.1 2GIS

**Доступ.** `2gis.kz` редиректит обычный запрос на `/museum` (заглушка «неподдерживаемый
браузер»). Снимается одной cookie:

```
dg5_museum_accept=true
```

После неё обычный HTTP-запрос получает полную SSR-страницу. Браузер не нужен.
Прокси не нужен. 15 запросов подряд без пауз — все `200`, ни капчи, ни `429`.

**Данные.** В HTML лежит весь стейт приложения:

```
var initialState = JSON.parse('...');
```

Внутри — JS-строка с JSON. Разбор в два шага:

```python
raw = re.search(r"var initialState = JSON\.parse\('(.*?)'\);", html, re.S).group(1)
state = json.loads(re.sub(r"\\(['\\])", r"\1", raw))
```

Второй шаг снимает только JS-экранирование (`\'` и `\\`), дальше payload — валидный JSON.
Способ через `unicode_escape` даёт тот же результат, но теряет символы на `errors='ignore'`
— не использовать.

**catalog.api.2gis.com не нужен.** Эндпоинт жив, но требует ключ; ключи, вшитые во
фронт (`webApiKey: c7f1a769-…`), при прямом обращении возвращают `apiKeyIsBlocked`.
SSR отдаёт те же данные без ключа.

**URL-схема:**

| Что | URL | Отдаёт |
|---|---|---|
| Корень рубрикатора | `/{city}/rubrics` | 19 корневых рубрик |
| Ветка рубрикатора | `/{city}/rubrics/subrubrics/{id}` | дочерние рубрики |
| Список организаций | `/{city}/rubric/{id}/page/{n}` | 12 организаций, `total`, `pages` |
| Карточка филиала | `/{city}/firm/{branch_id}` | контакты |

Города: `almaty`, `astana` (`nur-sultan` → 404).

**Пути внутри `state`:**

```
data.search.profile[<uuid>].data          → query, total, pages, currentPage
data.entity.profile[<branch_id>].data     → карточка организации
data.rubricator.items[<rubric_id>]        → {id, name, caption, tag, type}
data.rubricator.lists[<key>].data         → упорядоченный список id
```

**Поля карточки в списке:** `id` (филиал), `org.id` (компания), `org.name`,
`org.branch_count`, `rubrics[].name`, `address_name`, `address`, `point`, `adm_div`,
`reviews.general_rating`, `reviews.general_review_count`, `schedule`, `type`.

**Поля карточки филиала** — то же плюс `contact_groups[].contacts[]`, где `type` бывает
`phone`, `website`, `email`, `instagram`, `whatsapp`. Пример реального ответа:

```
phone     +77080141951, +77474446473, +77082449169
website   http://link.2gis.ru/1.2/…?http://vash-buh.kz
email     fin01@vash-buh.kz
instagram https://instagram.com/nasvazi.vashbuh
whatsapp  https://wa.me/77080141951
```

`website` завёрнут в редирект `link.2gis.ru` — настоящий URL идёт в хвосте после первого `?`.

**Объёмы.** Рубрика `653` «Бухгалтерские услуги» в Алматы: `total: 670`, `pages: 56`.
Верхнеуровневая рубрика `110609` называется «B2B-услуги», внутри неё `110613`
«Бизнес-услуги» с 24 листовыми рубриками — это отрасль v1 из §2.2 архитектуры.
Юридические услуги, HR, IT-аутсорс и клининг лежат в других ветках (`110565` «Услуги»,
`110616` «Для сферы услуг»), поэтому рубрикатор обходится целиком.

### 2.2 hh.kz

**Google не нужен.** §6.2 архитектуры исходит из того, что поиск hh закрыт и искать
должен Google. Проверено — неверно:

```
almaty.hh.kz/vacancies/menedzher_po_prodazham  → 200, 50 id вакансий
hh.kz/vacancy/131909478                        → 200
```

`robots.txt` секции `User-agent: *` содержит `Disallow: *?*` — запрещена **строка
запроса**, а не поиск. SEO-урлы вида `/vacancies/{slug}` идут без параметров и под
запрет не попадают.

Голый HTTP-клиент получает на этих URL `403`. `Fetcher.get(impersonate='chrome')`
проходит: дело в TLS-отпечатке, а не в интерактивном челлендже.

**Данные.** Страница вакансии содержит `<script type="application/ld+json">` с объектом
`@type: JobPosting`:

```
title              Менеджер по продажам, менеджер по работе с клиентами
hiringOrganization.name   Atrium
datePosted         2026-07-31T10:24:16.403+03:00
description        2745 символов
baseSalary         null | объект
```

Это напрямую покрывает `core.vacancies` (§9.1): `title`, `description_full`,
`published_at`, `source_url`. Своего парсера HTML не требуется.

**Пагинация.** `?page=N` работает, но `Disallow: *?*` её запрещает. Чистый SEO-урл даёт
50 вакансий на slug. Для v1 этого достаточно; углубление — открытый вопрос §6.

### 2.3 Scrapling 0.4.12

Установленная версия. Поведение, которое легко понять неправильно:

- **`retries` (по умолчанию 3) и `retry_delay` (по умолчанию 1) встроены в `Fetcher.get`.**
  Свой цикл повторов не нужен.
- **`stealthy_headers=True` по умолчанию** — добавляет браузерные заголовки и
  Google-referer. Именно это, вместе с `impersonate`, проводит запрос через hh.
- **`Response.text` пустой.** Это семантика `Selector` — текст корневого элемента, а не
  документ. Сырой HTML лежит в **`.html_content`**, байты — в `.body`.
- **`.re()` / `.re_first()` работают по извлечённому тексту, не по разметке.** По
  `initialState` они не находят ничего. Regex гнать через `re` по `.html_content`.

## 3. Общий слой — `fetch.py`

Ровно две функции. Всё, что не переиспользуется буквально, живёт в скриптах.

```python
get(url, **kw) -> str
    Fetcher.get(url, impersonate='chrome', **kw) -> .html_content
    Кэш на диск: cache/<sha1(url)>.html. Если файл есть — сеть не трогаем.
    Повторы делает сам Fetcher.

jsonl(path, rows, key)
    Дописать строки в JSONL, пропустив те, чей key уже встречался в файле.
```

Кэш здесь — не оптимизация, а условие отладки: разбор правится по сохранённому HTML без
похода в сеть. Он же служит хранилищем фикстур для проверок — отдельный каталог
`fixtures/` не заводим.

Разбор `initialState` в `fetch.py` **не кладём**: у списка, карточки и рубрикатора разные
ветки стейта, общий у них только regex. Каждый 2GIS-скрипт держит свою функцию разбора.

## 4. Скрипты

Пять штук. У каждого один вход, один выходной файл и `demo()` с ассертами на кэше.

### 4.1 `2gis_rubrics.py` → `raw/2gis_rubrics.jsonl`

Обходит рубрикатор от `/{city}/rubrics` вглубь по `/rubrics/subrubrics/{id}`, пока
появляются новые id.

**Выход:** `{id, name, parent_id}`
**Объём:** ~50 GET, запускается один раз.
**Проверка:** `653` == «Бухгалтерские услуги», у него в предках `110613`.

### 4.2 `2gis_list.py <rubric_id> <city>` → `raw/2gis_list.jsonl`

Берёт `/{city}/rubric/{id}`, читает `total` и `pages`, идёт по `/page/N` до конца.

**Выход:** `{org_id, branch_id, name, org_name, branch_count, rubrics[], address,
point, review_count, rating, city, rubric_id}`
**Объём:** 12 записей на GET; рубрика `653` Алматы = 56 GET.
**Дедуп:** по `branch_id`.
**Проверка:** на кэше страницы 1 — 12 записей, `total` совпадает с полем в стейте,
кириллица в `name` не побита.

### 4.3 `2gis_firm.py` → `raw/2gis_firm.jsonl`

Читает `raw/2gis_list.jsonl`, для каждого `branch_id` берёт `/{city}/firm/{branch_id}`,
разбирает `contact_groups`.

Берёт **все** `branch_id` из файла — своей фильтрации у скрипта нет. Отбор задаётся тем,
по каким рубрикам был запущен `2gis_list.py`: не нужна рубрика — не собираем её список.
Так дорогой шаг (карточки) никогда не выполняется для того, что заведомо отсеется.

**Выход:** `{branch_id, phones[], website, emails[], instagram, whatsapp[]}`
**Особенность:** `website` разворачивается из редиректа `link.2gis.ru` — берём хвост
после первого `?`.
**Проверка:** на кэше карточки `70000001037962810` — 3 телефона, `website` равен
`http://vash-buh.kz` (а не ссылке `link.2gis.ru`), email извлечён.

### 4.4 `hh_vacancies.py <slug> <city>` → `raw/hh_vacancies.jsonl`

Берёт `{city}.hh.kz/vacancies/{slug}`, вытаскивает id вакансий регуляркой
`/vacancy/(\d{6,})`, по каждому id забирает страницу и читает JSON-LD `JobPosting`.

**Выход:** `{vacancy_id, title, employer, published_at, description, url, city}`
**Объём:** 50 вакансий на slug, 51 GET.
**Проверка:** на кэше вакансии — `@type` == `JobPosting`, `employer` непустой,
`description` длиннее 200 символов.

### 4.5 `serp.py <query>` → `raw/serp.jsonl`

`POST` в Serper.dev, ключ из переменной окружения.

**Выход:** `{query, url, title, snippet, position}`
**Проверка:** разбор ответа на сохранённом JSON, без обращения к сети.

## 5. Известные пробелы

Помечаются в коде комментарием `ponytail:` с указанием потолка и пути наверх.

**Склейка hh ↔ 2GIS.** hh отдаёт работодателя строкой («Atrium»), 2GIS — «Atrium, ТОО».
Сопоставление по имени нечёткое, это правило «trgm_name_city» из §9.3 с ручной проверкой.
Точный путь существует: со страницы вакансии есть ссылка `/employer/{id}`, а на странице
работодателя — сайт, то есть склейка по домену, «точно» по той же таблице. Цена — ещё
один GET на вакансию и отдельный разбор. В MVP не входит.

**Глубина hh.** 50 вакансий на slug без нарушения `robots.txt`. Больше — только через
`?page=N`, что `Disallow: *?*` запрещает. Решение отложено до момента, когда 50 окажется
мало.

**Стабильность `initialState`.** Разбор завязан на внутреннюю структуру фронта 2GIS,
которая может поменяться без предупреждения. Смягчается кэшем и ассертами в `demo()`:
поломка проявится как упавшая проверка, а не как тихо пустые поля.

## 6. Порядок реализации

1. `fetch.py`
2. `2gis_list.py` — даёт охват, проверяет главную гипотезу
3. `2gis_firm.py` — даёт контакты, закрывает `require_at_least_one_of` из §13
4. `2gis_rubrics.py` — нужен, чтобы выйти за пределы одной рубрики
5. `hh_vacancies.py` — главный intent-сигнал
6. `serp.py` — ЛПР и добор компаний вне 2GIS

Первые три дают полный сегмент с контактами. Это минимальный набор, на котором видно,
годятся ли данные вообще.
