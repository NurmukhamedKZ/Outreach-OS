# Операционный слой системы 1 (этапы 1–2)

Статус: дизайн, одобренный в brainstorming-сессии 2026-08-18.
Первая из двух спек. Здесь — инфраструктура: замена CLI-скриптов на
HTTP-операции, переезд проверок на pytest, кэш ответов модели в отдельной базе.
Продуктовая часть — в `2026-08-18-ai-signals-design.md`, она опирается на эту.

**Продуктового результата эта работа не даёт намеренно.** Переносится
существующее один в один.

## Критерий приёмки

После этой работы `leads.db` собирается **идентичной**: те же 1660 компаний,
1876 сигналов, 40 профилей, тот же порядок выдачи. Проверка на это в проекте
уже есть — `check_rebuild_is_identical`, она переезжает в pytest и становится
приёмочной.

Если база разошлась — работа не принята, независимо от того, насколько
красивее стал код.

## Проблема

### Слой джобов запускает скрипты через subprocess

| что | где | следствие |
|---|---|---|
| прогресс парсится из stdout по префиксу `#progress ` | `jobs.py:_parse_progress` | в docstring честно: «Скрипты таких строк пока не пишут; парсер ждёт их» — **прогресс-бар в UI не работает вообще** |
| результат шага = `process.returncode` | `_run_step` | «нет `OPENROUTER_API_KEY`» и «сеть отвалилась» неразличимы: обе ненулевой код |
| отмена = `os.killpg(SIGKILL)` | `cancel` | убивает на середине записи файла в `raw/` |
| проверка пайплайна = `argv[:2] == ["uv","run"]` | `check_pipelines` | проверяется форма строки, а не существование операции |
| `uv run` на каждый из 4 шагов | `STEPS` | ~2с оверхеда на шаг и зависимость от `uv` внутри контейнера |

### Кэш ответов модели лежит файлами в `data/raw/`

Причина, по которой он слева от границы, верна: `db/schema.sql` начинается с
`DROP`, и ответ модели в `leads.db` умер бы на первой пересборке. Но вывод
неверный — невосстановимому слою нужна своя база, а не папка. Такой паттерн в
проекте уже есть: `writer/threads.db`.

1. Ключ восстанавливается из текста промпта
   (`lines[0].removeprefix("Компания: ")`). Каждый новый вид ответа — ещё один
   парсер первой строки, и каждый ломается от правки промпта.
2. Нельзя спросить «кого ещё не обработали» иначе как прочитав все файлы.
3. Протухшие ответы неотличимы от живых: правка промпта оставляет старые файлы
   лежать навсегда.
4. 157 ответов вперемешку с 7677 страницами в папке на 464 МБ.

### Проверки — самописный скрипт

```
collector/scripts/check.py   837 строк, 30 функций, 10 разделов
writer/scripts/check.py      226 строк
```

Всё или ничего по разделам, без изоляции состояния между проверками.

## 1. Операции вместо скриптов

### Структура

```
services/pipeline/
    collect.py     gis, sites, instagram
    analyze.py     profile, ig_signals        (существующие два слоя, 1:1)
    rebuild.py     пересборка базы (сюда переезжает build.py)
    export.py      выгрузка CSV (сюда переезжает report.py)
services/jobs.py   очередь + воркер: зовёт функции, не процессы
routes/pipeline.py HTTP
```

Удаляются: `scripts/collect.py`, `scripts/classify.py`, `scripts/classify_ig.py`,
`build.py`, `report.py`, `scripts/check.py`, `services/probes/*`.

### Контракт операции

Три механизма (stdout, exit code, SIGKILL) заменяются одним объектом:

```python
class RunContext:
    def progress(self, current, total, label): ...   # callback → SSE
    def log(self, message): ...                      # структурный лог
    def check_cancelled(self): ...                   # кооперативная отмена

def sites(ctx: RunContext) -> dict:
    domains = store.domains_without_page()
    for number, domain in enumerate(domains, 1):
        ctx.check_cancelled()
        fetch_home(domain)
        ctx.progress(number, len(domains), "главные страницы")
    return {"collected": len(domains), "skipped": 0}
```

Операция возвращает результат, а не код возврата: он ложится в `jobs.result` и
уходит в SSE — оператор видит «собрано 1088 страниц», а не «exit 0».

Отмена кооперативная: флаг проверяется между единицами работы, запись файла в
`raw/` не рвётся на середине.

### Реестр

```python
OPERATIONS = {
    "collect.gis": collect.gis,
    "collect.sites": collect.sites,
    "collect.instagram": collect.instagram,
    "analyze.profile": analyze.profile,
    "analyze.ig_signals": analyze.ig_signals,
    "rebuild": rebuild.run,
    "export": export.run,
    "probe.gis_list": probe.gis_list,
    "probe.gis_firm": probe.gis_firm,
    "probe.gis_rubrics": probe.gis_rubrics,
    "probe.serp": probe.serp,
}
```

Белый список argv был защитой от инъекции в shell. Реестр функций — та же
защита по построению: имени нет в словаре, вызывать нечего.

`services/probes/*` не удаляются в никуда, а становятся операциями: они нужны
на случай «источник поменял вёрстку, посмотреть глазами». Ответ — то же, что
они печатали, только JSON вместо `print`. Второго механизма не появляется.

### Эндпоинты

```
GET  /api/pipeline                каталог пайплайнов и операций
POST /api/pipeline/{kind}         пайплайн целиком         → 202 {job}
POST /api/operations/{name}       одна операция            → 202 {job}   новое
GET  /api/jobs/{id}               состояние, прогресс, результат
POST /api/jobs/{id}/cancel        кооперативная отмена
GET  /api/events                  SSE: snapshot | job | log | refresh
```

Операции синхронные (сеть, sqlite), воркер зовёт их через `asyncio.to_thread`:
event loop uvicorn не блокируется, SSE продолжает раздавать события во время
многочасового сбора.

Воркер один — ограничение сохраняется: пересборка идёт через `DROP`,
параллельный запуск писал бы в ту же базу. Очередь при этом честная.

### Что теряется

Subprocess давал изоляцию бесплатно: упавший скрипт не мог уронить API.
In-process исключение — может. Компенсация: воркер ловит всё, пишет тип и текст
в `jobs.error`, статус `failed`. Взамен появляется то, чего не было:
типизированная ошибка вместо номера.

### Граница «пересборка не ходит в сеть»

Сегодня держится проверкой в `check.py:360` — счётом файлов в `raw/` до и
после. Проверка поведенческая, переезд файла её не трогает.

Усиливается статической: разбором графа импортов убеждаемся, что `rebuild.py`
не тянет `services.fetch` и `scrapling` даже транзитивно. Раньше гарантия
держалась на том, что инструмента нет в файле; теперь — на том, что его нет в
графе импортов.

## 2. Кэш ответов модели

```sql
-- db/llm_cache.db
CREATE TABLE IF NOT EXISTS answers (
  request_sha  TEXT PRIMARY KEY,   -- sha256(модель + промпт)
  kind         TEXT NOT NULL,      -- вид ответа
  subject      TEXT NOT NULL,      -- company_id / username — явно, не из промпта
  model        TEXT NOT NULL,
  prompt       TEXT NOT NULL,
  answer       TEXT NOT NULL,      -- JSON
  created_at   TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS answers_subject ON answers (kind, subject);
```

`CREATE TABLE IF NOT EXISTS`, `DROP` запрещён, в git не лежит — как
`threads.db`. Это невосстановимый слой: ответы оплачены.

`subject` в колонке даёт то, чего файловый кэш не мог дать одновременно: промпт
остаётся стабильным (кэш не обесценивается сменой схемы идентификаторов), а
ключ при этом явный, а не выковырянный `removeprefix`.

Пересборка по-прежнему читает готовые ответы и по-прежнему не умеет ходить в
сеть — граница системы не двигается.

### Миграция 157 существующих ответов

Переносятся как есть: `kind` и `subject` восстанавливаются из промпта тем же
разбором, что делает сегодня `fill_profiles`, — один раз, скриптом миграции,
который потом удаляется.

Это единственное место, где старый разбор первой строки промпта ещё
используется. Ответ, для которого компания не нашлась, не переносится: сегодня
он всё равно молча игнорируется.

Альтернатива — не переносить вовсе и переспросить (~$0.02) — остаётся
запасным вариантом, если миграция окажется дороже переспроса. Решение
принимается при реализации, на критерий приёмки оно не влияет: `profiles`
обязаны собраться те же.

## 3. Проверки: pytest

```
collector/tests/
    test_parsers.py     ← единственный, работающий на чистом клоне (только fixtures/)
    test_raw.py  test_build.py  test_resolve.py  test_signals.py
    test_scores.py  test_leads.py  test_operations.py
    conftest.py         ← фикстуры: временная база, снимок raw/
writer/tests/
    test_schema.py  test_threads.py  test_leads.py  test_prompt.py
```

Раздел = файл. Ассерты переносятся дословно — меняется обёртка, не смысл.

`pytest` в dev-зависимостях — единственная новая зависимость за всю работу.

Выигрыш помимо соответствия требованию: падает один тест, а не раздел целиком;
`conftest.py` даёт каждому тесту свою временную базу.

### Новое в проверках

| тест | что проверяет |
|---|---|
| `test_operations` | каждое имя в `OPERATIONS` вызываемо; `rebuild` не тянет сеть по графу импортов |
| `test_cache` | запись/чтение `llm_cache.db`; ключ не зависит от порядка полей |
| `test_build::test_rebuild_is_identical` | **приёмочный**: база собирается той же |

## 4. Фронтенд

`frontend/` вызывает `/api/pipeline/*`. Каталог операций расширяется, поэтому
консоль получает вторую группу кнопок — отдельные операции рядом с готовыми
пайплайнами. Прогресс-бар начинает работать впервые: до этого он ждал строк
`#progress`, которых никто не писал.

## 5. Риски

- **In-process исключение может уронить воркер.** Снимается обработчиком в
  воркере, но это единственное место, где нужна дисциплина вместо структурной
  гарантии.
- **`rebuild` в одном процессе с `collect`.** Граница «пересборка не ходит в
  сеть» перестаёт держаться на отсутствии импорта в файле и начинает держаться
  на тесте графа импортов. Ослабление реальное, компенсация — тест.
- **Объём.** 1063 строки проверок плюс пять точек входа. Работа механическая,
  но не маленькая, и продуктовой отдачи не даёт до следующей спеки.

## Что НЕ делаем

- Несколько параллельных воркеров — пересборка через `DROP` этого не допускает.
- Celery, RQ, Redis — очередь на sqlite уже работает и переживает перезапуск.
- Новые продуктовые операции — они в следующей спеке.
- Изменения схемы `leads.db` — критерий приёмки требует идентичной базы.
