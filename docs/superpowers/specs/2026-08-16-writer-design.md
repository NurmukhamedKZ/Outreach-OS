# Writer (Система 2) — AI-персонализация исходящей переписки

Статус: дизайн, одобренный в brainstorming-сессии 2026-08-16.
Продукт — три системы; этот документ описывает вторую: агентную генерацию
персонализированных сообщений по данным системы 1 (`collector/`), с доставкой
через человека-оператора до появления системы 3 (`sender/`).

## Решения, принятые в brainstorming

| Вопрос | Решение |
|---|---|
| Чей оффер | Наш продукт (AI lead generation). Один оффер, зашит в `writer/config.toml` |
| Канал | WhatsApp-сообщения: канал, который реально есть у лидов (у collector почты почти нет) |
| Кто отправляет | Оператор, вручную из WhatsApp Web. Writer готовит тексты |
| Архитектура генерации | Беседа с состоянием в собственной таблице: тред на лида, `thread_id = "+7..."` (номер телефона), один structured-output вызов LLM на ход. Без langgraph-чекпойнтера и без цикла tool-calling |
| Цепочка | Не печётся заранее. Emerges из треда: ответ лида или молчание N дней → следующий ход агента |
| Ответы лидов | Оператор вставляет ответ в веб-консоли → ответ попадает в тред |
| Правки оператора | Черновик ≠ отправлено. В тред пишется только финальный отредактированный текст |

Подход A из сессии: `writer/` зеркалит паттерны `collector/` (config.toml,
pydantic-схемы, check-секции), читает готовую `collector/db/leads.db`, в
collector не пишет.

## Граница системы

- **Вход:** `collector/db/leads.db` (чтение), `collector/data/raw/*.llm.json`
  не нужны — всё нужное уже в базе (profiles, signals, scores, channels).
- **Выход:** `writer/threads.db` (переписка), черновики сообщений оператору.
- **Не делает:** сбор данных, скоринг, отправку, suppression-файл (refusal
  уходит существующим flow'ом collector'а: оператор отмечает отказ → writer
  проверяет suppression до каждого хода).

`build.py` и пересборка collector'а writer'у безразличны: company_id в тредах
ссылается на лид, а не наоборот; если лид исчез после пересборки, тред живёт
своей жизнью (переписка уже невосстановима снаружи).

## Компоненты

```
writer/
  config.toml          оффер, модель, каденция follow-up, лимиты
  agent.py             ходы переписки: seed → draft → (edit) → send → reply/silence
  schemas/outreach.py  pydantic-схемы: Draft, Message, RefusalMark
  thread_store.py      SQLite: таблицы threads и messages (draft vs sent)
  leads_source.py      чтение collector/db/leads.db: кандидаты + suppression-проверка
  scripts/write.py     сетевая сторона: первые сообщения для топ-N лидов
  scripts/check.py     офлайн-проверки (без LLM, без сети)
  api.py               роутер для collector/api.py (тонкая склейка)
```

### config.toml

Единственное место конфигурации, по образцу collector. Оффер — текстом:
системный промпт ссылается на него, смена оффера не требует правки кода.

```toml
[llm]
model = "deepseek/deepseek-v4-flash"
temperature = 0.7          # письма, не извлечение: 0 из classify не годится

[cadence]
followup_days = [3, 7]     # молчание: день 3 — новый угол, день 7 — последний

[offer]
text = """..."""           # что продаём, кому, каким языком
```

### Схемы (schemas/outreach.py)

- `Draft` — ответ агента: `text` (сообщение), `angle` (чем зацепили: «вакансия
  продаж», «реклама на сайте»...), `stop` (bool: агент советует не писать).
- `Message` — строка в `messages`: `thread_id`, `role` (outgoing/incoming),
  `draft_text`, `sent_text` (null для incoming), `angle`, `created_at`,
  `sent_at`.
- `RefusalMark` — вручную оператором, дублируется в suppression-flow collector'а.

### Агент (agent.py)

Без langgraph и без цикла tool-calling: инструментов у агента нет, на ход
нужен ровно один вызов модели со structured output — как в `classify.py`
(`ChatOpenAI(base_url=openrouter).with_structured_output(Draft)`).

Память треда — таблица `messages` в `writer/threads.db`, а не чекпойнтер.
Причина: протокол draft → edit → send требует, чтобы неподтверждённый
черновик **не** попадал в историю, а чекпойнтер аппендит ответ модели в
состояние автоматически. Плюс таблица всё равно нужна вебу (draft vs sent) —
чекпойнтер сверху дал бы второй источник правды.

`thread_id = "+7..."` — номер WhatsApp лида из каналов collector'а.

Ходы переписки (обычные функции, не узлы графа):

1. **seed** — при создании треда: строка в `threads` с контекстом лида из
   системы 1 (имя, город, отрасль, `why_now`, цитата, сигналы с типами —
   углы для follow-up). LLM не вызывается.
2. **draft** — сборка сообщений (system: роль + оффер из config; далее seed и
   история треда: только `sent_text` и incoming) → один вызов → `Draft`
   пишется в `messages` со статусом draft.
3. **confirm** — человек. Оператор правит или нет, жмёт «отправлено» →
   `sent_text` + `sent_at`. LLM-вызов не повторяется.
4. **reply** — incoming-сообщение от оператора → новый draft.
5. **silence** — кнопка «молчит N дней» → draft с новым углом (первый угол
   из сигналов, ещё не использованный в треде; «checking in» запрещён промптом).

Апгрейд-путь: если агенту понадобятся инструменты (сам лезет в базу лидов за
контекстом) — переход на `create_agent` с чекпойнтером, `messages` переезжает
туда.

### leads_source.py

Читает `collector/db/leads.db` (путь — в config.toml). Отбор кандидатов —
SQL по образцу `report.CANDIDATES`, но **без импорта collector-кода**: writer
не должен зависеть от Python-окружения другой системы. F19/F21 воспроизводятся
запросом: канал в (whatsapp, phone), handle не в suppression, intent > 0.
Проверка suppression повторяется перед **каждым** ходом агента — не только
при отборе.

### scripts/write.py

Сетевая сторона, как `classify.py`: топ-N лидов из leads_source, seed тредов
(если треда нет), draft первого сообщения. Печатает готовые к отправке
черновики. `--env-file .env` для OPENROUTER_API_KEY, проверка ключа до сети.

### Веб (api.py + фронтенд)

`collector/api.py` монтирует один роутер из `writer/api.py`. Фронтенд получает
в карточке лида секцию «переписка»:

- история треда (incoming + sent, без черновиков);
- текущий черновик: текст, угол, кнопки «править» → «отправлено»;
- поле «вставить ответ лида»;
- кнопка «молчит N дней» → новый черновик с новым углом;
- кнопка «отказ» → RefusalMark + подсказка занести в suppression.

Два процесса сохраняются (FastAPI 8787 + Next.js 3000).

### scripts/check.py (writer)

Офлайн, без LLM и сети — аналог `check_parsers`:

- `threads`: у каждого треда `thread_id` — валидный телефон, не в suppression;
  у каждого outgoing sent-сообщения есть draft_text (история правок цела).
- `schema`: эталонный ответ агента (в fixtures) валиден по `Draft`;
  запрещённые фразы («checking in», «просто напоминаю») не проходят.
- `leads_source`: на эталонной тестовой базе (fixtures) отбор воспроизводит
  F19/F21.

## Цикл данных

```
collector/db/leads.db ──read──> seed треда ──> draft#1 ──edit──> sent#1
                                   ↑                            │
                                   │                     WhatsApp Web
                                   │                     (оператор)
                            reply/silence                     │
                                   ↑                            │
                            incoming <──── оператор вставляет ответ
```

## Стоимость

LLM-вызов только на реально случившиеся ходы: draft первого сообщения, ответ
на reply, follow-up по молчанию. Правка оператора и confirm — бесплатны.
Черновики, не ставшие sent (лид потерян), не порождают новых вызовов.

## Error handling

- Нет OPENROUTER_API_KEY — отказ до сети (как classify).
- Лид исчез из collector'а после пересборки — тред живёт, но seed-данные уже
  в нём; новые ходы разрешены.
- suppression появился после seed — ход агента блокируется проверкой
  leads_source перед каждым draft.
- Агент вернул `stop: true` — черновик не предлагается, тред помечается
  «агент советует стоп», решение за оператором.

## Testing

- `uv run -m scripts.check` в writer/ — без сети, на fixtures.
- Ручная проверка цикла: seed → draft → edit → reply → draft на одном лидe
  перед мержем.
- Ходы агента тестируются на временной SQLite-базе с заглушкой LLM (клиент
  модели инжектится, а не создаётся внутри).
