# Sender, часть 1: транспорт и пул номеров

Статус: дизайн. Выделено 2026-08-28 из общей спеки системы 3.

Зонтичный документ — [2026-08-23-sender-whatsapp-design.md](2026-08-23-sender-whatsapp-design.md):
проблема, границы системы, дерево модулей, `config.toml`, машина состояний
треда, порядок выката целиком. Здесь — только то, что нужно, чтобы у продукта
появились живые прогретые номера, с которых можно писать.

**Почему это первая часть.** Прогрев — критический путь длиной около двух
недель, и он не зависит от разработки: SIM покупаются, регистрируются и
греются, пока пишется код очереди. Начать прогрев в день готовности кода
значит заставить продукт ждать номера.

**Область:** Node-сервис Baileys, `transport.py`, таблицы `numbers` и `outbox`
(последняя — как журнал отправок, логику очереди строит часть 2), идемпотентные
миграции, календарь и цикл прогрева, монитор здоровья, Telegram-канал аварий.
Ничего про очередь, гейты и агента — это части 2 и 3.

**План реализации:** [2026-08-28-sender-transport-and-numbers.md](../plans/2026-08-28-sender-transport-and-numbers.md) — 13 задач.

**Готово, когда:** номер зарегистрирован через pairing code, `transport.send`
доставляет сообщение самому себе, прогревочный тик сам пишет с одного нашего
номера на другой по календарю от `started_at`, а `loggedOut` от Node переводит
номер в `banned` с уведомлением в Telegram.

## 1. Схема: пул номеров и миграции

Всё в `state.db` — невосстановимый слой. Новых файлов баз нет.

```sql
-- Пул наших номеров.
CREATE TABLE IF NOT EXISTS numbers (
  number      TEXT PRIMARY KEY,
  session_dir TEXT NOT NULL,
  status      TEXT NOT NULL,   -- new | warming | active | quarantined | banned
  started_at  TEXT NOT NULL,   -- дата регистрации: от неё считается день прогрева
  note        TEXT
);

-- Журнал и очередь отправок. Логику очереди строит часть 2; здесь таблица
-- нужна как журнал: по ней считается дневной расход номера.
-- message_id/thread_id пусты у прогревочных отправок — сообщения лиду за ними
-- нет, а лимит номера они тратят наравне с боевыми.
CREATE TABLE IF NOT EXISTS outbox (
  outbox_id    INTEGER PRIMARY KEY,
  message_id   INTEGER REFERENCES messages (message_id),
  thread_id    TEXT,
  recipient    TEXT,            -- кому ушло прогревочное; у боевых — из треда
  our_number   TEXT NOT NULL,
  send_after   TEXT NOT NULL,   -- не раньше этого времени, UTC
  status       TEXT NOT NULL,   -- pending | sending | sent | failed | cancelled | stuck
  attempts     INTEGER NOT NULL DEFAULT 0,
  provider_id  TEXT,            -- id сообщения у транспорта
  delivered_at TEXT,
  read_at      TEXT,
  error        TEXT,
  created_at   TEXT NOT NULL,
  updated_at   TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS outbox_due ON outbox (status, send_after);
CREATE INDEX IF NOT EXISTS outbox_by_number ON outbox (our_number, status, updated_at);
CREATE UNIQUE INDEX IF NOT EXISTS outbox_one_per_message ON outbox (message_id);
```

**Почему `outbox` создаётся здесь, а не вместе с очередью.** Дневной лимит
нужен уже в этой части: прогрев шлёт внутренние сообщения по `internal_ramp`, и
их надо считать. Расход не денормализуется — это `count(*)` по `outbox` за
сутки; отдельный счётчик рано или поздно разъедется с реальностью, и разъедется
молча. Прогревочная отправка при этом не является сообщением лиду: строки в
`messages` за ней нет, поэтому `message_id` и `thread_id` — nullable.
`UNIQUE(message_id)` от этого не страдает: в SQLite `NULL` в уникальном индексе
сам с собой не конфликтует, и структурный запрет двойной отправки боевого
сообщения (часть 2) работает как задумано.

Альтернатива — отдельный журнал прогрева — это вторая таблица с тем же смыслом
и два места, где считается дневной расход.

**Подводный камень миграции.** В SQLite `ALTER TABLE ADD COLUMN` не
идемпотентен, а схема здесь создаётся на каждом старте (`DROP` в
невосстановимом слое запрещён). Второй запуск процесса упал бы с
`duplicate column name`. Решение — `sender/db/migrate.py::ensure_column()`,
которая смотрит `PRAGMA table_info` и добавляет колонку, только если её нет.
Alembic в проект не тащим.

## 2. Транспорт: граница Python и Node

**Node — тупая труба.** Он держит сокеты, шлёт текст, принимает события. Он не
знает про лидов, треды, лимиты и расписание. Причина не эстетическая: Node —
единственная часть системы, которую нельзя протестировать без живого WhatsApp,
поэтому всё, что содержит решение, обязано жить там, где есть база и pytest.

```
POST /send   {number, to, text, type, key}  -> {ok, sent, provider_id}
POST /check  {number, to}                   -> {has_whatsapp}
POST /pair   {number}                       -> pairing code / QR
GET  /health                                -> по номеру: connected | loggedOut | qr_needed,
                                               счётчики реконнектов и re-auth
     webhook -> Python                      : входящее | статус доставки | смена состояния сокета
```

- `key` — ключ идемпотентности (`outbox_id`). Node его помнит: повтор с тем же
  ключом возвращает `provider_id` первой отправки и второго сообщения не шлёт.
  Дубликат в холодном аутриче — прямой повод нажать Report, и защита от него не
  может жить только на стороне Python.
- `sent` — честный флаг «фрейм ушёл в сокет». Именно он отличает безопасный
  ретрай от неопределённости. Поэтому `sent: false` Node отдаёт только когда
  сокет и не был поднят; ошибка на живом сокете (таймаут подтверждения по уже
  ушедшему фрейму) — это 500 и `TransportError`, то есть «неизвестно», а не
  приглашение отправить лиду второе такое же сообщение.
- `type` = `text | audio | image`. В боевой отправке используется только
  `text`; `audio`/`image` нужны пассивному прогреву, которому требуется
  разнообразный контент.

Прогрев планирует Python: он решает, какой номер кому пишет и когда, и дёргает
тот же `/send`. Для Node внутренняя переписка неотличима от боевой.

`sender/transport.py` — единственный модуль системы, который ходит в сеть. В
тестах он подменяется целиком; тест графа импортов сторожит, что второй такой
точки не появилось.

## 3. Пул номеров и прогрев

Статусы: `new` (сессия есть, молчит) → `warming` (только свои) → `active`
(боевой) → `quarantined` (пауза, возврат на половинном лимите) → `banned`.
**`banned` — терминальный: при блокировке прогрев обнуляется полностью, и
вернувшийся номер по репутации является новым.**

**Календарь прогрева** (источник: рекомендации Green API по прогреву номера,
применимы к любому клиенту того же протокола):

```toml
[warmup]
socket_delay_hours = 24                        # Baileys не привязываем сутки после регистрации
passive_days      = 3                          # дни 2-4: только входящие, ~1 в 2 часа
internal_ramp     = [6, 12, 20, 30, 45, 60]    # дни 5-10, сообщения своим
cold_start_day    = 11
cold_ramp         = [5, 10, 15, 20, 25, 30]
ceiling           = 30
tick_minutes      = 10                         # одна прогревочная отправка за тик
tick_jitter_minutes    = 4                     # разброс: :00, :10, :20 — машинный почерк
passive_interval_hours = 2                     # как часто новичок принимает на днях 2-4
phrases           = ["привет, как дела", "созвонимся завтра?", "принял, спасибо"]
```

**`ceiling` не режет `internal_ramp`.** Это предел холодных касаний — на нём и
кончается `cold_ramp`. Переписка со своими на днях 9-10 идёт объёмом 45 и 60,
ради которого рампа и написана; применение потолка к обеим рампам молча
съедало треть внутреннего прогрева.

**Пауза сокета считается часами, а не сменой даты.** Номер, заведённый в 23:50,
иначе выходил бы из неё через десять минут — при том, что сама привязка сокета
и есть событие, ради отсрочки которого пауза существует.

Дни фаз считаются без пересечений: `socket_delay` — день 1, `passive` — дни
2–4 (`1 + passive_days`), `internal` — дни 5–10, и длина `internal_ramp` ровно
им и равна, `cold` — с 11-го. Пересечение дня 4 в двух фазах, как было записано
в исходном дизайне, дало бы номеру исходящие на сутки раньше положенного.

Три вещи, в которых календарь строже интуиции:

1. **Первые дни — только входящие.** Новый номер принимает сообщения с уже
   активных и сам молчит. Исходящие начинаются с дня 5, по одному за тик и
   только контактам.
2. **Холодные касания — примерно с 11-го дня**, не с четвёртого. Полное доверие
   — через 25–30 дней.
3. **Пауза 24 часа — это «не подключать», а не «не отправлять».** Привязка
   сокета сама по себе событие, которое WhatsApp видит.

**Открытие треда — в части 2.** Записано здесь, потому что зовёт
`transport.check()` и `pool.assign()` этой части, но сделать его раньше нельзя:
`threads.status` появляется вместе с очередью.

Тред по-прежнему открывает пайплайн `write` системы 2, но теперь при открытии
он дополнительно зовёт `transport.check()` и
`pool.assign()`: номер без WhatsApp сразу получает тред в состоянии
`unreachable` и больше не проверяется, остальные — `our_number` и `queued`.
Проверка платная только по времени, но делается ровно один раз на лида.

**Выбор номера.** `our_number` присваивается один раз при первом касании и
дальше не меняется: для лида сообщение с другого номера — новый чат без
истории. Выбирается наименее загруженный сегодня `active`; все выбрали лимит →
перенос на завтра, а не отправка через `warming`.

**Монитор здоровья** — раз в час, скользящее окно 7 дней:

| Сигнал | Порог | Действие |
|---|---|---|
| `loggedOut` от Node | — | `banned` немедленно, повторно не диагностируется |
| Всплеск реконнектов и запросов повторной аутентификации | `health.reconnects_per_day_alert` | `quarantined` **до** бана |
| delivered / sent | < 80% при 20+ отправках | `quarantined` — **часть 2** |
| replies / sent | < 5% при 20+ отправках | `quarantined` + Telegram — **часть 2** |

Две последние строки включаются в части 2: пока боевых отправок нет, delivered
и reply rate считать не по чему, а карантин по выборке из нуля остановил бы
прогрев. Вход для них готов уже здесь — `outbox.delivered_at`/`read_at`.

Строка про реконнекты — единственная метрика, срабатывающая заранее: delivered
и reply rate констатируют задним числом. Отключение связанных устройств и
частые запросы повторной авторизации — задокументированный ранний признак
приближающейся блокировки, а не бытовой сбой сети. Туда же попадают временные
ограничения (задержка отправки, запрет создавать группы): они приходят как
ошибки на `/send` и должны учитываться как метка здоровья номера, а не как
случайный сбой.

Для этого outbox и ведёт `delivered_at`/`read_at`: без них мониторить нечего —
«отправлено» само по себе не значит ничего.

**Бан → треды — в части 2**, по той же причине: двигать `threads.status`
нечем, пока колонки нет. Монитор этой части доводит номер до `banned` и шлёт
уведомление; треды разбирает часть 2.

Холодные без ответа переезжают на новый номер и возвращаются в
`queued`: лид, скорее всего, сообщения и не читал. Треды с ответами — в
`escalated`: продолжение с чужого номера выглядит как «кто это?».

**Кто отправляет прогревочные.** Календарь сам ничего не шлёт — его крутит
`warmup.tick`: одна отправка за тик (`tick_minutes` плюс джиттер), текстом из
`[warmup] phrases`. Одна за тик, а не пачка: шесть сообщений подряд отличаются
от живого общения ровно тем, из-за чего номера и банят. Неудачная отправка
(`sent: false`) лимит не тратит.

**Роли получателя и отправителя разведены — это не одно и то же.** Принять
может любой номер с поднятым сокетом, включая новичка в пассивной фазе:
входящие ему сейчас и нужны. Отправить может тот, кому календарь сегодня
разрешил исходящие (фазы `internal` и `cold`), то есть в том числе боевой
номер — иначе пассивной фазы не случается вовсе, ведь у самого новичка лимит
ноль. Приоритет тика — у пассивной фазы: она короткая, и пропущенные в ней
сутки не наверстываются. Такой номер принимает не чаще
`passive_interval_hours` и обычным путём получателем не выбирается — иначе
десятиминутный тик засыпал бы его полутора сотнями сообщений в сутки.

Номер в статусе `new` тик переводит в `warming`, как только прошли сутки
паузы: застрявший `new` выпал бы из списка тех, кому можно писать.
`warming -> active` делает человек — это решение о доверии, а не о календаре.

Прогревочная отправка кладёт строку в `outbox` с пустым `message_id` и
заполненным `recipient`: для Node внутренняя переписка неотличима от боевой,
дневной лимит она тратит наравне, а `recipient` нужен пассивной фазе — ей
важно не «сколько отправлено», а «как давно этот номер что-то получал».

**Номер приводится к канонической форме на границе** (`+7XXXXXXXXXX`). Одна SIM,
заведённая как `+7700…` и как `7700…`, стала бы двумя строками пула, двумя
сессиями Baileys и двумя дневными лимитами; строка с `../` увела бы каталог
сессии за пределы `sessions/` — и из-под `.gitignore` заодно.

**Реконнекты — суточные, переподключение — с backoff.** Счётчик Node сбрасывается
на смене даты: порог `reconnects_per_day_alert` сравнивается с числом «за
сутки», и накопительный счётчик за месяц аптайма отправил бы в карантин весь
пул. Переподключение идёт экспоненциальным backoff'ом до пяти минут и
двенадцати попыток: плоские пять секунд дают ~17 тысяч подключений в сутки с
одного адреса по номеру, которому не ввели pairing code, — это само по себе
поведение, за которое банят.

**Регистрация номера — ручная операция.** Кнопка в UI → Node отдаёт pairing code
→ код вводится на телефоне → сессия в `sessions/<number>/`. SIM физическая,
автоматизировать нечего. На самой SIM нужно сохранить в контакты остальные наши
номера: прогрев требует общения именно с контактами, а в multi-device контакты
подтягиваются с телефона.

**Проблема курицы и яйца при первом запуске.** Пассивный прогрев требует
входящих от разных контактов, а на старте активных номеров ноль. Первый номер
греется руками — личные телефоны, коллеги; дальше пул греет сам себя.

**`sessions/` попадает в тот же бэкап, что `state.db`.** Потерянная сессия — это
номер, который надо заново подключать телефоном, и в худшем случае разлогин на
живом номере.

## 4. Наблюдаемость

**Telegram (`sender/notify.py`) — только события, требующие человека:**
карантин или бан номера, всплеск реконнектов. Одно сообщение на событие.
Уведомление на каждый тик превращается в шум, который перестают читать за
неделю, — а вместе с ним перестают читать и аварии номеров. Тот же модуль
дальше зовут части 2 и 3 (застрявшая строка, три неудачных попытки,
эскалация), поэтому он появляется здесь, а не там, где понадобится первым.

**`/api/stats`** получает первые счётчики sender: номера по статусам.
Очередь, эскалации и heartbeat воркера добавят части 2 и 3.

Страница «Отправка» на этом этапе показывает ровно пул: номер, день прогрева
от `started_at`, статус, здоровье, кнопку регистрации нового номера. Очередь и
эскалации добавятся частями 2 и 3.

## 5. Тесты

Всё, кроме Node, тестируется без сети: монитор здоровья и календарь прогрева
получают `transport` и «сейчас» аргументами.

- **Календарь:** день от `started_at` → фаза и лимит, на всех границах
  (1, 4, 5, 10, 11, 40-й день); номер в `warming` не получает боевых отправок
  ни при каких условиях.
- **Прогревочный тик:** в socket_delay и passive не шлёт ничего; в internal
  пишет другому нашему номеру; успешная отправка тратит дневной лимит, а
  `sent: false` — нет; единственный номер в пуле не пишет никому (курица и
  яйцо честно возвращает «некому»); `new` с прошедшими сутками становится
  `warming` сам.
- **Здоровье:** `loggedOut` → `banned`; delivered rate ниже порога при
  достаточной выборке → `quarantined`; та же метрика на выборке меньше
  `min_sample` не двигает ничего.
- **Бан:** холодные треды переезжают на новый номер, треды с ответами
  эскалируются.
- **Миграции:** второй вызов `ensure_column` на той же базе не падает.
- **Граф импортов:** `transport.py` — единственная точка выхода в сеть, по
  образцу теста, который сторожит отсутствие сети в `rebuild.py`.

Живой WhatsApp — отдельный ручной смоук-чеклист, не pytest.

## 6. Порядок выката

**Этап 0 — начинается до единой строки кода.** Купить три SIM,
зарегистрировать, заполнить профили, сохранить в контакты телефоны команды.

**Этап 1.** Node-сервис и `transport.py`. Проверка одна: отправить сообщение
самому себе.

**Этап 2.** Пул, календарь прогрева, монитор здоровья. Работает только автомат
прогрева — пассивный, затем внутренний. Боевых касаний ноль: их некому ставить
в очередь, пока не сделана часть 2.

Стоп-правило этапа: любой бан на прогреве — остановка и разбор, а не замена
номера.
