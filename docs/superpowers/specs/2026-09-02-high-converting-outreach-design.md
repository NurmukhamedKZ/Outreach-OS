# Высококонвертирующая холодная переписка: повод, этап, оффер, воронка

Статус: спека, реализация не начата.

**Проблема.** Системы 1 и 2 умеют находить компании и писать им сообщения, но
ни одна цифра не говорит, работает ли это. Конкретно:

1. **Повод слабый.** `seed.signals` отдаёт агенту все сигналы подряд, включая
   инфраструктурные (`crm_widget` весом 3.0, `ads_platform`, `inbound_widget`).
   «У вас на сайте виджет CRM» — не боль и не повод написать сегодня.
   `half_life_days = 90` означает, что в промпт легально попадает наблюдение
   трёхмесячной давности, а `why_now` — весь наш оффер.
2. **Адресат безымянный.** Пишем на общий номер компании из 2GIS. При этом
   `decision_maker_hint` уже собирается моделью и лежит в
   `dossiers_all.decision_maker`, но `leads_source.CANDIDATES` его не
   выбирает — до промпта письма имя не доезжает.
3. **Диалог без этапов.** `seller.py` на каждое входящее видит только историю и
   волен сразу закрывать на созвон. «Нельзя перескакивать этапы» нельзя
   записать в промпт, пока этап не хранится.
4. **Оффер не тестируется.** `[offer].text` — один абзац; какая формулировка
   даёт встречи, узнать не из чего.
5. **Воронки нет.** `/api/stats` отдаёт четыре счётчика (threads, drafts, sent,
   replies). Reply rate, конверсия во встречу и разрезы по поводу, офферу и
   рубрике не считаются ничем.

**Решения, принятые на брейншторме 2 сентября 2026:**

| Вопрос | Решение |
|---|---|
| Модель оплаты | pay-per-meeting: платят за состоявшуюся встречу |
| ICP v1 | вся ветка B2B-услуг, без сужения (сузим по цифрам из воронки) |
| Единица оплаты | согласие на созвон **и** состоявшийся созвон |
| Адресат | искать имя ЛПР; нет имени — просьба передать |
| Доказательство в первом сообщении | наблюдение о нём самом (не «3 лида бесплатно») |
| Этапы диалога | `threads.stage`, перескок запрещён кодом |
| Сырьё | выжать текущие три источника, новых интеграций нет |
| Тест оффера | варианты в конфиге + запись версии на сообщении |

**Не входит.** Госзакупки и вакансии с сайта как источники, «3 бесплатных
лида» как доказательство, сужение ICP, cost-per-meeting в деньгах (стоимость
номеров и LLM живёт вне базы).

**Готово, когда:** оператор открывает `/analytics` и видит воронку
отправлено → ответ → диалог → согласие → встреча с разрезами по офферу, поводу
и рубрике, а первое сообщение в `/cold` обращается по имени и цитирует
наблюдение свежее 60 дней.

## 1. Сырьё: сигнал становится поводом только с цитатой и датой

### 1.1 Поводы отделены от сигналов — в конфиге системы 2

Система 1 решает, что считать сигналом; система 2 решает, о чём писать. Это
разные вопросы, поэтому список поводов живёт в `backend/writer/config.toml`, а
не в `collector/config.toml` — и это не вторая копия знания, а другой домен:

```toml
[signals]
# Типы, которые годятся как повод для письма. Остальные сигналы продолжают
# влиять на intent_score (компания с CRM и отделом продаж — лучший лид), но в
# промпт не идут: «у вас на сайте виджет CRM» — не боль.
pitchable = [
  "reviews_unanswered_complaint",
  "reviews_missed_lead",
  "ig_unanswered_question",
  "site_hiring_sales",
  "ig_reach_declining",
  "ig_dormant",
  "site_no_pricing",
]
# Наблюдение старше этого в промпт не попадает вовсе. Не затухание, а отсечка:
# «увидел, что вы ищете продажника» про вакансию трёхмесячной давности убивает
# доверие одним предложением.
max_age_days = 60
```

`intent_score` при этом не меняется: `crm_widget` остаётся в
`collector/config.toml [scoring.intent]` и продолжает поднимать лид в очереди.
Меняется только то, что видит агент.

### 1.2 `leads_source.signals_of` фильтрует

Сейчас возвращает все сигналы компании. Становится:

```python
def signals_of(db, company_id, pitchable, max_age_days, today):
    """Поводы для письма: только pitchable-типы, только с цитатой, только свежие."""
```

- `type NOT IN pitchable` → отбрасывается;
- `quote` пустая → отбрасывается (нечего процитировать — это догадка, а не
  наблюдение);
- `observed_at` старше `max_age_days` → отбрасывается.

`SELECT` дополняется `observed_at` (колонка в `signals_all` уже есть).

Компания, у которой после фильтра не осталось ни одного повода, из
`candidates()` **не исчезает** — она остаётся в списке, но агент на ней вернёт
`stop=true`. Молчаливое выпадение лида из выдачи было бы вторым,
недокументированным фильтром рядом с F19/F21.

### 1.3 Затухание — 30 дней

`collector/config.toml`: `half_life_days = 90 → 30`. Это влияет на порядок
лидов в очереди, а не на текст письма (за текст отвечает отсечка 1.1).
Пересборка бесплатна (`state.llm_answers`), числа в `test_parsers` не
затрагиваются — они про разбор, а не про скоринг.

### 1.4 ЛПР доезжает до промпта

Три правки, ни одного нового вызова модели:

1. `collector/schemas/dossier.py` — у `decision_maker_hint` появляется
   `description`: «имя и роль человека, принимающего решение, если они названы
   прямо в данных (страница «Команда», био инстаграма, подпись под ответом на
   отзыв); ничего не выдумывать, нет — null». Сейчас поле без описания, и
   модель заполняет его как попало.
2. `writer/db/leads_source.py` — `CANDIDATES` добавляет `d.decision_maker`,
   `seed["dossier"]["decision_maker"]` его несёт.
3. `writer/services/agent.py::prompt()` — строка «Кто решает: …», когда поле
   непустое.

Правка описания меняет промпт `dossier` и обесценивает кэш `kind="dossier"` —
это осознанная плата: досье пересчитывается один раз по всей базе. Кэш
`reviews`/`site`/`instagram` (самая дорогая часть) не затрагивается.

## 2. Этап диалога — состояние, а не пожелание

### 2.1 Колонка

`writer/db/thread_store.py` — владелец таблицы `threads`, поэтому колонки
доливает он (`sender/db/migrate.py` доливает свою `status` и остаётся при ней):

```sql
stage TEXT NOT NULL DEFAULT 'contact'  -- contact | probing | offer | closing
```

`_ensure_prompt_columns` переименовывается в `_ensure_columns` — имя обязано
описывать то, что функция делает.

### 2.2 Переход зажимает код, а не промпт

`Draft` получает поле `next_stage`. Решение агента проходит через:

```python
STAGES = ("contact", "probing", "offer", "closing")

def stage_after(current: str, proposed: str) -> str:
    """Только текущий этап или следующий. Перескок — то, ради чего это в коде:
    инструкция «не перескакивай» нарушается ровно на вопросе «сколько стоит»,
    где модель прыгает в closing и называет цену."""
```

Неизвестное значение `proposed` → остаётся `current`. Это вход для
предохранителя, а не авария — тот же принцип, что `seller.UNKNOWN`.

### 2.3 Ограничения по этапу

`agent.py` получает `STAGE_RULES: dict[str, str]`, вставляемый в системный
промпт:

| stage | что можно | что запрещено |
|---|---|---|
| `contact` | наблюдение + один вопрос | продавать, называть услугу, звать на созвон |
| `probing` | вопрос про их процесс поиска клиентов | оффер, цены |
| `offer` | вариант оффера, снятие одного возражения | назначать время |
| `closing` | предложить окно для созвона | новые аргументы |

`seller.py` берёт те же правила: ответ в диалоге и холодное касание — одна
калибровка, два промпта на одну ситуацию дали бы две.

## 3. Промпт по RIC+ECO и оффер вариантами

### 3.1 Структура системного промпта

`agent.SYSTEM` пересобирается блоками, каждый с заголовком:

- **Роль** — кто пишет (общая, не меняется);
- **Инструкции** — правила тона и запрет выдумывать (то, что уже есть);
- **Контекст** — вариант оффера, досье, поводы;
- **Ограничения** — `STAGE_RULES[stage]`;
- **Формат** — 2–3 предложения, один вопрос, на «вы».

Примеров писем в промпт **не добавляем**: на русском WhatsApp модель начинает
копировать их дословно, а гайд прямо предупреждает, что примеры могут снижать
конверсию.

Структура первого сообщения фиксируется в инструкции этапа `contact`:
обращение по имени → наблюдение с цитатой → чего оно им стоит → микро-вопрос.
Нет имени — «передайте, пожалуйста, тому, кто отвечает за продажи».

### 3.2 `angle` перестаёт быть свободной строкой

Разрез `by_angle` в аналитике осмыслен только если `angle` — перечислимое
значение. Сейчас в `Draft` это `str` с описанием, то есть модель вправе вернуть
фразу, и таблица разреза наполнится вариациями одного и того же повода.
`schemas/outreach.py` получает валидатор: `angle` обязан быть одним из
`pitchable`-типов или `"answer"`. Невалидное значение — повод для повторного
вызова `with_structured_output`, тем же механизмом, что запрет пустых follow-up.

### 3.3 Варианты оффера

`writer/config.toml`:

```toml
[[offer.variant]]
id   = "free_first_meetings"
text = """
Находим компании, которым ваша услуга нужна прямо сейчас, пишем каждой лично и
доводим до встречи. Первые две встречи — за наш счёт: платите только за те, что
состоялись после них. Списков контактов не продаём, работаем по Казахстану.
"""

[[offer.variant]]
id   = "pay_per_meeting"
text = """
Находим компании, которым ваша услуга нужна прямо сейчас, пишем каждой лично и
доводим до встречи. Оплата только за состоявшуюся встречу — не за письма, не за
базу, не помесячно. Работаем по Казахстану.
"""
```

Варианты различаются ровно одной переменной — способом снять риск, — потому что
иначе результат теста не читается: два текста, отличающихся всем, не говорят
ничего о том, что именно сработало.

Вариант назначается треду при открытии, детерминированно и стабильно между
процессами:

```python
def variant_of(thread_id: str, variants: list[dict]) -> dict:
    digest = hashlib.sha1(thread_id.encode()).hexdigest()
    return variants[int(digest, 16) % len(variants)]
```

`random` нельзя — тред не должен менять когорту; встроенный `hash()` тоже
нельзя — он рандомизирован `PYTHONHASHSEED` и после перезапуска процесса
раскидал бы те же треды иначе, тихо смешав когорты. Выбранный вариант пишется в
`messages.offer_variant` рядом с `prompt` — по той же причине, по которой промпт
хранится, а не реконструируется: сегодняшний конфиг уже другой.

Старый ключ `[offer].text` остаётся как значение по умолчанию для тредов,
открытых до этой правки, — у них `offer_variant` пуст, и аналитика показывает
их отдельной строкой «до A/B», а не подмешивает к варианту.

## 4. Аналитика

### 4.1 Данные

`writer/db/thread_store.py` доливает:

```sql
outcome    TEXT,   -- meeting_agreed | meeting_held | refused | lost
meeting_at TEXT    -- когда созвон состоялся
```

`messages` доливает `offer_variant TEXT`. `angle` уже есть.

`meeting_held` ставит **оператор** кнопкой в карточке треда
(`writer/routes/threads.py`), не автомат: это единица оплаты, и вероятностный
классификатор не имеет права её выписывать. `meeting_agreed` предлагает агент
(`classify(status="interested")` уже это распознаёт), подтверждает оператор.

### 4.2 Модуль

`backend/analytics.py` — модуль верхнего уровня рядом с `activity.py`, по тому
же принципу: данные лежат в трёх системах (`threads`/`messages` — система 2,
`outbox` — система 3, рубрика и город — derived системы 1), и ни одна из них не
имеет права знать две других. Путь к базе приходит швом, как у `activity.use()`.

Роутер `collector/routes/analytics.py`, `GET /api/analytics?days=30`.

Ответ:

```json
{
  "funnel": [{"step": "sent", "count": 412}, {"step": "delivered", "count": 380},
             {"step": "replied", "count": 31}, {"step": "dialog", "count": 18},
             {"step": "meeting_agreed", "count": 7}, {"step": "meeting_held", "count": 4}],
  "by_offer":  [{"key": "free_first_meetings", "sent": 210, "replied": 19, "meetings": 3}],
  "by_angle":  [{"key": "reviews_unanswered_complaint", "sent": 96, "replied": 11, "meetings": 2}],
  "by_segment":[{"key": "Бухгалтерские услуги · almaty", "sent": 54, "replied": 4, "meetings": 1}],
  "edited_share": 0.62,
  "diagnosis": "reply_rate_low"
}
```

`dialog` — тред, доросший до `stage >= probing`. `diagnosis` считает бэкенд по
правилу из гайда, а не фронт:

- `reply_rate < 2%` → `reply_rate_low` («чинить текст и оффер»);
- ответы есть, `meeting_held == 0` при `replied >= 10` → `icp_mismatch`
  («чинить ICP»);
- иначе `ok`.

Порог `replied >= 10` обязателен: на трёх ответах диагноз — это шум, а фронт,
показавший «чините ICP» после первого молчащего лида, обучит оператора не
верить странице.

### 4.3 Страница

`frontend/app/analytics/page.tsx`, пункт «Аналитика» в сайдбаре. Содержимое —
целиком с бэкенда, как на `/activity`:

1. воронка шестью строками с абсолютом и % перехода;
2. три таблицы разрезов (оффер, повод, сегмент) — по трём переменным, которые
   тестируются раздельно;
3. диагноз одной строкой сверху;
4. доля правок оператора (`sent_text != draft_text`) — накопленная разметка
   качества промпта.

Свои стримы страница не открывает: `refreshTick` из `LiveProvider` достаточно.

## 5. Порядок работ и тесты

1. **Сырьё** (§1) — `writer/tests/test_leads.py`: сигнал без цитаты, сигнал
   старше `max_age_days` и не-`pitchable` тип не попадают в `seed`; компания без
   поводов остаётся в `candidates()`.
2. **Этап** (§2) — `writer/tests/test_threads.py`: `stage_after` не пропускает
   перескок и неизвестное значение; новый тред открывается в `contact`.
3. **Промпт и оффер** (§3) — `writer/tests/test_prompt.py`: в промпте этапа
   `contact` присутствуют правила этапа и отсутствуют правила `closing`; вариант
   оффера, записанный в сообщение, совпадает с тем, что ушёл в модель.
4. **Аналитика** (§4) — `backend/tests/test_analytics.py` на синтетической базе:
   воронка не растёт вверх по шагам, `diagnosis` молчит на выборке меньше
   порога.

Аналитика последняя не по важности, а по зависимостям: до `stage` и `outcome`
ей нечего показывать.
