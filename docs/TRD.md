## 1. Стек

| Слой | Выбор | Почему |
|---|---|---|
| Язык | Python 3.13, `uv` | уже в проекте |

## 2. Проверенные ограничения источников

Всё проверено живыми запросами 6–7 августа 2026. Это не предположения, и именно эти
факты определяют конструкцию.

### 2.1 Главный класс проблем: молчаливая подмена

**Источники подменяют содержимое, сохраняя `HTTP 200`.** Обнаружено дважды, оба раза —
уже после того, как код «работал»:

| Источник | Что происходит | Признак подмены |
|---|---|---|
| 2GIS | Начиная с 6-й страницы возвращается содержимое **первой**, при этом `total` и `pages` продолжают обещать больше (рубрика `653`: заявлено 670 и 56, доступно 60) | поле `currentPage` не равно запрошенному |
| hh.kz | Несуществующий slug редиректит на `/vacancies` — общий список всех вакансий города; сбор набирает 50 посторонних записей | конечный URL после редиректов не содержит slug |

**Требование к каждому коннектору: проверять, что получено именно запрошенное, и
останавливаться, если нет.** Статус ответа для этого бесполезен. `fetch.get` запоминает
конечный адрес после редиректов, `final_url()` его отдаёт.

Это же требование распространяется на любой будущий источник.

### 2.2 2GIS

- Редирект на `/museum` снимается cookie `dg5_museum_accept=true`; дальше обычный HTTP
- Весь стейт в HTML: `var initialState = JSON.parse('...')`, разбор в две строки
- `catalog.api.2gis.com` не нужен: требует ключ, ключи из фронта дают `apiKeyIsBlocked`
- Ни браузера, ни аккаунта, ни прокси. 15 запросов подряд без пауз — все `200`
- Потолок: **60 организаций на рубрику на город**; охват набирается числом рубрик
- Ветка «B2B-услуги» — 127 листовых рубрик, потолок ≈ 15 240 организаций по двум городам
- Карточка филиала отдаёт телефон, сайт, email, Instagram, WhatsApp

### 2.3 hh.kz

- `robots.txt` запрещает **строку запроса** (`Disallow: *?*`), а не поиск; SEO-урлы
  `/vacancies/{slug}` идут без параметров
- Обычный клиент получает `403`; `Fetcher.get(impersonate='chrome')` проходит — вопрос
  TLS-отпечатка, а не интерактивного челленджа
- Вакансия отдаёт `JSON-LD` типа `JobPosting`: `title`, `hiringOrganization.name`,
  `datePosted`, `description`. Своего парсера HTML не требуется
- **Slug — фиксированный набор SEO-страниц, а не произвольный запрос.** Автоматически
  получить slug из фразы можно только через `?text=`, что запрещено `robots.txt`
- 50 вакансий на страницу без нарушения robots

### 2.4 Scrapling 0.4.12

- `retries` (3) и `retry_delay` (1) встроены в `Fetcher.get` — свой цикл не нужен
- `stealthy_headers=True` по умолчанию; вместе с `impersonate` это и проводит через hh
- **`Response.text` пустой** — это семантика `Selector`. Сырая разметка в `.html_content`
- `.re()` / `.re_first()` работают по извлечённому тексту, не по разметке

## 3. Реализованные компоненты

```
fetch.py           HTTP с кэшем, дедуплицирующая запись JSONL, HttpError со статусом
gis_rubrics.py     справочник рубрик 2GIS с иерархией
gis_list.py        организации рубрики: org_id, branch_count, рубрики, адрес, отзывы
gis_firm.py        контакты: телефоны, сайт, email, Instagram, WhatsApp
hh_vacancies.py    вакансии: заголовок, работодатель, дата, полный текст
serp.py            выдача Google через Serper.dev
```

**Правило слоя:** коннекторы не знают ни друг о друге, ни о базе. Один вход из
командной строки, один файл на выходе, никаких вызовов модели.

**Кэш** (`cache/<sha1(url)>.html` + `.url`) — не оптимизация, а условие отладки: разбор
правится по сохранённому ответу без похода в сеть. Он же хранилище фикстур для проверок.

**Общий слой намеренно тонкий.** Разбор `initialState` живёт в каждом 2GIS-скрипте
отдельно: у списка, карточки и рубрикатора разные ветки стейта, общий только regex.
Вынести его в `fetch.py` — начало абстракции, которая при пяти скриптах не окупается.

## 4. Модель данных

Полная схема — `ARCHITECTURE.md` §9. Ключевые решения и их причины:

| Решение | Причина |
|---|---|
| `raw` неизменяем, `core` пересобирается из него | Нормализация меняется еженедельно; перекачать нельзя — вакансия закрывается, страница удаляется |
| `signals` — события с датой, не флаги | Вакансия вчерашняя и полугодовой давности — разные лиды. `intent_score` считается на лету с затуханием |
| `channels.confidence` — число, не булево | Решение «слать или не слать» принимает Система №3 исходя из здоровья своих доменов |
| Все каналы равноправны | Telegram бывает найден как `@username` без телефона; порождать один канал из другого неверно |
| `segment_id` — первоклассная сущность | Разброс конверсии между сегментами до двух раз. Технически это id рубрики 2GIS |
| `core.companies` глобальная | Два клиента таргетят одну компанию — обогащаем один раз |

**Identity resolution** — по правилам, без модели: домен, телефон в E.164, БИН,
Instagram — точно; `similarity(name_norm) > 0.8` в пределах города — нечётко, с ручной
проверкой.

## 5. Пайплайн

```
S1 SEED      2GIS по рубрикам + вакансии hh + SERP-добор
S2 RESOLVE   склейка дублей
S3 SCAN      сайт целиком (5–15 страниц), regex по разметке
S4 CLASSIFY  один вызов Haiku на компанию, structured output
S5 QUALIFY   fit_score по правилам, отсев не-ICP
S6 CONTACTS  корпоративные адреса; ЛПР опционально
S7 VERIFY+RANK  проверка каналов, intent_score, агент → why_now
```

**Границы модели:** ИИ извлекает и классифицирует, правила решают. Ровно два обращения
к модели на компанию — один вызов Haiku на всех и агент на топ-300. Скоринг только
правилами: клиенту придётся объяснять выбор лида, а чёрный ящик объяснить нельзя.

**Открытый вопрос по порядку этапов.** Сейчас платные S3 и S4 стоят перед отсевом S5,
то есть классифицируются компании, которые потом отсеются. Предложение — разрезать
QUALIFY на дешёвый гейт после RESOLVE и полный `fit_score` после CLASSIFY, а верификацию
каналов поднять перед ранжированием. Не принято, зафиксировано в Приложении Б.

## 6. Проверки

У каждого модуля `demo()` с ассертами, запуск `uv run <модуль>.py demo`. Ни фреймворков,
ни фикстур-каталога — фикстурой служит кэш.

Проверки закрывают ровно то, что ломалось на практике:

| Модуль | Что утверждает |
|---|---|
| `fetch` | дедуп работает, повторный прогон не плодит строк |
| `gis_list` | 12 организаций на странице, кириллица цела, **потолок пагинации ловится** |
| `gis_firm` | 3 телефона, email, сайт развёрнут из редиректа `link.2gis.ru` |
| `gis_rubrics` | `653` = «Бухгалтерские услуги», родитель `110613`, обход ограничен веткой |
| `hh_vacancies` | JobPosting разобран, **выдуманный slug приводит к отказу** |
| `serp` | разбор выдачи, включая пустую и без сниппета |

Все шесть проходят.

## 8. Открытые технические вопросы

| # | Вопрос | Состояние |
|---|---|---|
| 1 | Склейка работодателя hh с компанией 2GIS | По имени нечётко. Точный путь — `/employer/{id}` → сайт → домен, ценой лишнего GET на вакансию |
| 2 | Автоматическое получение slug hh из фразы | Единственный механизм — `?text=`, запрещён robots. Альтернатива: список slug'ов в конфиге, собранный вручную |
| 3 | Обход потолка 60 организаций | В стейте есть `spatial.districts` (8 районов Алматы), URL-форма фильтра не выяснена |
| 4 | Работа email-верификаторов на `.kz` | Бенчмарков нет ни у одного вендора, нужен тест на реальной базе |
| 5 | Прокси для `size_est` | Фильтр 10–200 сотрудников не обеспечен ни одним источником. Кандидаты: `org.branch_count`, число активных вакансий |
| 6 | Порядок этапов пайплайна | См. §5 |
| 7 | Локализация хранения ПД в РК | Юридически спорно, нужна консультация до продажи услуги внешним клиентам |
