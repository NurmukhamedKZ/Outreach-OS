## Правила исполнения

1. **Каждая фаза завершается работающей командой.** Не «написан модуль», а «команда
   запускается и выдаёт проверяемый результат».
2. **Каждая фаза оставляет ассерт в `check.py`.** Отдельной фазы «написать тесты» нет.
   Ассерт — минимальный: тот, который падает, если логика фазы сломается.
3. **Не переходить к следующей фазе, пока приёмка текущей не зелёная.**
4. Разведка источников уже сделана и проверена на живых данных. **Разбор не
   переписывается** — переносится из работающих скриптов.

# Ф1. Слой сырья ✅

**Выполнено 12 августа 2026.** Объём по факту: 5 минут.

`cache/` → `raw/`, 111 страниц в gzip, сайдкар `{url, final_url, status, fetched_at}`
у каждой. **69 МБ → 15 МБ, сжатие 4,6×.** Все 319 строк производных JSONL целы в
`raw_jsonl_legacy/`, удалятся в Ф3. Резервная копия удалена после побайтовой сверки
всех 111 страниц: расхождений 0.

Три решения агента сверх задания, все верные:

- **Сайдкар пишется последним, страница считается собранной только при наличии
  обоих файлов.** Иначе оборванная запись оставила бы HTML без `final_url`, и
  обнаружение подмены ослепло бы молча — ровно тем способом, против которого
  построен проект.
- `jsonl()` и `read()` направлены в `raw_jsonl_legacy/`: производные файлы не
  смешиваются с невосстановимым сырьём, и дозапись коллекторов не прерывается.
- Ответы Serper названы `<sha>.serp.json`, чтобы не путаться с сайдкарами страниц.

**Известное приближение:** у 111 мигрированных страниц поле `url` равно `final_url` —
имя файла это `sha1(url)`, обратно не восстанавливается, а старый сайдкар хранил
только конечный адрес. Того же порядка, что `fetched_at` из mtime. У всех новых
страниц оба поля честные; обнаружение подмены не затронуто, оно смотрит на
`final_url`.

**Правило слоя, действующее дальше:** `raw/` — невосстановимое сырьё, `raw_jsonl_legacy/`
— производное. HTML не заменяется извлечённым `initialState` ни при каких условиях:
разбор будет меняться, сырьё остаётся сырьём.

```
# ponytail: gzip на файлах. zstd или один pack-файл — если 1.5 ГБ станет неудобно.
```

# Ф2. Конфиг ✅

**Выполнено 12 августа 2026.** Объём по факту: 6 минут, ручной работы ноль.

`config.toml`: 36 листовых рубрик, 20 slug'ов hh, веса скоринга, чёрный список.
31 сетевой запрос из потолка 40.

### Открытый вопрос №2 TRD закрыт

TRD утверждал, что автоматически получить slug нельзя: «единственный механизм —
`?text=`, запрещён robots». Это оказалось неверно. `?text=` нужен, чтобы **искать**
slug по произвольной фразе, но не чтобы **проверять** догадку:

```
транслитерация фразы → кандидат → GET /vacancies/{кандидат} → final_url содержит его?
```

Механизм, написанный для защиты от молчаливой подмены, оказался готовым валидатором.
Из 32 кандидатов выжили 20. Час ручной работы превратился в три минуты машинной, и
robots.txt не нарушен: строка запроса не используется.

**Поправка к этому документу:** транслитерация `х` → `kh`, а не `h`. Пример
`buhgalter`, приведённый ниже в исходном плане Ф2, — несуществующий slug, уводит на
`/vacancies`. Работает `bukhgalter`. При этом `ц` → `c`, а не `ts`. Отвалившиеся 12
кандидатов записаны в комментарии `config.toml`: у hh таких SEO-страниц нет, повторно
пробовать незачем.

### Незакрытое: две отрасли ICP недостижимы через 2GIS

BRD §4 называет ICP «бухгалтерский и **юридический** аутсорс, HR и рекрутинг,
IT-аутсорс, консалтинг, **клининг**». В собранном справочнике на 135 рубрик:

- **юридических услуг нет** — ветка 110565 из TRD в выгрузке отсутствует; право
  представлено суррогатом 638 «Регистрация и ликвидация предприятий»
- **клининга нет** — 110616 оказалась «Для сферы услуг» (продажа оборудования), а
  719 это «Клининговое оборудование», то есть продавцы техники. Клининговые компании
  живут в потребительской ветке справочника

Частично закрывается со стороны hh: slug'и `yurist` и `yuriskonsult` собраны, и
работодателей оттуда видно без рубрики 2GIS. **Решение нужно на уровне BRD:** либо
ICP сужается до достижимого, либо в Ф4 добавляется вторая ветка рубрикатора.
Приёмку v1 не блокирует — 36 рубрик × 2 города × 60 дают потолок 4 320 организаций
при целевых 1 000–1 500.

### Про `exclude`

`include` — белый список листьев, `exclude = [110611]` — id ветки, он ни с одним
листом не совпадёт. Реальную защиту от конкурентов даёт сам белый список. `exclude`
остаётся не декорацией, а страховкой для склейки работодателей hh, где рубрики 2GIS
нет и белый список не работает.

### Правило отсечения нелистовых рубрик

Лист — это id, который ни разу не встречается как `parent_id`. Принадлежность к
`exclude` проверяется подъёмом по `parent_id` до корня, а не только по прямому
родителю: иначе конкурент через два уровня иерархии проходит фильтр.

Веса: высокий = 3.0, средний = 1.5, низкий = 0.5 (перевод таблицы ARCHITECTURE.md
§10 в числа). `stale_vacancy_days = 60` вынесен константой конфига, чтобы в Ф6 не
появилось магическое число.

### Найден третий класс молчаливой подмены: капча с кодом 200

hh отдаёт `HTTP 200` и страницу «Подтвердите, что вы не робот» вместо вакансии.
В пилоте так пришли **19 страниц из 98**. Разбор на них молча не находит
`JobPosting`, и вакансия просто исчезает из базы.

Опаснее самой подмены то, что `raw/` — content-addressed: заглушка занимает имя
`sha1(url)` **навсегда**, и настоящую страницу по этому адресу уже никто не
запросит. Поэтому проверка стоит в `fetch.get` до записи на диск: капча
возбуждает `BotCheck` и в сырьё не попадает.

Причина — темп. 8 потоков без паузы это ~40 запросов в секунду; TRD §2.3 мерил
последовательный сбор и лимитов не увидел. `PAUSE_SECONDS = 1.0` на поток
держит 4–8 запросов в секунду: проверено доборным slug'ом, 48 страниц, ноль капчи.

**Долг:** 19 страниц капчи лежат в `raw/` и блокируют свои вакансии. Лечится
удалением заглушек, после чего они доберутся сами:

```bash
uv run python -c "import json,glob,os; [os.remove(f) or os.remove(f.replace('.json','.html.gz')) for f in glob.glob('raw/*.json') if not f.endswith('.serp.json') and 'captcha' in json.load(open(f))['final_url']]"
```

Не сделано намеренно: удаление из `raw/` — решение владельца, а не агента.

### Проверки подмены работают на свежем сырье — доказано

У четырёх рубрик шестая страница скачана заново, и в сайдкаре видно то, ради
чего он существует:

```
url       https://2gis.kz/almaty/rubric/1236/page/6      ← что запрошено
final_url https://2gis.kz/almaty/rubric/1236             ← куда привело
currentPage 1                                            ← что отдано
```

**`tiktok.com` объединил 16 несвязанных компаний, `jivo.chat` — 11.** Соцсети,

нечёткое сходство меряется с ближайшим — склейка по имени транзитивна (A≈B, B≈C).

Порог нечёткого сравнения поднят с 0.8 из ARCHITECTURE.md до **0.88**: на живых
данных «Альфа» и «Альфа-Строй» дают 0.85 и склеиваются, а это разные компании.

### Главное: intent-корпус и корпус компаний почти не пересекаются

**Из 321 работодателя hh к компаниям привязалось 3.** Это не дефект алгоритма —
измерено распределение лучших совпадений по всем работодателям, без фильтров:

| Лучшее сходство | Работодателей |
|---|---|
| ≥ 0.88 | 3 |
| 0.75–0.88 | 5 |
| 0.6–0.75 | 53 |
| **< 0.6** | **272** |

Средняя зона — сплошь ложные срабатывания: «хилти казахстан» → «звонобот

**Причина в том, как собирались вакансии.** Slug'и пилота — `menedzher_po_prodazham`,

источником сигналов становится сканирование сайтов (CRM, пиксели, формы) — оно
детерминированно, идёт regex'ом и не зависит от hh, который к тому же блокирует
сбор. Вакансия остаётся сильным, но редким бонусом.

Открытый вопрос №1 TRD (точная привязка работодателя через `/employer/{id}`)
остаётся открытым: он стоит лишнего запроса на вакансию, а hh уже отдаёт капчу.

Пять правил из ARCHITECTURE.md §9.3, по убыванию надёжности. Модель не участвует —
правила точнее и дешевле.

| Правило | Реализация | Надёжность |
|---|---|---|
| Домен | нормализация URL, `link.2gis.ru` разворачивается | точно |
| Телефон в E.164 | `phonenumbers` | почти точно |
| Instagram username | сопоставление ссылок | точно |
| БИН | если найден | точно |
| Похожее имя в пределах города | `difflib.SequenceMatcher` > 0.8 | нечётко → в `company_links` с `confidence` |

Кандидаты для нечёткого правила сужаются городом и первой буквой `name_norm` —
иначе 1 500² сравнений, а так их сотни.

Отдельно: работодатель hh склеивается с организацией 2GIS **только по имени** и
только нечётко. Точный путь — `/employer/{id}` → сайт → домен — стоит лишнего GET

### Спека умалчивала о зависимости: сигналы требуют сайтов

«Regex по сырому HTML» подразумевает HTML **сайтов компаний**, а в `raw/` лежали

**Только главная страница, а не сайт целиком.** ARCHITECTURE §8.1 предполагает обход
до 30 страниц. CRM-виджет, пиксель, форма заявки и кнопка WhatsApp живут на главной:
1 088 запросов вместо 15 000 ради того же набора сигналов.

```
# ponytail: только главная. Внутренние страницы — когда понадобится извлекать
#           людей и услуги, то есть вместе с Ф9 и вызовом модели.
```

**Откат на `http://` при битом сертификате.** У пятой части сайтов малого бизнеса в
КЗ сертификат выписан на другое имя или просрочен. Читается публичная страница,
ничего не отправляется — понижение протокола риска не создаёт, а без него терялся бы
каждый пятый сайт.

Итог сбора: 1 128 запросов, 11,6 минут, **92 сайта недоступны** (31 DNS, 28 HTTP,
23 сертификат, 4 таймаут, 4 соединение, 2 TLS). Обычная смертность сайтов малого
бизнеса, ошибки прогон не роняют.

### Ошибка, которая едва не стоила воспроизводимости

`enrich` **перечитывал `raw/` заново**, а сбор сайтов шёл параллельно — он видел
страницы, которых не было в списке, с которого началась сборка. Они отсутствовали в
`fetches`, и вставка сигнала падала на `NOT NULL observed_at`.

Симптом безобидный, причина нет: **сборка переставала быть функцией одного снимка
сырья.** Не упади она на ограничении схемы, получилась бы база, которую нельзя
воспроизвести. Список страниц теперь передаётся в `enrich` снаружи.

Само ограничение `NOT NULL` сработало как задумано: сигнал без даты не затухает, и
вакансия позапрошлого года весила бы как вчерашняя.

### Поправка к проверке сырья

Ассерт «страница длиннее килобайта» писался под 2GIS и hh, где короткая страница
означает обрыв. Сайт компании — чужая территория: 11 страниц оказались заглушками
припаркованных доменов и SPA на одном скрипте. Проверка сужена до источников.

### Вакансии сигналов почти не дали

Привязанных вакансий 4 (см. Ф5), сигналов из них — ноль: ни одна не про продажи.

1. **Сигналы из вакансий** — то, ради чего проект существует. Поиск по тексту:

# Ф7. `score.py` ✅

**Выполнено 14 августа 2026.** Оценены все 1 660 компаний, у 843 `intent_score > 0`.

Обе оси по правилам, модель не участвует. Каждая функция возвращает число **и
разбивку** — объяснимость (F17) обеспечивается ею, а не отдельной сущностью.
Проверка сверяет разбивку с числом: расхождение означало бы, что показанное
оператору обоснование не соответствует позиции лида в списке.

Опорная дата — **последний забор сырья, а не сегодня**. Иначе пересборка той же
`raw/` через месяц дала бы другие числа и проверка воспроизводимости стала бы ложной.

| `intent_score` | Компаний |
|---|---|
| 0 | 817 |
| 0–2 | 114 |
| 2–4 | 238 |
| 4–6 | 383 |
| 6+ | 108 |

### `fit_score` почти не различает — и это правильно

Значения только 6.0 и 5.0: рубрика и город совпадают у **всех**, потому что фильтр
ICP применён ещё на сборе — собирались только 36 рубрик белого списка и два города.
Различает единственный признак «есть сайт». Дублировать на этапе скоринга то, что
уже сделано на этапе сбора, не нужно; `fit_score` остаётся как страховка на случай,
когда в базу попадут компании из других источников (например, работодатели hh).

### Затухание пока ничего не делает

Все сигналы с сайтов имеют одну дату наблюдения — день сбора. Формула
`weight × 2^(-days/half_life)` работает, но на одинаковых датах вырождается в сумму
весов. Затухание оживёт, когда появится второй прогон сбора и вакансии с настоящим
`published_at`. Это не повод убирать его: убрать легко, добавить задним числом —
невозможно, дата наблюдения к тому моменту потеряется.

### Известный ложноположительный класс: интеграторы CRM

В топе оказались «automate systems **официальный партнер битрикс24 amocrm**» и
«businessprocess kz **партнер битрикс24 amocrm zoho crm**». У них Bitrix на сайте
потому, что они его **продают**, а не потому что управляют своими продажами.

Сигнал `crm_widget` для рубрик 186 (1С-франчайзи) и 112624 (IT-интеграторы) означает
не то, что для остальных. При этом сами компании из ICP не выпадают: интегратор
Bitrix — это B2B-услуги, и клиенты ему нужны.

```
# ponytail: не фильтруем. Тридцать лидов приёмки просматриваются глазами, а в
#           разбивке видно «виджет Bitrix24» рядом с названием «партнёр Битрикс24».
#           Отдельное правило — если класс попадёт в выдачу и после первых ответов.
```

### Шаги

1. Две функции, обе возвращают `(score, breakdown)`, где `breakdown` — список
   сработавших сигналов с весами. Объяснимость (PRD F17) обеспечивается разбивкой,
   а не отдельной сущностью.

2. `fit_score` — соответствие ICP по правилам: рубрика в `include`, город, наличие
   сайта, не в `exclude`.

3. `intent_score = Σ(weight × exp(-days_since / half_life))` — одно выражение.

4. **Нет сигналов ≠ отрицательный вес.** Компания без рекламы, но с CRM и отделом
   продаж — лучший лид из возможных.

5. Веса — словарь в начале файла. Это гипотеза; калибруется после первых 30 ответов.

### Приёмка

- вакансия вчерашняя даёт заметно больший вклад, чем полугодовой давности
- у любого лида из топ-10 `breakdown` объясняет его позицию
- модель в скоринге не участвует нигде

| В выдаче | 30 (astana 16, almaty 14) |

### Приёмка PRD

| # | Критерий | Статус |
|---|---|---|
| П1 | 30 компаний, бизнес-услуги, Алматы или Астана | ✅ |
| П2 | у каждой канал из `[whatsapp, phone, email]` | ✅ |
| П3 | у каждой `why_now` с цитатой и ссылкой | ⚠️ см. ниже |
| П5 | повторный прогон даёт тот же результат | ✅ дамп совпадает |
| П6 | ни одной записи с подменённой страницы | ✅ 28 подмен поймано |
| П4 | начата переписка | за человеком |

### Оговорка по П3: обоснование есть, цитаты нет

`why_now` собирается шаблоном из сигналов и выглядит так:

> платит за рекламу (Google Ads) — покупает лиды прямо сейчас; ведёт заявки в CRM
> (виджет Bitrix24) — есть отдел продаж и процесс; ждёт входящих: форма заявки

Это **факт с ссылкой на источник**, и оператор может его повторить в разговоре. Но
это не цитата из текста компании, а описание того, что мы нашли у неё на сайте.
Настоящая цитата есть только у сигналов из вакансий, а их в базе четыре (см. Ф5).

Следствие видно на числах: **на 30 лидов приходится 4 различных `why_now`.** Скоринг
насыщается — четыре типа сигнала с фиксированными весами дают мало комбинаций, и
верхние сто компаний стоят на 8.0 плечом к плечу.

Это ровно та работа, ради которой существует Ф9: модель читает текст сайта и пишет
причину, специфичную для компании. До первых ответов её делать рано — но и объявлять
П3 полностью закрытым нельзя.

### Решения фазы

**WhatsApp приводится к номеру.** 2GIS отдаёт его ссылкой `wa.me` с зашитым текстом
«Пишу из приложения 2ГИС». Оператор открывает WhatsApp Web и пишет сам — ему нужен
номер, а не чужая ссылка с чужим приветствием.

**Название берётся из карточки 2GIS**, а не из `companies.name_norm`: нормализованное
имя нужно склейке, оператору читать «Институт автоматизации, ТОО», а не
«институт автоматизации компания».

**Статус переписки в систему не возвращается.** Кто ответил и кому перезвонить —
работа человека в его таблице. Обратно приходит только `suppression`, и она
проверяется до выдачи, а не после (закон РК №94-V).

19 компаний с сигналами остались без канала и в выдачу не попали. Правило F19 не
смягчается ради красивого числа: компания без канала — не лид, а мусор в отчёте.

### Шаги

1. `VIEW` поверх `companies` + `contacts` + `signals` + скоринг.

2. **Жёсткое правило: лид без канала из `[whatsapp, phone, email]` в выдачу не
   попадает** (PRD F19). Компания с прекрасным скорингом, но без канала — не лид.

3. `suppression` проверяется **до** выдачи, не после (PRD F21). Таблица не
   очищается никогда.

4. Экспорт CSV: компания, канал, `why_now`, разбивка скоринга, ссылки на источники.

5. **Статус переписки в CSV не возвращается.** Кто ответил и кому перезвонить —
   работа человека в его таблице. В систему приходит только `suppression`.

### Приёмка — это приёмка PRD

| # | Критерий | Проверка |
|---|---|---|
| П1 | 30 компаний, бизнес-услуги, Алматы или Астана | выгрузка |
| П2 | у каждой канал из `[whatsapp, phone, email]` | колонка канала |
| П3 | у каждой `why_now` с цитатой и ссылкой | ручной просмотр всех 30 |
| П5 | повторный прогон даёт тот же результат | `build.py` дважды |
| П6 | ни одной записи с подменённой страницы | проверки Ф4 зелёные |

П4 — начата переписка — выполняется руками. Это и есть цель проекта.

На этой фазе `why_now` собирается **шаблоном из `signals`**: цитата из вакансии плюс
ссылка. Этого достаточно для П3. Агент — следующая фаза, и она не блокирует приёмку.

# Ф9. Классификация и `why_now` — OpenAI ✅

**Выполнено 14 августа 2026.** 40 компаний, модель `gpt-5.4-mini`, 40 ответов в кэше.

| | |
|---|---|
| Профилей в `profiles` | 40 из 40, ни одного пустого `why_now` или `quote` |
| Лидов с цитатой и отраслью | 30 из 30 |
| Различных `why_now` в выдаче | **30 из 30** (было 4 на шаблонах Ф8) |
| Повторный `classify.py 40` | новых вызовов 0, из кэша 40 |

Исходный план откладывал фазу до первых тридцати ответов: живые ответы переопределят
половину весов скоринга, и промпт, написанный до них, пишется вслепую. Решением
заказчика фаза построена сейчас. Отсрочка касалась только момента запуска — код от
этого не меняется, а кэш делает повторный прогон с другим промптом дешёвым.

### Что сделано

1. **Провайдер — OpenAI**, модель из `config.toml` `[llm].model`. Вызов —
   `POST /v1/chat/completions` со `response_format: json_schema`, `strict: true`,
   обычным HTTPS через тот же `Fetcher`, которым ходит `serp.py`. SDK не добавлен:
   зависимостей у проекта по-прежнему ноль сверх Scrapling.

2. **Кэш — `raw/<sha256(модель + промпт)>.llm.json`**, тот же content-addressed
   механизм, что у страниц, в той же папке. Рядом с ответом сохраняется сам промпт:
   через месяц он будет другим, и без него нельзя понять, на что модель отвечала.

3. **`classify.py` — сетевая сторона, как `collect.py`.** `build.py` читает готовые
   ответы с диска в таблицу `profiles` и остаётся чистой функцией от сырья: пересборка
   не стоит ни цента, платится только за компании, увиденные впервые.

4. **Один вызов, а не два.** ARCHITECTURE.md §11 разделяет классификацию и агента
   `why_now`; на топ-40 это лишнее — связи между источниками видны только в общем
   контексте, и одна схема лучше двух. `why_now` и `quote` — поля того же ответа.

5. **Только по топу отсева** (`[llm].top_n = 40`), не по всей базе: отрасль известна
   из рубрики, размер недостижим ни одним источником, отдел продаж виден по вакансии,
   CRM найден regex'ом. Модель добавляет только чтение текста сайта, порезанного до
   `[llm].site_chars = 6000`.

6. **Границы ИИ не сдвинуты.** В схеме ответа нет вердикта «писать или нет» — только
   `industry`, `size_hint`, `has_sales_team`, `why_now`, `quote`, `confidence`. Поля
   без основания в данных модель возвращает как `null`. Решают правила.

7. `report.py`: модельный `why_now` вытесняет шаблонный из Ф8, в CSV добавлены
   колонки **цитата** и **чем занимается**.

### Приёмка

- [x] без ключа `classify.py` выходит с внятной инструкцией, а не трассировкой
- [x] `raw/*.llm.json` под `.gitignore` вместе с остальным сырьём
- [x] имя модели взято из `--models`, а не угадано: в `config.toml` `gpt-5.4-mini`
- [x] **повторный прогон не тратит ни цента** — `новых вызовов 0, из кэша 40`
- [x] `build.py` остаётся чистой функцией: `sha256` дампа не изменился, `raw/` не вырос
- [x] `check.py` зелёный на всех семи разделах
- [x] `why_now` содержательнее шаблонного: 30 различных обоснований против 4

### Что нашлось

**Баг в `check.py`.** Сайдкары страниц отбирались как `raw/*.json` за вычетом
`.serp.json`. Появление `.llm.json` сломало равенство «страниц = сайдкаров» —
проверка честно упала на 40 лишних файлах. Исправлено по корню, а не по симптому:
сайдкар страницы — это `<sha1>.json`, то есть **ровно одна точка в имени**; всё с
составным суффиксом — кэш другого рода в той же папке. Следующий вид кэша проверку
уже не сломает.

### Чем это закрывает оговорку П3

На Ф8 `why_now` собирался шаблоном из `signals`, и на 30 лидах давал 4 разных
предложения: скоринг насыщается при четырёх типах сигналов, а описание маркера — не
обоснование. Теперь в выдаче 30 разных обоснований, и `quote` — дословная фраза с
сайта компании:

> «Закажите бесплатный экспресс аудит IT инфраструктуры. Оставьте свои контакты,
> в рабочее время мы выходим на связь в течение 15 минут.»

Это то, что оператор может повторить в разговоре. П3 выполнен не только буквально.

### Осталось

- Веса скоринга по-прежнему угаданы. Первые тридцать ответов переопределят половину —
  промпт классификатора тогда стоит переписать под понятные признаки. Кэш по
  `sha256(модель + промпт)` делает такую переделку дешёвой: платится только за новое.
- Ложные срабатывания `crm_widget` у интеграторов CRM модель видит и описывает
  корректно («продаёт услуги внедрения CRM»), но `intent_score` их по-прежнему
  завышает — фильтр не ставился намеренно, 30 лидов просматриваются глазами.

# Ф10. Веб-консоль оператора ✅

**Выполнено 14 августа 2026.** FastAPI + Next.js, две команды на запуск.

| | |
|---|---|
| Бэкенд | `api.py`, 4 эндпоинта, порт 8787 |
| Фронтенд | `web/`, Next 16 + React 19, порт 3000 |
| Новых зависимостей Python | `fastapi`, `uvicorn` |
| Файлов фронтенда | 5: `layout.tsx`, `page.tsx`, `LeadCard.tsx`, `api.ts`, `globals.css` |

### Найденная дыра, из-за которой всё чуть не потеряло смысл

`build.py` делает `DROP TABLE suppression`, а наполнял её **никто**. Таблица была
пуста с самого Ф8 — и первый же отказ, записанный из UI прямо в базу, исчез бы на
ближайшей пересборке. Это F21 и закон РК №94-V, то есть не «баг интерфейса».

Починено до написания UI: источник истины — `suppression.csv`, `build.fill_suppression`
заливает его в таблицу, API дописывает в файл и дублирует в базу, чтобы выдача
обновилась без пересборки. Файл первым: если запись в него не удалась, в базу не
пишем вовсе — лучше отсутствующий запрет, который человек увидит и повторит, чем
запрет, работающий до ближайшего `build.py`.

### Решения

1. **Отбор лидов импортируется из `report.py`, а не переписывается.** F19 и F21 —
   закон, а не формат вывода. Две копии закона расходятся на первой же правке.

2. **`/api/*` проксируется через `next.config.ts`.** Фронтенду не нужен ни адрес
   бэкенда в переменных окружения, ни CORS: один порт для человека, один для браузера.

3. **Веб не пишет в `leads.db`** ничего, кроме дубля отказа. Всё остальное —
   производное от `raw/`, и менять его в обход `build.py` значит ломать
   воспроизводимость ради удобства формы.

4. **Статуса переписки нет** — по той же причине, по которой его нет в базе. Кто
   ответил и кому перезвонить, человек ведёт у себя.

5. Скаффолд `create-next-app` вычищен: удалены `public/`, `page.module.css`, шрифты
   из `next/font/google` (тянут сеть на сборке), три README от генератора.

### Приёмка

- [x] `check.py web` — новый восьмой раздел: порядок веб-выдачи совпадает с
      `leads.csv` построчно, ни один отказ не просочился, файл и таблица сходятся
- [x] `npm run build` — типы и сборка чистые
- [x] отказ через форму проверен в браузере: оба канала с этим номером перечёркнуты,
      ссылка «открыть» снята, лид ушёл из списка, счётчик вырос
- [x] отказ пережил `build.py`
- [x] `web/node_modules` и `.next` не попадают в git — под коммит идёт 13 файлов

### Найдено при проверке в браузере

- **Длинное название компании выдавливало intent за край строки.** `overflow: hidden`
  не действует на инлайновом элементе — обёртке нужен `display: block` и
  `min-width: 0` в grid-ячейке.
- **Карточка не показывала, каким из каналов писать.** Добавлена пометка «пишем сюда»
  на канале, выбранном по приоритету WhatsApp → телефон → почта.

### Осталось

- Аутентификации нет: инструмент поднимается на `localhost` одним оператором. Прежде
  чем выставлять наружу, нужна она и HTTPS — сейчас `POST /api/suppression` открыт
  всякому, кто дотянется до порта.
- Запуска пайплайна из веба нет: `collect.py` идёт полтора часа, и кнопка, которая
  на полтора часа вешает HTTP-запрос, — это очередь и воркеры, то есть ровно то,
  что v2 выкинула. Появится вместе с триггером из §9. **Закрыто в Ф11.**
- `leads.csv` не обновляется сам после отказа из UI. `check.py` это ловит; лечится
  запуском `report.py`.

# Ф11. Продуктизация: джобы, SSE, дашборд ✅

**Выполнено 18 августа 2026.** MVP-консоль стала продуктом: продуктовые
эндпоинты вместо запуска скриптов, живые процессы на экране, дашборд с тремя
системами. Закрывает «Осталось» Ф10 про запуск пайплайна из веба.

| | |
|---|---|
| Очередь | `services/jobs.py`: таблица `jobs` в `db/ops.db`, один asyncio-воркер |
| Продуктовые операции | `POST /api/pipeline/{discover\|classify\|rebuild\|write}` |
| Real-time | `GET /api/events` — SSE: `snapshot`, `job`, `log`, `refresh` |
| Счётчики | `GET /api/stats` — все три системы одним ответом |
| Система 3 | `sender/stub.py`: `GET /api/sender` отдаёт «скоро», остальное — 501 |
| Фронтенд | сайдбар + 4 страницы: обзор, сбор, персонализация, отправка |
| Удалено | `routes/runs.py`, страница `/runs` — консоль запуска скриптов |

### Решения

1. **Джоба ≠ команда.** У джобы есть шаги с именами, и фронт показывает «шаг 2
   из 3», а не хвост консоли. Шаги — те же `uv run ...` из белого списка argv,
   без shell; аргументы из веба не принимаются.
2. **Состояние очереди в базе, не в памяти.** История и прогресс переживают
   перезагрузку страницы и рестарт бэкенда: `running` без процесса помечается
   проваленной (`fail_orphans`), `queued` продолжается воркером при старте.
   Исполнение одно за раз — `build.py` пересобирает базу через `DROP`, — но
   очередь честная: ставить можно несколько.
3. **SSE, а не поллинг.** Подписка начинается снапшотом, дальше летят изменения;
   reconnect приносит снапшот заново, потерь у клиента нет. Издатели и подписчики
   в одном event loop — эндпоинты, публикующие события, объявлены `async`.
4. **SSE ходит на API-оригин напрямую, минуя rewrite next.** Dev-прокси Next 16
   отдаёт браузеру заголовки стрима, но буферизует тело бесконечного ответа —
   события до страницы не доезжают. JSON-эндпоинтам это не мешает.
5. **Прогресс внутри шага — строкой вывода.** `#progress {"current": N, "total":
   M}` разбирается воркером и уходит в событие `job`: счётчики UI без второго
   канала связи. Скрипты таких строк пока не пишут, парсер ждёт.
6. **Система 3 заявлена, а не спрятана.** Страница «Отправка» рисует замок и
   «скоро» из ответа бэкенда; любая операция — 501, а не 404.
7. **Инбокс системы 2.** `GET /api/threads` — треды одной сводкой (последняя
   реплика, счётчики); черновик в «последнюю реплику» не попадает — лид его
   не получал.

### Приёмка

- [x] `check.py jobs` — десятый раздел: очередь на временной базе, успех/провал/
      отмена/сироты/шина событий/контракт снапшота
- [x] e2e в браузере: запуск `rebuild` кнопкой, шаги и живой лог по SSE,

- [x] `npm run build` и `tsc --noEmit` чистые
