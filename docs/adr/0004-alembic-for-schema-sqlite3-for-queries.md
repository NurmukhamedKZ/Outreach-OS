# Alembic для схемы, синхронный sqlite3 для запросов

Схема базы жила в трёх стилях: `schema.sql` с маркерами, `_ensure_columns` в `writer`, `migrate.py` в `sender` — и породила правило «чужую колонку терпим, а не доливаем». Решили: схема новых модулей ведётся одной историей Alembic в `backend/migrations/`, миграции пишутся операциями в batch-режиме, обратимы и применяются программно при старте приложения и при создании базы прогона песочницы. Запросы модулей остаются сырым SQL через стандартный `sqlite3`; ORM и SQLAlchemy Core в коде модулей не используются.

## Considered Options

- **Свои нумерованные SQL-файлы и раннер на тридцать строк.** Отвергнуто: SQLite меняет таблицу только пересозданием с копированием данных, и эту процедуру пришлось бы каждый раз писать руками на таблицах с отказами и перепиской. Alembic делает пересоздание сам.
- **`aiosqlite` и асинхронный доступ.** Отвергнуто: у SQLite один писатель, асинхронный драйвер — тот же поток в обёртке и лишняя зависимость.
- **SQLAlchemy Core для запросов.** Не принято, пока база — SQLite: вернуться к вопросу при переезде на Postgres (ADR 0002).

## Consequences

- История миграций одна на все модули: две миграции от одной базы дают две головы, поэтому миграцию одновременно добавляет не больше одного кодера.
- SQLAlchemy появляется в зависимостях только как движок Alembic.
- Таблицы `writer` и `sender` остаются вне Alembic до #7.
- Роуты, которые ходят в базу, объявляются обычным `def`: FastAPI исполняет их в пуле потоков.
