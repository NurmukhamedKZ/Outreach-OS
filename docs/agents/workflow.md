# Воркфлоу: настройки проекта

Факты о проекте для скиллов плагина `workflow` (`launch-main`, `launch-coder`, `review-axes`, `ci-watch`, `manual-qa`). Скиллы описывают процесс, а этот файл — где что лежит и какими командами проверяется. Правится руками; создаёт `/workflow:setup`. Скилл ссылается на раздел по его заголовку: «workflow.md, «Ветки»».

## Проект

- **Название:** Outreach-OS
- **Репо:** `NurmukhamedKZ/Outreach-OS` (GitHub, работа через `gh`; соглашения трекера — `docs/agents/issue-tracker.md`)
- **Родительский issue тикетов:** #3 — новые тикеты заводятся его sub-issue (`gh api --method POST repos/NurmukhamedKZ/Outreach-OS/issues/3/sub_issues -F sub_issue_id=<database id>`), связи — «blocked by».
- **Метка готового тикета:** `ready-for-agent` (метки — `docs/agents/triage-labels.md`)

## Автономия main

Main ведёт тикеты сам и зовёт пользователя только по списку «Когда звать пользователя». Там, где скиллы плагина говорят иначе, действует эта таблица.

| В скилле | У нас |
|---|---|
| грилинг пользователя (`launch-main`, шаг 2) | пользователю — только решения из «Когда звать пользователя», одним раундом; остальное main решает сам по коду, `GLOSSARY.md`, ADR и спеке #4 и записывает в «Решения грилинга» как свои решения |
| ревью спеки пользователем (`launch-main`, шаг 5) | нет: main пишет спеку и сразу запускает кодера; пользователю — одна строка со ссылкой на issue |
| «мержит пользователь» | мержит main: `gh pr merge <PR> --squash`, когда выполнены «Условия мержа» |
| новый тикет по команде пользователя | main не ждёт команды: после мержа убирает worktree и берёт следующий тикет без открытых блокеров; изучать и грилить следующий тикет начинает заранее, пока кодер работает над текущим |

**Маленькое изменение — сразу, без тикета.** Main не заводит тикет на правку, которую быстрее сделать, чем описать. Маленькое — всё сразу:
- до ~50 строк кода в 1–3 файлах, без новой миграции и без нового модуля;
- не трогает чувствительные пути из «Ревью» (отправка, отказы, вебхук, песочница, `config.py`);
- не требует решений из «Когда звать пользователя».

Как: main сам в своём worktree `.claude/worktrees/fix-<slug>` на ветке `fix/<slug>` от свежего `main` — сначала падающий тест, затем правка, `scripts/check` («Проверки»), PR с коротким описанием, мерж squash, уборка. Находка внутри идущего тикета того же участка — не отдельная правка, а сообщение его кодеру. Не подходит хотя бы по одному пункту — тикет, как обычно.

**Связь с кодерами** — `cmux agent message` (`launch-main`, шаг 7): кодер пишет main о вопросах, развилках и готовом PR; main отвечает сам, если ответ следует из спеки, кода или решений пользователя. Страховка на случай потерянного сообщения — фоновое ожидание PR ветки тикета: `until gh pr list --head ticket/<N>-<slug> --json number -q '.[0].number' | grep -q .; do sleep 60; done`.

**Условия мержа.** Все сразу:
- в описании PR — итог `/workflow:review-axes` без нерешённых находок и вывод `scripts/check`, зелёный;
- для тикета с интерфейсом пройден `/workflow:manual-qa`, а если дифф трогает `frontend/`, в выводе `scripts/check` зелёный `e2e`;
- ветка обновлена из `main`, конфликтов нет; у тикета с миграцией — одна голова Alembic;
- у кодера нет открытых вопросов к main.

После мержа main обновляет своё дерево, прогоняет `scripts/check --all` на `main`, закрывает панель кодера целиком — терминал и все вкладки в ней, включая страницу PR на GitHub (`cmux list-pane-surfaces --pane <панель кодера>` → `cmux close-surface --surface <каждая> --force`), — убирает worktree и ветку и докладывает пользователю: что влито, что дальше. Красные тесты на `main` — сразу кодеру или новому тикету, а не молча.

**Когда звать пользователя.** Main останавливается и спрашивает, если:
- решение продуктовое: что видит и делает оператор, что и кому пишем, цены и оффер;
- решение противоречит ADR или спеке #4 либо его трудно откатить (перенос или удаление данных, смена контракта между модулями);
- действие может отправить сообщение живому человеку: режим автопилота, боевой Node, номера;
- нужен живой прогон, который ходит в 2GIS или платит за модель больше, чем за одну партию;
- нужно удалить данные: `backend/data/`, сессии WhatsApp, отказы;
- три круга ревью не сошлись или проверки красные, и кодер не может их починить;
- тикеты без открытых блокеров кончились.

## Ветки

- **База тикетов и единственная постоянная ветка:** `main` — тикеты вливаются squash.
- **Ветка тикета:** `ticket/<N>-<slug>`, worktree — `.claude/worktrees/ticket-<N>-<slug>` от `origin/main`.
- **Мержит main-сессия** (squash), см. «Автономия main». Удалённую ветку после мержа удаляет GitHub (`delete_branch_on_merge` включён); локальную ветку и worktree убирает main-сессия (`/workflow:launch-main`, шаг 0).

## Параллельные кодеры

Сверх общих условий `/workflow:launch-main` (нет «blocked by» между тикетами, не трогают одни файлы):

- миграцию Alembic (`backend/migrations/`) добавляет не больше одного: две миграции от одной базы дают две головы (ADR 0004). Перед пушем ветки с миграцией — `git fetch`, перебазироваться на свежий `main`, `uv run alembic heads` — голова одна;
- сборщик приложения `backend/main.py` правит не больше одного.

## Проверки

Полный набор — один раз на финальном коде после ревью (`/workflow:launch-coder`, шаг 4). В цикле TDD — только отдельные тест-файлы.

- **Одна команда из корня:** `scripts/check` (#50). Бэкенд — всегда, четыре проверки параллельно: `ruff check` и `ruff format --check`, `mypy`, `lint-imports`, `pytest` (сети не требует, около 25 секунд); охват линтеров — `backend/CLAUDE.md`, «Команды». Фронт — `npm run build`, затем `npx tsc --noEmit` (сборка пересоздаёт `.next/types`, без неё `tsc` падает на устаревших), только если дифф относительно `origin/main` трогает `frontend/`; `--all` — всё независимо от диффа. Вывод — строка на проверку (`ok`/`FAIL`/`skip` и время) и текст только упавших; код выхода 1 при любой красной. Нет `frontend/node_modules` — подсказка `cd frontend && npm ci`. Node-транспорт — `npm test` в `backend/sender/node` (#55, `node:test`, секунда), только если дифф трогает `backend/sender/node/`; `npm ci` не нужен: `server.js` не импортирует пакетов. Контракт Node с Python (`backend/sender/node/test/contract.json`) читает и `pytest`, поэтому расхождение подменного Node ловится без этой проверки.
- **Хук `pre-push`** (`scripts/hooks/pre-push`) зовёт `scripts/check --pre-push`: красная ветка не пушится, push с незакоммиченными правками и push коммита, который не `HEAD` этого дерева, отклоняются (проверки идут по рабочему дереву), удаление ветки проходит без проверок. Подключение — один раз на клон, действует на все worktree: `git config core.hooksPath scripts/hooks`.
- **E2E** (#54) — запись `e2e`: `npx playwright test` во `frontend/`, по тому же диффу, что фронт, и в `pre-push`. Прогон поднимает свой стенд (`frontend/e2e/stand.ts`: стирает `.stand/data`, `scripts/stand up` собирает демо-мир, в конце `scripts/stand down`), офлайн, без сети и ключей, около 30 секунд со стартом стенда; идёт после проверки `frontend` (поле `after` записи: `next dev` стенда переписывает `next-env.d.ts` и `.next/dev/types`, которые читает `tsc`), весь `scripts/check --all` — около 45 секунд. Стенд дерева уже поднят — прогон отказывается: `scripts/stand down`. Нет браузера — подсказка `cd frontend && npx playwright install chromium`. Упавший тест оставляет скриншот и трейс в `frontend/e2e/results/` (в `.gitignore`): `npx playwright show-trace <trace.zip>`. Как писать тест — `frontend/AGENTS.md`, «E2E».
- **Новая проверка** — одна запись в таблице `CHECKS` в начале `scripts/check`.

Отдельного линтера фронтенда нет: типы проверяют `tsc` и `next build`, а ESLint без правил проекта только шумел бы (#5). CI в репо нет: проверки идут локально, `/workflow:ci-watch` пропускается.

## Ревью

- **Модель субагентов осей:** `sonnet` (пять ревьюеров на Opus съедают лимит и падают с 429).
- **Доменные edge cases** (ось «Баги», сверх общих): граница окна 10:00–18:00 и суток в Asia/Almaty; повторная доставка вебхука (дедуп по `provider_id`); отказ лида в любой момент — проверяется до выдачи и до отправки; лид без канала (F19); падение посреди партии исследования или посреди тика; перезапуск процесса; пустое или медиа-входящее; номер в неканонической форме; смена режима автопилота при непустой очереди (строки автомата и оператора); повторное исследование компании против нового платного вызова (досье — версией, а не перезаписью).
- **Чувствительные пути** (ось «Безопасность» запускается, только если дифф их трогает): `backend/delivery/` (самые чувствительные — гейты в `domain.py`, тик в `worker.py`, вебхук и постановка в очередь в `service.py`), `backend/core/whatsapp.py`, `backend/sender/node/`, `backend/refusals/`, правило лида `backend/research/` (F19–F21), `backend/config.py`, миграции, `backend/sandbox/`.
- **Правила безопасности:** `CLAUDE.md`, «Безопасность».

## Ручной QA

- **E2E и ручной QA делят работу** (#54): e2e (`frontend/e2e/`, «Проверки») ловит регрессию — каждую страницу на двух экранах и сценарии переписки, отправки, настроек и исследования; ручной QA смотрит новый интерфейс глазами. Тикет с интерфейсом добавляет или правит e2e-тест своей истории тем же PR.
- **Инструмент:** Playwright MCP (`mcp__plugin_playwright_playwright__*`); QA делает Claude, не пользователь.
- **Где:** локально, preview-деплоев нет. `scripts/stand up` в своём worktree (`CLAUDE.md`, «Команды»): бэкенд и фронт на свободных портах, страницы — по адресу `dashboard`, который печатает команда; после QA — `scripts/stand down`. Стенды разных кодеров не мешают друг другу. Стенд задаёт всё сам и ключей не требует: он офлайн (`OFFLINE=1`, `CLAUDE.md`, «Песочница») — партия, черновики и продавец отвечают без сети и без денег, ключ модели из `backend/.env` не читается, 503 `errors.modelKeyMissing` нет. `scripts/stand up --online` — настоящая модель и сеть (ключ — в `backend/.env`, скопировать из основного дерева): для работы над промптами, не для QA; живой прогон там — решение пользователя («Когда звать пользователя»).
- **Переписка и отправка** проверяются только в песочнице — стенд всегда в ней (`SANDBOX=1`, подменный Node на своём порту, Telegram выключен). Боевой Node (`backend/sender/node`) для QA не запускается; режим автопилота боевой базы не трогается (умолчание — `manual`, настройка «Отправка»). `companies` и `research` в песочнице работают с боевой базой стенда (`.stand/data/state.db`). На офлайн-стенде «Исследовать партию», «Исследовать заново», «Черновики топ-N» и ответ продавца нажимать можно: страницы — только сохранённые в `.stand/data/pages` (чего нет — 404, сегмент без страниц не собирается), модель отвечает детерминированно, каждый её текст начинается с `[офлайн]`. На стенде `--online` они ходят в 2GIS и платят за модель — там их в QA не нажимают.
- **Вердикт продавца офлайн** — по последней реплике лида, регистр не важен, первое найденное слово в порядке таблицы (`conversations/offline.py`, `VERDICTS`). Стоп-слова доставки («не пиши», «отпиш», «спам», «жалоб»…) закрывают тред до продавца — во входящем для проверки продавца их не писать.

  | Слово во входящем | Что делает продавец |
  |---|---|
  | `отказываемся` | `refusal` — отказ, тред закрыт |
  | `созвонимся` | `interested` — тред человеку |
  | `ошиблись` | `wrong_number` — не тот человек |
  | `абракадабра` | `junk` — бессмыслица |
  | `сколько` | ответ с ценой — `needs_human` отдаёт его человеку |
  | любое другое | `answer` — черновик ответа |
- **Бэкап:** на стенде выключен (`BACKUP_DIR` без родительского каталога) — снимков в iCloud Drive QA не делает.
- **Устройства:** десктоп `1280×800`, телефон `390×844`.
- **Языки:** только русский.
- **Данные:** демо-мир (#53). Свежий офлайн-стенд собирает его сам за секунды: `scripts/stand up` печатает строку `world` со сводкой. Выдуманные компании проходят настоящий конвейер, поэтому ни одна из десяти страниц не пуста: на «Сегодня» — задачи всех видов, на `/sender` — пул из трёх номеров и очередь, в «Процессах» — журнал всех демонов, на `/sandbox` — прогон на лида «Бухгалтерия Ласточка». Что в мире — `CLAUDE.md`, «Песочница», абзац «Демо-мир». Копия рабочей базы и мини-сбор main-сессии не нужны: настоящие лиды и их номера на стенд не кладутся. Повторный `up` мир второй раз не собирает. Пересобрать: `scripts/stand down && rm -rf .stand && scripts/stand up`. Пустой стенд — `scripts/stand up --empty`. Часы прогона мира сдвинуты на 11–14 суток вперёд, режим автопилота — `manual`.
- **Скриншоты:** только в `.playwright-mcp/` (в `.gitignore`).
- **Тикет доделок:** открытый issue «Доделки QA: …», ещё не взятый в работу; образца пока нет — заводится при первых доделках sub-issue #3.
