# Воркфлоу: настройки проекта

Факты о проекте для скиллов плагина `workflow` (`launch-main`, `launch-coder`, `review-axes`, `ci-watch`, `manual-qa`). Скиллы описывают процесс, а этот файл — где что лежит и какими командами проверяется. Правится руками; создаёт `/workflow:setup`. Скилл ссылается на раздел по его заголовку: «workflow.md, «Ветки»».

## Проект

- **Название:** Outreach-OS
- **Репо:** `NurmukhamedKZ/Outreach-OS` (GitHub, работа через `gh`; соглашения трекера — `docs/agents/issue-tracker.md`)
- **Родительский issue тикетов:** #3 — новые тикеты заводятся его sub-issue (`gh api --method POST repos/NurmukhamedKZ/Outreach-OS/issues/3/sub_issues -F sub_issue_id=<database id>`), связи — «blocked by».
- **Метка готового тикета:** `ready-for-agent` (метки — `docs/agents/triage-labels.md`)

## Автономия main

Main ведёт тикеты сам и зовёт пользователя только по списку «Когда звать пользователя». Там, где скиллы плагина говорят иначе, действует эта таблица.

| В скилле | У нас |
|---|---|
| грилинг пользователя (`launch-main`, шаг 2) | пользователю — только решения из «Когда звать пользователя», одним раундом; остальное main решает сам по коду, `GLOSSARY.md`, ADR и спеке #4 и записывает в «Решения грилинга» как свои решения |
| ревью спеки пользователем (`launch-main`, шаг 5) | нет: main пишет спеку и сразу запускает кодера; пользователю — одна строка со ссылкой на issue |
| «мержит пользователь» | мержит main: `gh pr merge <PR> --squash`, когда выполнены «Условия мержа» |
| новый тикет по команде пользователя | main не ждёт команды: после мержа убирает worktree и берёт следующий тикет без открытых блокеров; изучать и грилить следующий тикет начинает заранее, пока кодер работает над текущим |

**Маленькое изменение — сразу, без тикета.** Main не заводит тикет на правку, которую быстрее сделать, чем описать. Маленькое — всё сразу:
- до ~50 строк кода в 1–3 файлах, без новой миграции и без нового модуля;
- не трогает чувствительные пути из «Ревью» (отправка, отказы, вебхук, песочница, `config.py`);
- не требует решений из «Когда звать пользователя».

Как: main сам в своём worktree `.claude/worktrees/fix-<slug>` на ветке `fix/<slug>` от свежего `main` — сначала падающий тест, затем правка, полный набор «Проверок», PR с коротким описанием, мерж squash, уборка. Находка внутри идущего тикета того же участка — не отдельная правка, а сообщение его кодеру. Не подходит хотя бы по одному пункту — тикет, как обычно.

**Связь с кодерами** — `cmux agent message` (`launch-main`, шаг 7): кодер пишет main о вопросах, развилках и готовом PR; main отвечает сам, если ответ следует из спеки, кода или решений пользователя. Страховка на случай потерянного сообщения — фоновое ожидание PR ветки тикета: `until gh pr list --head ticket/<N>-<slug> --json number -q '.[0].number' | grep -q .; do sleep 60; done`.

**Условия мержа.** Все сразу:
- в описании PR — итог `/workflow:review-axes` без нерешённых находок и вывод полного набора проверок, зелёный;
- для тикета с интерфейсом пройден `/workflow:manual-qa`;
- ветка обновлена из `main`, конфликтов нет; у тикета с миграцией — одна голова Alembic;
- у кодера нет открытых вопросов к main.

После мержа main обновляет своё дерево, прогоняет `cd backend && uv run pytest` на `main`, закрывает панель кодера целиком — терминал и все вкладки в ней, включая страницу PR на GitHub (`cmux list-pane-surfaces --pane <панель кодера>` → `cmux close-surface --surface <каждая> --force`), — убирает worktree и ветку и докладывает пользователю: что влито, что дальше. Красные тесты на `main` — сразу кодеру или новому тикету, а не молча.

**Когда звать пользователя.** Main останавливается и спрашивает, если:
- решение продуктовое: что видит и делает оператор, что и кому пишем, цены и оффер;
- решение противоречит ADR или спеке #4 либо его трудно откатить (перенос или удаление данных, смена контракта между модулями);
- действие может отправить сообщение живому человеку: режим автопилота, боевой Node, номера;
- нужен живой прогон, который ходит в 2GIS или платит за модель больше, чем за одну партию;
- нужно удалить данные: `backend/data/`, сессии WhatsApp, отказы;
- три круга ревью не сошлись или проверки красные, и кодер не может их починить;
- тикеты без открытых блокеров кончились.

## Ветки

- **База тикетов и единственная постоянная ветка:** `main` — тикеты вливаются squash.
- **Ветка тикета:** `ticket/<N>-<slug>`, worktree — `.claude/worktrees/ticket-<N>-<slug>` от `origin/main`.
- **Мержит main-сессия** (squash), см. «Автономия main». Удалённую ветку после мержа удаляет GitHub (`delete_branch_on_merge` включён); локальную ветку и worktree убирает main-сессия (`/workflow:launch-main`, шаг 0).

## Параллельные кодеры

Сверх общих условий `/workflow:launch-main` (нет «blocked by» между тикетами, не трогают одни файлы):

- миграцию Alembic (`backend/migrations/`) добавляет не больше одного: две миграции от одной базы дают две головы (ADR 0004). Перед пушем ветки с миграцией — `git fetch`, перебазироваться на свежий `main`, `uv run alembic heads` — голова одна;
- сборщик приложения `backend/main.py` правит не больше одного.

## Проверки

Полный набор — один раз на финальном коде после ревью (`/workflow:launch-coder`, шаг 4). В цикле TDD — только отдельные тест-файлы.

- **`backend/`:** `cd backend && uv run ruff check . && uv run ruff format --check . && uv run mypy && uv run lint-imports && uv run pytest` (сети не требует, около 30 секунд). Охват линтеров — `backend/CLAUDE.md`, «Команды».
- **`frontend/`, если дифф его трогает:** `cd frontend && npx tsc --noEmit && npm run build`.

Отдельного линтера фронтенда нет: типы проверяют `tsc` и `next build`, а ESLint без правил проекта только шумел бы (#5). CI в репо нет: проверки идут локально, `/workflow:ci-watch` пропускается.

## Ревью

- **Модель субагентов осей:** `sonnet` (пять ревьюеров на Opus съедают лимит и падают с 429).
- **Доменные edge cases** (ось «Баги», сверх общих): граница окна 10:00–18:00 и суток в Asia/Almaty; повторная доставка вебхука (дедуп по `provider_id`); отказ лида в любой момент — проверяется до выдачи и до отправки; лид без канала (F19); падение посреди партии исследования или посреди тика; перезапуск процесса; пустое или медиа-входящее; номер в неканонической форме; смена режима автопилота при непустой очереди (строки автомата и оператора); повторное исследование компании против нового платного вызова (досье — версией, а не перезаписью).
- **Чувствительные пути** (ось «Безопасность» запускается, только если дифф их трогает): `backend/delivery/` (самые чувствительные — гейты в `domain.py`, тик в `worker.py`, вебхук и постановка в очередь в `service.py`), `backend/core/whatsapp.py`, `backend/sender/node/`, `backend/refusals/`, правило лида `backend/research/` (F19–F21), `backend/config.py`, миграции, `backend/sandbox/`.
- **Правила безопасности:** `CLAUDE.md`, «Безопасность».

## Ручной QA

- **Инструмент:** Playwright MCP (`mcp__plugin_playwright_playwright__*`); QA делает Claude, не пользователь.
- **Где:** локально, preview-деплоев нет. `cd backend && uv run python main.py` (порт 8787) и `cd frontend && npm run dev`, страницы — `http://localhost:3000`.
- **Переписка и отправка** проверяются только в песочнице: `SANDBOX=1` и `SENDER_NODE_URL=http://127.0.0.1:8787/api/sandbox/node` в `backend/.env`. Боевой Node (`backend/sender/node`) для QA не запускается; режим автопилота боевой базы не трогается (умолчание — `manual`, настройка «Отправка»).
- **Бэкап:** при запуске бэкенда для QA задай `BACKUP_DIR` во временный каталог: демон `backup` иначе делает снимок копии базы в настоящую папку iCloud Drive, а снимок за сегодня откладывает следующий настоящий (и без сессий WhatsApp).
- **Устройства:** десктоп `1280×800`, телефон `390×844`.
- **Языки:** только русский.
- **Данные:** слой данных пуст. Страницы с данными проверяются после мини-сбора (одна рубрика, один город), который один раз делает main-сессия, а не каждый кодер; сбор ходит в сеть и платит за модель.
- **Скриншоты:** только в `.playwright-mcp/` (в `.gitignore`).
- **Тикет доделок:** открытый issue «Доделки QA: …», ещё не взятый в работу; образца пока нет — заводится при первых доделках sub-issue #3.
