# Система №1 — Intelligent Targeting & Data Enrichment (Казахстан)

Проектный документ. Зафиксированы решения на 6 августа 2026.
Источники проверены фактически (curl / WebFetch / WebSearch) — см. Приложение А.

---

## Назначение

Система находит B2B-компании в Казахстане, обогащает их данными и сигналами,
и выдаёт готовые профили лидов с каналами связи и обоснованием «почему им нужна
лидогенерация именно сейчас».

Это **Система №1** из трёх. Система №2 (AI-персонализация писем) и Система №3
(инфраструктура доставки) — вне этого документа. Здесь фиксируется только то,
какие идентификаторы и сигналы собирать, чтобы №2 и №3 могли работать.

**Первый пользователь системы — её автор.** Цель v1 — найти клиентов на услуги
AI-лидогенерации и превратить сам процесс в кейс.

## 1. ICP

### Страна и география
Казахстан, **Алматы + Астана**. РФ — не раньше, чем КЗ заработает полностью.

### Тип бизнеса
Компании, которые **сами продают B2B**.

Это осознанный выбор из трёх вариантов. Отвергнутая альтернатива — B2C-бизнесы
(клиники, риелторы, онлайн-школы, e-com): их легче продать, но им нужен inbound
(реклама, SEO), а не outbound по компаниям. Система нашла бы их, но не смогла бы
произвести то, что им продаётся. При выборе «сами продают B2B» одна система
работает и для нас, и для клиента — мы продаём ровно то, чем пользуемся сами.

### Отрасль v1 — Бизнес-услуги

| Сегмент | ~компаний (Алматы+Астана) |
|---|---|
| Бухгалтерский аутсорс | 800–1500 |
| Юридический аутсорс для компаний | 500–1000 |
| HR / рекрутинг / аутстаффинг | 200–400 |
| IT-аутсорс, сисадмин, 1С | 300–600 |
| Консалтинг, аудит, налоговый | 300–500 |
| Клининг / охрана / АХО-аутсорс | 500–1000 |

**Итого ~2500–5000, после фильтра (10+ человек, есть сайт) → ~1000–1500.**

Почему отрасль сильная:
- продают B2B-услугу по подписке — та же модель, что у нас, разговор на одном языке
- **уже делают outbound руками** (холодный обзвон — их основной канал), продаём не
  идею, а замену ручного труда
- вакансия «менеджер по продажам» = прямое признание нехватки клиентов

**Чёрный список:** SMM- и маркетинговые агентства, лидген-подрядчики, таргетологи —
конкуренты. Отсеивать по рубрике 2GIS автоматически, не вручную.

### Фильтры
```
geo:        Алматы, Астана
size:       10–200 сотрудников
must:       есть сайт
exclude:    госсектор, монополии, микро (<5 чел), маркетинговые агентства
```

## 2. Целевая воронка и масштаб

Калибровка по реальным цифрам отрасли (Respondo, десятки проектов):

```
1000–1500 компаний в базе
   → 50 писем/день с одного почтового аккаунта
   → цепочка из 5 писем = 200 компаний/мес на аккаунт
   → reply rate 8–15%
   → лидов 2–5%
   → 20–40 лидов → 2–4 сделки за полгода
```

**Ключевое следствие:** целевой масштаб — **тысячи компаний, не сотни тысяч.**
Отсюда: Postgres на одной машине, никакого шардирования, никаких оптимизаций,
дорогой агент можно пускать хоть на всю базу.

Оговорка: цифры выше — **email-воронка** (данные российского рынка). В Казахстане
WhatsApp даёт больший объём при том же ручном труде — ~60 новых диалогов в день
против 50 писем, то есть ~1200/мес против 200/мес на аккаунт. Реальная воронка КЗ
будет мультиканальной, но её конверсию мы узнаем только после первых 30 лидов,
поэтому планируем по консервативной email-цифре.

Верхняя граница по каналам: ~60 новых диалогов в WhatsApp в день до бана,
50 писем/день на почтовый аккаунт. Выдавать больше 50–60 готовых лидов в день
бессмысленно — их некуда девать.

## 3. Источники данных

### Основные

| Источник | Роль | Доступ | Цена |
|---|---|---|---|
| **SERP** (Serper.dev) | Утилита + discovery + транспорт для hh | API | **$1 / 1000 запросов** |
| **hh.kz через SERP** | Intent: тексты вакансий | Google-поиск + прямые URL вакансий | входит в SERP |
| **2GIS** | Охват, телефоны, рубрики, адреса | Браузерный профиль | прокси |
| **Сканер сайтов** | Email, CRM, пиксели, признаки продаж | Scrapling | 0 |

### Резерв (для других ICP, не для бизнес-услуг)

| Источник | Когда пригодится |
|---|---|
| Instagram | B2C-отрасли, HoReCa-поставщики, e-com |
| Meta Ad Library (веб, браузером) | Отрасли, рекламирующиеся в Meta |
| satu.kz / flagma.kz | Оптовая торговля, дистрибуция |
| kgd.gov.kz списки | Фильтр качества: лжепредприятия, банкроты, недоимщики (бесплатные годовые дампы) |
| statsnet.co API | Финансы и руководитель по БИН, от 4990 ₸/мес |

### LinkedIn — активный канал для этого ICP, но только через Google

Для бизнес-услуг в Алматы/Астане LinkedIn живой (оценка владельца проекта), поэтому
он **не в резерве** — это рабочий источник имён ЛПР на этапе S6. Но доступ к нему
только через SERP-выдачу: `site:linkedin.com/in "Ромашка" (директор OR коммерческий)`.

**Для сбора данных** аккаунт LinkedIn не нужен вообще: сниппет Google обычно уже
содержит имя и должность, на страницу заходить не приходится. Отсюда нет нарушения
ToS, нет риска бана, нет лимитов поиска.

**Для отправки** аккаунт, разумеется, нужен — но это Система №3, и она использует
твой личный, который остаётся чистым именно потому, что мы им ничего не скрейпим.
Лимиты отправки — в §11.

### Ключевая связка: hh через Google

`api.hh.ru` закрыт (403), поиск на `hh.kz` под DataDome и `robots.txt: Disallow: *?*`.
Но `/vacancy/<id>` без параметров **разрешён**. Отсюда:

```
1. Поиск делает Google:  site:hh.kz "бухгалтерские услуги" "менеджер по продажам" Алматы
2. Получаем прямые URL:  hh.kz/vacancy/12345678
3. Забираем вакансию по прямому URL — robots.txt это разрешает
4. Полный текст → core.vacancies → полнотекстовый поиск
```

Закрытую поисковую функцию нам возвращает Google; тексты берём оттуда, откуда
разрешено. Это воспроизводит киллер-фичу Контур.Компаса — **поиск по тексту
вакансий**, который в кейсах даёт reply rate 8–20% против обычных 3–5%.

Ограничение: Google индексирует не все вакансии и с лагом в несколько дней.
Для нашего масштаба несущественно — вакансия живёт неделями.

> **В Казахстане нет Контур.Компаса и купить его негде.** Российский лидген стоит
> на готовой базе с фильтрами по ОКВЭД, выручке и вакансиям. В КЗ этой
> инфраструктуры не существует. Мы не строим обвязку вокруг чужой базы — мы строим
> отсутствующую на рынке инфраструктуру данных. Это и есть актив.

## 4. Архитектура

### 4.0 Браузерный слой (фундамент)

Часть источников доступна только реальному браузеру. Профиль на источник,
ручной логин один раз, персистентный `user_data_dir`.

```
profiles/
  2gis/        StealthySession(real_chrome=True, user_data_dir=...)
  hh/          (если понадобится прямой доступ)
  instagram/   (резерв, уже настроен)
```

Правила:
- один источник = один профиль = один аккаунт, **не смешивать** (бан не должен
  утаскивать соседей)
- человеческий темп: рандом 3–8 с между страницами
- резидентный прокси KZ на профиль
- circuit breaker: 3 подряд challenge → профиль на паузу + алерт

**Физическое ограничение системы:** реальный браузер с человеческим темпом даёт
**200–400 страниц в час на профиль**. Не API-лимиты определяют производительность,
а это число. 1000 компаний ≈ 3–4 часа скрейпа — приемлемо.

Параллелизм ограничен **количеством аккаунтов, а не вычислениями.** Десять
параллельных задач на один аккаунт = потеря аккаунта.

### 4.1 SERP как утилита, а не источник

`serp(query) -> [{url, title, snippet}]` — инструмент уровня инфраструктуры,
как `fetch_page`. Используется многими этапами:

| Задача | Запрос |
|---|---|
| Discovery | `"аутсорсинг бухгалтерии" Алматы ТОО -site:2gis.kz` |
| Вакансии | `site:hh.kz "..." "менеджер по продажам" Алматы` |
| Email компании | `"@company.kz"` |
| Кто платит за рекламу | платная выдача по коммерческому запросу |
| Кому нужны клиенты | органика на 2–3 странице |
| ЛПР без LinkedIn | `"директор" "ТОО Ромашка"` |
| ЛПР через LinkedIn | `site:linkedin.com/in "Ромашка" (директор OR коммерческий)` |
| Сигнал потери лидов | `"Ромашка" отзывы -site:company.kz` |

Провайдер: **Serper.dev, $1/1000**. Свой скрейпер Google не строим — прокси,
капчи и вечная борьба ради экономии двух долларов.

Поиск ЛПР через Google вместо LinkedIn-аккаунта: не заходим на LinkedIn вообще,
значит нет нарушения ToS, нет риска бана, нет лимитов поиска. Сниппет обычно уже
содержит имя и должность — на страницу можно не ходить.

### 4.2 Коннекторы

Единый контракт: получают конфиг, отдают сырые записи в `raw.fetches`,
о системе ничего не знают.

## 5. Пайплайн

```
S1  SEED       SERP-discovery + 2GIS + вакансии через SERP
               → core.companies, signals пишутся сразу
                    ↓
S2  RESOLVE    склейка дублей, отсев по kgd-спискам
                    ↓
S3  SITE SCAN  сайт целиком → email, телефоны, CRM, пиксели, формы
                    ↓
S4  CLASSIFY   ОДИН вызов Haiku на компанию: сайт + вакансии + 2GIS → всё сразу
                    ↓
S5  QUALIFY    fit_score по правилам → отсев не-ICP
                    ↓
S6  CONTACTS   корпоративные адреса + классификация типа;
               ЛПР через SERP — опционально, для топа
                    ↓
S7  VERIFY+RANK  проверка каналов, intent_score, агент → why_now
                    ↓
               mart.lead_profiles
```

### S3 — сканирование сайта

**Не угадывать эндпоинты** (`/team`, `/about` — у всех по-разному, часто вообще
одностраничник). Сайты малого бизнеса маленькие, дешевле скачать целиком:

```
1. sitemap.xml → если нет, собрать внутренние ссылки с главной (1 уровень)
2. Лимит 30 страниц, отсечь блог/новости/каталог по паттернам URL
3. Скачать текст всех оставшихся (обычно 5–15 страниц)
4. Сохранить в raw.fetches — LLM здесь НЕ вызывается
```

Пиксели и CRM-виджеты ищутся regex'ом по сырому HTML — они детерминированы,
LLM для них не нужен.

### S4 — один вызов LLM на компанию

К этому моменту собрано всё: текст сайта, тексты вакансий, карточка 2GIS с
отзывами. Всё склеивается в **один промпт** и уходит одним вызовом Haiku
со structured output:

```
вход:  текст сайта (5–15 стр.) + вакансии + карточка 2GIS + отзывы
выход: {industry, size_hint, has_sales_team, people[], phones[], emails[],
        socials[], vacancy_signals[], review_signals[], icp_match, confidence}
```

Почему один, а не пять отдельных вызовов по задачам:
- **связи между источниками видны только в общем контексте** — вакансия
  «менеджер по продажам» + отсутствие CRM на сайте вместе значат больше, чем
  по отдельности
- по токенам дешевле: один системный промпт вместо пяти
- меньше кода, меньше мест для рассинхрона схем

Исключение — нормализация должностей: у неё свой кэш (одна и та же должность
встречается сотни раз), но в v1 она входит в тот же вызов.

### S6 — контакты: приоритет корпоративным адресам

**80–90% работающих писем уходят на общие адреса**, секретарь пересылает ЛПР.
Поэтому поиск имени ЛПР — опциональный бонус, а не обязательный этап.

```
1. Личные ЛПР      director@, ceo@, имя.фамилия@
2. Функциональные  sales@, marketing@, it@   ← классифицировать под оффер
3. Общие           info@, office@             ← это работает
```

Для КЗ телефон из 2GIS — тот же «общий корпоративный канал», попадающий к
нужному человеку через администратора.

## 6. Схема данных

Один Postgres. Три слоя схем.

```sql
CREATE EXTENSION pg_trgm;

-- RAW: сырые ответы, навсегда, никогда не удаляются
raw.fetches(id, source, source_key, fetched_at, payload jsonb, payload_hash)

-- CORE
core.companies(
  company_id   text PRIMARY KEY,   -- 'dom:x.kz' | '2gis:id' | 'bin:...' | 'ig:user'
  bin          text UNIQUE,        -- NULL, если не нашли
  name, name_norm, city, industry, industry_confidence,
  domain, segment_id,
  size_est int, maturity_level,
  stage text, priority int,
  first_seen, updated_at
)

core.company_aliases(              -- склейка дублей из разных источников
  alias_id   text PRIMARY KEY,
  company_id text REFERENCES core.companies,
  match_rule text,                 -- 'domain'|'phone'|'ig'|'trgm_name_city'
  confidence numeric
)

core.contacts(
  contact_id uuid PK, company_id text FK,
  full_name, role_raw, role_normalized, seniority,
  source, source_url, confidence numeric
)

core.channels(                     -- мультиканальность
  channel_id uuid PK,
  company_id text FK, contact_id uuid NULL,
  kind text,                       -- phone|whatsapp|telegram|instagram|email|linkedin
  handle text,                     -- +7701... | @username | mail@x.kz
  addr_type text,                  -- personal|functional|generic  (для email)
  is_corporate bool,
  status text,                     -- valid|invalid|catch_all|unknown|unverified
  confidence numeric,              -- 0..1, НЕ булево
  verified_at, verifier, source_url,
  UNIQUE(kind, handle)
)

core.vacancies(                    -- ключевой intent-источник
  id, company_id text FK,
  title, description_full text,
  published_at, closed_at, city, salary_range, source_url,
  tsv tsvector GENERATED ALWAYS AS
      (to_tsvector('russian', title||' '||description_full)) STORED
)
CREATE INDEX ON core.vacancies USING GIN(tsv);

core.signals(                      -- события с затуханием, НЕ флаги
  id bigserial PK, company_id text FK,
  type text, source text, observed_at timestamptz,
  weight numeric, evidence_url, evidence_quote, payload jsonb
)

-- MART: контракт с Системой №2
mart.lead_profiles(
  company_id, contact_id, segment_id,
  fit_score, intent_score, best_channel,
  why_now text,                    -- обоснование с цитатой и ссылкой
  profile jsonb, built_at
)
```

### Обоснование ключевых решений

**`raw` неприкосновенен.** Нормализация будет меняться еженедельно, а перекачать
данные дорого или невозможно (вакансия закрыта, страница удалена). Сырьё
сохраняется всегда, `core` пересобирается из него сколько угодно раз.

**`signals` — события, не флаги.** Вакансия, опубликованная вчера, и такая же
полугодовой давности — разные лиды. `intent_score` считается на лету:
`Σ(weight × exp(-days_since / half_life))`. Колонка `has_hiring_signal boolean`
через месяц станет незаметной ложью.

**`channels.confidence` — число, не флаг.** Решение «слать или не слать» принимает
Система №3 исходя из здоровья своих доменов. Бинарный `is_valid` эту развилку убивает.

**`telegram` не порождается из `phone`.** Telegram-контакт может быть найден как
`@username` в bio или на сайте, без всякого телефона. Все каналы равноправны и
обнаруживаются независимо.

**`segment_id` — первоклассная сущность.** Разброс конверсии между сегментами
достигает двух раз (12,4% против 17,5% в известных кейсах). Сегменты запускаются
и меряются отдельно.

**`core.companies` глобальная, ICP-матчинг на клиента.** Два клиента таргетят одну
компанию → обогащаем один раз. Каждый следующий клиент дешевле предыдущего, а база
со временем становится активом, который нельзя отобрать сменой чужой API-политики.

## 7. Identity Resolution

Одна компания приходит из 3–4 источников под разными идентификаторами. Без склейки
получим дубли и напишем одному человеку трижды.

Правила по убыванию точности:

| Правило | Надёжность |
|---|---|
| Домен (после нормализации) | точно |
| Телефон (E.164) | почти точно — в КЗ номер редко делят два бизнеса |
| БИН | точно, если найден |
| Instagram username ↔ ссылка на сайте/в 2GIS | точно |
| `similarity(name_norm) > 0.8` **в пределах города** | нечётко → ручная проверка |

LLM здесь не нужен: правила точнее и дешевле.

## 8. Скоринг

Две независимые оси, **обе по правилам, не ИИ** — клиенту придётся объяснять,
почему выбран этот лид, а чёрный ящик объяснить нельзя.

**`fit_score`** — соответствие ICP: отрасль, город, размер, наличие сайта,
не в чёрном списке.

**`intent_score`** — нужна ли лидогенерация сейчас:

| Сигнал | Смысл | Вес |
|---|---|---|
| Вакансия «менеджер по продажам» (текст!) | Не хватает клиентов | **высокий** |
| Вакансия висит 60+ дней | Пытались решить наймом, не смогли | **высокий** |
| Рост числа вакансий за квартал | Компания растёт | высокий |
| Google Ads / Яндекс.Директ | Платят за лиды | высокий |
| Bitrix24 / amoCRM виджет | Есть отдел продаж и процесс | высокий |
| Отзывы «не дозвонились», «не ответили на заявку» | Теряют оплаченные лиды | высокий |
| Форма заявки, WhatsApp-виджет | Ждут входящих | средний |
| Каталог услуг, прайс на сайте | Готовы к продажам | низкий |

**Нет сигналов ≠ отрицательный вес.** Для B2B компания без рекламы, но с CRM и
пятью менеджерами — лучший лид из возможных: есть люди, которым нечего обзванивать.

**Недоступно в КЗ:** рост выручки (реестр закрыт, `dfo.kz` только крупняк).
Замена — рост числа вакансий, новые филиалы в 2GIS.

## 9. Где ИИ, где агенты

Правило: **ИИ извлекает и классифицирует. Правила решают.**

| Задача | Решение |
|---|---|
| Фильтры, дедупликация, скоринг | SQL / правила |
| Верификация каналов | SMTP / MX / детерминированные проверки |
| Пиксели, CRM-виджеты, соцсети | regex по сырому HTML |
| **Всё извлечение из текста** — отрасль, размер, люди и роли, нормализация должностей, сигналы из вакансий, сигналы из отзывов | **ОДИН вызов Haiku на компанию** (этап S4), structured output |
| `why_now` для топовых лидов | **Агент**, только топ |

Ровно два обращения к модели на компанию: один вызов Haiku на всех, один
агент — на выживших. Никаких «по вызову на задачу»: пять отдельных вызовов
стоят дороже, теряют связи между источниками и дают пять схем вместо одной.

### Агент — один на компанию, не по одному на канал

```
ОДИН агент, каналы = его инструменты:
  serp, fetch_site, get_2gis_card, get_vacancies, get_instagram_profile
Параллелизм ПО КОМПАНИЯМ, не по каналам внутри компании.
```

Почему не N агентов на N каналов:
1. **Браузерные аккаунты** — 10 параллельных агентов на один аккаунт = бан в первый час
2. **Стоимость** — 4 агента × 1500 компаний ≈ $780 против ~$54 у парсера + 1 вызова Haiku
3. **Каналы зависимы последовательно** — SERP → сайт → телефон → WhatsApp;
   параллелить нечего, агенты будут ждать друг друга или работать вслепую
4. **Дублирование** — независимые агенты трижды скачают одну главную страницу
5. **Невоспроизводимость** — скоринг на недетерминированных данных нельзя отладить

Агент стоит ~$0.13 на компанию. В бюджете он заложен на **топ-300** (~$40) —
не потому, что дороже нельзя, а потому что на остальных `why_now` не нужен: им
всё равно не будут писать в этом цикле. Прогнать всю базу в 1500 компаний стоило
бы ~$195 — допустимо, если понадобится.

## 10. Оркестрация

**Postgres как очередь**, `FOR UPDATE SKIP LOCKED`. Стадия — состояние в строке,
воркер на стадию, `attempts` + `next_retry_at` + `last_error`.

Не Airflow, не Temporal, не n8n. n8n отдельно: хорош для демо и первых двух
клиентов, но не версионируется по-человечески, теряет элементы на батчах и
становится нечитаемым на 40+ нодах.

```
# ponytail: Postgres-очередь. При >1M компаний/мес или ветвящихся workflow → Temporal.
```

**Две раздельные очереди с разной скоростью:**

| Очередь | Что | Темп |
|---|---|---|
| Медленная | Всё браузерное и авторизованное: 2GIS, hh, Instagram | 1 воркер на профиль, паузы, circuit breaker |
| Быстрая | SERP, сканер сайтов, LLM, верификация, скоринг | параллельно, без ограничений |

Смешивать нельзя: один агрессивный воркер в медленной очереди стоит аккаунта.

**Rate limiting на источник** — токен-бакет. Один жадный воркер выносит доступ
ко всем источникам сразу.

## 11. Каналы связи

Что собирать и в каком приоритете (для ICP «бизнес-услуги, КЗ»):

```
channel_priority:        ["whatsapp", "email", "phone", "linkedin", "telegram"]
require_at_least_one_of: ["whatsapp", "phone", "email"]
```

Лид считается **готовым**, только если у него есть канал из тех, которыми реально
пользуются. Компания с прекрасным score, но без единого рабочего канала — это не
лид, а мусор в отчёте.

Почему телефон стоит выше LinkedIn, а не в конце списка:
- **cold calling в Казахстане жив** и остаётся рабочим каналом для B2B
- 2GIS отдаёт телефон практически всегда — это канал с максимальным покрытием,
  то есть страховка на случай, когда ни email, ни WhatsApp не нашлись
- один номер даёт и WhatsApp, и звонок; это два канала за одно обнаружение

`telegram` в списке последним не потому, что слаб, а потому что найти его труднее:
он обнаруживается как `@username` в bio, на сайте или в контактах, независимо от
телефона (см. §6). Когда найден — работает; систематически его добыть нельзя.

Проверенные ограничения платформ (август 2026):

| Канал | Ограничение |
|---|---|
| WhatsApp | ~60 новых диалогов/день до бана. Cloud API — только opt-in и шаблоны |
| Email | 50 писем/день на аккаунт. Единственный канал, где холодный первый контакт легален по дизайну платформы |
| LinkedIn | 100 connection requests/неделю, у новых аккаунтов 20–30 |
| Instagram DM | API инициировать диалог не позволяет; вручную работает |
| Telegram | `Telethon` архивирован 02.2026; массовый `importContacts` — триггер бана |
| Телефон | Cold calling в КЗ жив и работает |

Для v1 отправка **ручная** — WhatsApp Web, почта, руками. 30–50 сообщений это час
работы. Никаких API, никакого opt-in-контура, ноль риска бана номера.

```
# ponytail: ручная отправка. WhatsApp Cloud API — при >500 лидов/мес и наличии
#           opt-in контура. Не раньше.
```

## 12. Юридический контур

Закон РК №94-V «О персональных данных и их защите»:
- ФИО + должность + рабочий контакт = персональные данные
- **отдельное согласие требуется именно на рекламную рассылку**
- штрафы для юрлиц выросли до 10 000 МРП (~40 млн ₸)
- уведомление регулятора об утечке в течение 72 часов

Практические следствия для архитектуры:
1. **`suppression_list`** — глобальная таблица, проверяется до каждого касания,
   никогда не очищается. Отписки, жалобы, hard bounce, ручные исключения.
2. Индивидуальная деловая переписка вручную ≠ рекламная рассылка. Автоматическая
   рассылка по базе — уже рассылка со всеми требованиями 94-V. Это ещё одна причина
   держать v1 ручной.
3. Локализация хранения в РК — закон допускает трансграничную передачу (ст. 16),
   жёсткого требования по типу российского 152-ФЗ не подтверждено. **Тема спорная,
   нужен юрист перед продажей услуги клиентам.**

## 14. Критерий готовности v1

> **v1 готова, когда выдала 30 компаний Казахстана из отрасли «бизнес-услуги»
> с проверенным каналом связи и обоснованием `why_now` — и с ними начата переписка.**

Всё, что не приближает к этим 30 компаниям, в v1 не входит: мультитенантность,
второй ICP, РФ, UI, автоматическая отправка, Instagram, Ad Library.

Реакция живых людей переопределит половину весов скоринга. Любая работа, сделанная
до первых ответов, — работа вслепую.

### Порядок реализации

1. Postgres + схема + SERP-утилита (Serper)
2. Коннектор вакансий: SERP → прямые URL hh → тексты → FTS
3. Сканер сайтов на Scrapling: email, телефоны, CRM, пиксели
4. LLM-классификатор + правила скоринга
5. Выгрузка топ-30 → ручная переписка
6. 2GIS-коннектор — после того, как первые три покажут, чего не хватает

## Приложение А. Проверено и отвергнуто

Чтобы через месяц не вернуться к тем же идеям. Все проверки — август 2026.

### Источники

| Идея | Почему отвергнута |
|---|---|
| `api.hh.ru` /vacancies, /employers | **403 подтверждён** живым curl. С самодельным UA — `bad_user_agent: blacklisted`. Закрыт с 2025 |
| Прямой скрейп поиска `hh.kz` | **DataDome** + `robots.txt: Disallow: *?*`. Обходится только через Google (см. §3) |
| Дамп реестра юрлиц КЗ | `stat.gov.kz` перенёс поиск по БИН **в личный кабинет**, публичного дампа нет. Аналога ЕГРЮЛ-выгрузки не существует |
| Публичная бухотчётность (аналог `bo.nalog.ru`) | `dfo.kz` покрывает только «организации публичного интереса» — крупняк. Наш ICP (10–200 чел.) там отсутствует |
| **Meta Ad Library API** | Покрывает **только политическую/социальную рекламу** глобально + все типы только для EU/UK. Для КЗ коммерческой рекламы не отдаёт. Живой запрос → `OAuthException`, HTTP 500 |
| Meta Ad Library веб | **403** на прямой запрос даже с браузерным UA. Доступен только реальным браузером, серая зона ToS |
| Госзакупки `goszakup.gov.kz` | API бесплатный и рабочий, но в КЗ **мало кто участвует** — выборка нерепрезентативна для нашего ICP |
| 2GIS API | Публичного прайса нет, только калькулятор через sales. Браузерный скрейп даёт то же бесплатно |
| `job.kz`, `rabota.nur.kz`, `headhunter.kz` | Мертвы физически (connection refused / DNS не резолвится) |
| `enbek.kz` | `robots.txt` прямо запрещает `/search/*` |
| `flamp.ru`, `olx.kz` | 403 на первом же запросе |
| Контур.Компас, СПАРК, СБИС, 2GIS.Data | Только РФ. **В КЗ аналога не существует** |
| Apollo.io, ZoomInfo | Слабое покрытие Казахстана |
| Свой скрейпер Google | Serper.dev стоит $1/1000. Прокси и капчи ради экономии $2 |

### Архитектурные решения

| Идея | Почему отвергнута |
|---|---|
| **N параллельных агентов по каналам** | ×100 стоимость, конфликт с браузерными аккаунтами (10 сессий на 1 аккаунт = бан), каналы зависимы последовательно, дублирование работы, невоспроизводимость. Заменено на 1 агента на компанию с каналами-инструментами |
| Поиск ЛПР через LinkedIn-аккаунт | Риск бана аккаунта, нужного для продаж. Заменено на Google dorks — не заходим на LinkedIn вообще |
| Обязательный поиск имени ЛПР | 80–90% работающих писем идут на `info@`, секретарь пересылает. Понижено до опции для топа |
| Угадывание `/team`, `/about` | У сайтов малого бизнеса структура непредсказуема. Заменено на скачивание сайта целиком (5–15 страниц) |
| ICP из B2C-отраслей (клиники, риелторы, онлайн-школы, e-com) | Им нужен inbound, а не outbound по компаниям. Система нашла бы их, но продукт для них произвести не смогла бы |
| Телефон как родитель для Telegram | Telegram-контакт бывает `@username` без телефона. Каналы равноправны |
| Отдельный вызов LLM на каждую задачу (отрасль / команда / вакансии / отзывы) | Дороже, теряет связи между источниками (вакансия + отсутствие CRM значат вместе больше, чем порознь), пять схем вместо одной. Заменено на один вызов на компанию в S4 |
| Скоринг через LLM | Недетерминирован, неотлаживаем, необъясним клиенту. Только правила |
| Kafka / Airflow / Temporal / n8n | Избыточно для 1000–2000 компаний. Postgres-очередь = ~150 строк |
| Векторная БД / RAG | Нечего искать семантически. `pg_trgm` закрывает нечёткое сопоставление имён |
| Микросервисы, real-time, свой UI | Один репозиторий, батчи раз в сутки, Metabase поверх Postgres |

### Каналы

| Идея | Почему отвергнута |
|---|---|
| Instagram DM cold через API | Meta не позволяет бизнесу инициировать диалог — ни через API, ни через ManyChat. Вручную работает |
| WhatsApp cold без opt-in | Прямо запрещено политикой WhatsApp, не просто рискованно |
| Telegram массовая рассылка | `Telethon` архивирован 02.2026; `importContacts` в объёме — триггер бана номера |
| LinkedIn connection-автоматизация | Кап 100/неделю, у новых аккаунтов 20–30. Прямое нарушение ToS |
| WhatsApp Cloud API для v1 | Не нужен при 30–50 лидах. Ручная отправка проще, дешевле и юридически чище |
