# Часть I. Что строим

## 1. Назначение и границы

Система находит B2B-компании в Казахстане, обогащает их данными и сигналами и
выдаёт готовые профили лидов: кто, по какому каналу с ними связаться и почему им
нужна лидогенерация именно сейчас.

**Что вне этого документа.** Это Система №1 из трёх. Система №2 (AI-персонализация
сообщений) и Система №3 (инфраструктура доставки) описываются отдельно. Здесь
фиксируется только то, какие идентификаторы и сигналы собирать, чтобы №2 и №3 могли
работать.

**Первый пользователь системы — её автор.** Цель v1 — найти клиентов на услуги
AI-лидогенерации и превратить сам процесс в кейс. Платящего клиента на момент
проектирования нет.

---

## 2. ICP

### 2.1 География и тип бизнеса

**География:** Казахстан, Алматы + Астана. РФ — не раньше, чем КЗ заработает полностью.

**Тип бизнеса:** компании, которые **сами продают B2B**.

> **Почему не B2C-отрасли.** Клиники, риелторы, онлайн-школы и e-com легче продать,
> но им нужен inbound (реклама, SEO), а не outbound по компаниям. Система нашла бы
> их, но не смогла бы произвести то, что им продаётся. При выборе «сами продают B2B»
> одна система работает и для нас, и для клиента — мы продаём ровно то, чем
> пользуемся сами, и кейс не разваливается на исполнении.

### 2.2 Отрасль v1 — бизнес-услуги

| Сегмент | ~компаний (Алматы+Астана) |
|---|---|
| Бухгалтерский аутсорс | 800–1 500 |
| Юридический аутсорс для компаний | 500–1 000 |
| HR / рекрутинг / аутстаффинг | 200–400 |
| IT-аутсорс, сисадмин, 1С | 300–600 |
| Консалтинг, аудит, налоговый | 300–500 |
| Клининг / охрана / АХО-аутсорс | 500–1 000 |

**Итого ~2 500–5 000 → после фильтров ~1 000–1 500.**

Три причины, по которым отрасль сильная:

1. **Та же бизнес-модель, что у нас** — B2B-услуга по подписке. Одинаковый цикл,
   одинаковые возражения, разговор на одном языке.
2. **Они уже делают outbound руками** — холодный обзвон их основной канал. Продаём
   не идею, а замену ручного труда: самый лёгкий разговор из возможных.
3. **Вакансия «менеджер по продажам» = прямое признание нехватки клиентов.**

### 2.3 Фильтры и чёрный список

```
geo:      Алматы, Астана
size:     10–200 сотрудников
must:     есть сайт
exclude:  госсектор, монополии, микро (<5 чел), маркетинговые агентства
```

**Чёрный список:** SMM- и маркетинговые агентства, лидген-подрядчики, таргетологи —
прямые конкуренты. Отсеиваются автоматически по рубрике 2GIS, не вручную.

## 3. Масштаб и воронка

```
1 000–1 500 компаний в базе
   → 50 писем/день с одного почтового аккаунта
   → цепочка из 5 писем = 200 компаний/мес на аккаунт
   → reply rate 8–15 %
   → лидов 2–5 %
   → 20–40 лидов → 2–4 сделки за полгода
```

Калибровка по реальным цифрам отрасли (Respondo, десятки проектов).

> **Оговорка: это email-воронка с российского рынка.** В Казахстане WhatsApp даёт
> больший объём при том же ручном труде — ~60 новых диалогов в день против 50 писем,
> то есть ~1 200/мес против 200/мес на аккаунт. Реальная воронка КЗ будет
> мультиканальной, но её конверсию мы узнаем только после первых 30 лидов, поэтому
> планируем по консервативной email-цифре.

**Ключевое следствие:** целевой масштаб — **тысячи компаний, не сотни тысяч.**
Отсюда всё остальное: Postgres на одной машине, никакого шардирования, никаких
преждевременных оптимизаций, дорогой агент можно пускать хоть на всю базу.

**Верхняя граница пропускной способности:** ~60 новых диалогов WhatsApp в день,
50 писем/день на почтовый аккаунт. Выдавать больше 50–60 готовых лидов в день
бессмысленно — их некуда девать.

---

## 4. Критерий готовности v1

> **v1 готова, когда выдала 30 компаний Казахстана из отрасли «бизнес-услуги» с
> проверенным каналом связи и обоснованием `why_now` — и с ними начата переписка.**

Не входит в v1: мультитенантность, второй ICP, РФ, UI, автоматическая отправка,
Instagram, Ad Library.

Реакция живых людей переопределит половину весов скоринга. Любая работа, сделанная
до первых ответов, — работа вслепую.

# Часть II. Как строим

## 5. Общая схема

```
┌─ ИСТОЧНИКИ ─────────────────────────────────────────────┐
│    2GIS         hh.kz напрямую   SERP (Serper)  сайты   │
│       │                │             │          │       │
└───────┼────────────────┼─────────────┼──────────┼───────┘
        │                │             │          │
        ▼                ▼             ▼          ▼
   ┌──────────────────────────────────────────────────┐
   │  raw.fetches — сырые ответы, навсегда            │
   └──────────────────────┬───────────────────────────┘
                          ▼
   ┌──────────────────────────────────────────────────┐
   │  S1 SEED → S2 RESOLVE → S3 SCAN → S4 CLASSIFY    │
   │  → S5 QUALIFY → S6 CONTACTS → S7 VERIFY+RANK     │
   └──────────────────────┬───────────────────────────┘
                          ▼
   ┌──────────────────────────────────────────────────┐
   │  core.companies · contacts · channels            │
   │  core.vacancies (FTS) · core.signals             │
   └──────────────────────┬───────────────────────────┘
                          ▼
              mart.lead_profiles  →  Система №2
```

Сквозная подсистема одна — **SERP-утилита** (§7.2). **Браузерный пул** (§7.1) в v1 не
задействован: все источники берутся обычным HTTP.

## 6. Источники данных

### 6.1 Основные

| Источник | Роль | Доступ | Цена |
|---|---|---|---|
| **2GIS** | Охват, рубрики, адреса + телефон, сайт, email, Instagram, WhatsApp | HTTP + cookie, SSR-стейт | **0** |
| **hh.kz** | Intent: тексты вакансий | HTTP с TLS-impersonation, JSON-LD | **0** |
| **SERP** (Serper.dev) | Утилита: ЛПР, добор компаний вне 2GIS, email по домену | API | **$1 / 1 000 запросов** |
| **Сканер сайтов** | CRM, пиксели, признаки продаж | Scrapling | 0 |

Ни одному источнику v1 не нужен реальный браузер, аккаунт или прокси. Детали доступа,
URL-схемы и пути внутри ответов — в [спеке коннекторов](docs/superpowers/specs/2026-08-06-connectors-design.md).

### 6.2 2GIS — охват и контакты одним источником

2GIS отдаёт серверный рендеринг: весь стейт приложения лежит в HTML как
`var initialState = JSON.parse('...')`. Обычного HTTP-запроса с одной cookie
`dg5_museum_accept=true` достаточно — ни браузера, ни аккаунта, ни ключа API.

```
/{city}/rubrics                     → дерево рубрик
/{city}/rubrics/subrubrics/{id}     → ветка вглубь
/{city}/rubric/{id}/page/{n}        → 12 организаций, total, pages
/{city}/firm/{branch_id}            → контакты
```

**Рубрика — это машинный эквивалент сегмента из §2.2.** У 2GIS есть верхнеуровневая
рубрика «B2B-услуги» (`110609`), внутри неё «Бизнес-услуги» (`110613`) с 24 листовыми
рубриками: `653` Бухгалтерские услуги, `339` Аудиторские, `638` Регистрация и ликвидация,
`1236` Финансовый консалтинг, `1238` Управленческий консалтинг, `22129` Call-центры и
другие. Юридические, HR, IT-аутсорс и клининг лежат в соседних ветках `110565` и `110616`.

Отсюда три следствия:

- `segment_id` из §9.2 — это буквально id рубрики 2GIS, придумывать сегменты не нужно
- чёрный список §2.3 — тоже список id: `110611` «Реклама» и есть ветка прямых конкурентов
- перечисление по рубрике даёт **полный список категории**, а не выдачу по релевантности

**Карточка филиала отдаёт весь набор каналов сразу** — телефон, сайт, email, Instagram,
WhatsApp. Это закрывает `require_at_least_one_of` из §13 одним источником и делает 2GIS
не «источником охвата и телефонов», а самым дешёвым источником готовых контактов.

Дополнительно из списка: `org.id` (компания, а не филиал), `org.branch_count`,
`reviews.general_rating` и `general_review_count`, правовая форма в `org.name`.

**Потолок пагинации — 60 организаций на рубрику на город.** 2GIS отдаёт максимум 5
страниц по 12: с шестой возвращается `HTTP 200` с содержимым **первой** страницы, а
`total` и `pages` продолжают обещать больше (рубрика `653` заявляет 670 и 56). Признак
подмены один — поле `currentPage`. Проверено на трёх рубриках, граница везде одна.

**Отсюда главное следствие для охвата: база набирается числом рубрик и городов, а не
глубиной пагинации.** 25 рубрик ветки «Бизнес-услуги» × 60 × два города ≈ до 3 000
организаций — это попадает в целевые 1 000–1 500 после фильтров, но запаса не даёт.
Резерв, если понадобится: в стейте есть фильтр `spatial.districts` (8 районов Алматы),
срез по районам поднимает потолок примерно в 8 раз. URL-форма фильтра не выяснена.

**Ограничений по темпу не обнаружено:** 15 запросов подряд без пауз — все `200`, ни
капчи, ни `429`.

### 6.3 hh.kz — intent напрямую, Google не нужен

`api.hh.ru` закрыт (403). Но сам сайт доступен: `robots.txt` в секции `User-agent: *`
содержит `Disallow: *?*` — запрещена **строка запроса**, а не поиск. У hh есть SEO-урлы
без параметров, и под запрет они не попадают.

```
{city}.hh.kz/vacancies/{slug}   → 50 id вакансий на странице
hh.kz/vacancy/{id}              → JSON-LD JobPosting: title, employer,
                                  datePosted, description
```

Голый HTTP-клиент получает здесь `403` — дело в TLS-отпечатке, а не в интерактивном
челлендже. `Fetcher.get(impersonate='chrome')` из Scrapling проходит.

Вакансия отдаёт `<script type="application/ld+json">` с готовым объектом `JobPosting` —
это напрямую `core.vacancies` (§9.1), своего парсера HTML не требуется.

**Ограничение:** 50 вакансий на slug без нарушения `robots.txt`. Глубже — только через
`?page=N`, что `Disallow: *?*` запрещает. Решается, когда 50 окажется мало.

> **Зачем это нужно.** Поиск **по тексту** вакансии — киллер-фича Контур.Компаса,
> дающая в кейсах reply rate 8–20 % против обычных 3–5 %. Не «компания нанимает», а
> «компания в тексте вакансии описала ровно ту проблему, которую я решаю».

> **В Казахстане нет Контур.Компаса и купить его негде.** Российский лидген стоит на
> готовой базе с фильтрами по ОКВЭД, выручке и вакансиям. В КЗ этой инфраструктуры не
> существует. Мы не строим обвязку вокруг чужой базы — мы строим отсутствующую на
> рынке инфраструктуру данных. Это и есть актив.

### 6.4 LinkedIn — активный источник, но только через Google

Для бизнес-услуг в Алматы/Астане LinkedIn живой (оценка владельца проекта), поэтому
он **не в резерве** — это рабочий источник имён ЛПР на этапе S6. Доступ только через
SERP-выдачу:

```
site:linkedin.com/in "Ромашка" (директор OR коммерческий)
```

**Для сбора данных** аккаунт LinkedIn не нужен вообще: сниппет Google обычно уже
содержит имя и должность, на страницу заходить не приходится. Нет нарушения ToS, нет
риска бана, нет лимитов поиска.

**Для отправки** аккаунт, разумеется, нужен — но это Система №3, и она использует
личный аккаунт, который остаётся чистым именно потому, что мы им ничего не скрейпим.
Лимиты отправки — в §13.

### 6.5 Резерв

Не используется в v1, пригодится при смене ICP или если основных не хватит.

| Источник | Когда пригодится |
|---|---|
| Instagram | B2C-отрасли, HoReCa-поставщики, e-com |
| Meta Ad Library (веб, браузером) | Отрасли, рекламирующиеся в Meta |
| satu.kz / flagma.kz | Оптовая торговля, дистрибуция |
| kgd.gov.kz списки | Фильтр качества: лжепредприятия, банкроты, недоимщики (бесплатные годовые дампы) |
| statsnet.co API | Финансы и руководитель по БИН, от 4 990 ₸/мес |

## 7. Инфраструктурные слои

### 7.1 Браузерный пул

**В v1 не используется.** Проверка августа 2026 показала, что ни 2GIS, ни hh реального
браузера не требуют: 2GIS берётся обычным HTTP с одной cookie (§6.2), hh — HTTP с
TLS-impersonation (§6.3). Пул остаётся описанным здесь ради источников резерва (§6.5),
прежде всего Instagram, где авторизация обязательна.

Когда понадобится: профиль на источник, ручной логин один раз, персистентный
`user_data_dir`.

```
profiles/
  instagram/   StealthySession(real_chrome=True, user_data_dir=...)   (резерв, уже настроен)
```

**Правила:**
- один источник = один профиль = один аккаунт, **не смешивать** (бан не должен
  утаскивать соседей)
- человеческий темп: рандом 3–8 с между страницами
- резидентный прокси KZ на профиль
- circuit breaker: 3 подряд challenge → профиль на паузу + алерт

> **Ограничение браузерных источников.** Реальный браузер с человеческим темпом даёт
> **200–400 страниц в час на профиль**, и параллелизм упирается в количество аккаунтов,
> а не в вычисления: десять параллельных задач на один аккаунт = потеря аккаунта.
>
> **К источникам v1 это не относится.** Они ходят обычным HTTP, лимитов на них не
> обнаружено, и узким местом остаётся только сеть.

### 7.2 SERP-утилита

`serp(query) -> [{url, title, snippet}]` — инструмент уровня инфраструктуры, как
`fetch_page`. Используется многими этапами:

| Задача | Запрос |
|---|---|
| Добор компаний вне 2GIS | `"аутсорсинг бухгалтерии" Алматы ТОО -site:2gis.kz` |
| Email компании | `"@company.kz"` |
| Кто платит за рекламу | платная выдача по коммерческому запросу |
| Кому нужны клиенты | органика на 2–3 странице |
| ЛПР без LinkedIn | `"директор" "ТОО Ромашка"` |
| ЛПР через LinkedIn | `site:linkedin.com/in "Ромашка" (директор OR коммерческий)` |
| Сигнал потери лидов | `"Ромашка" отзывы -site:company.kz` |

**Провайдер: Serper.dev, $1/1 000.** Свой скрейпер Google не строим — прокси, капчи и
вечная борьба ради экономии двух долларов.

### 7.3 Коннекторы

Единый контракт: получают конфиг, отдают сырые записи в `raw.fetches`, о системе
ничего не знают. Единственная абстракция, которую документ допускает, — при четырёх
с лишним реализациях она себя окупает.

## 8. Пайплайн

| Этап | Что делает | Выход |
|---|---|---|
| **S1 SEED** | 2GIS по рубрикам + вакансии с hh + SERP-добор | `core.companies`, `signals` пишутся сразу |
| **S2 RESOLVE** | Склейка дублей, отсев по kgd-спискам | `company_aliases` |
| **S3 SCAN** | Скачивание сайта целиком | `raw.fetches`, regex-сигналы |
| **S4 CLASSIFY** | **Один вызов `gpt-5.4-mini` на компанию** | структурированный профиль |
| **S5 QUALIFY** | `fit_score` по правилам → отсев не-ICP | стадия `qualified` |
| **S6 CONTACTS** | Корпоративные адреса + классификация; ЛПР опционально | `contacts`, `channels` |
| **S7 VERIFY+RANK** | Проверка каналов, `intent_score`, агент → `why_now` | `mart.lead_profiles` |

Три этапа заслуживают детализации.

### 8.1 S3 — сканирование сайта

**Не угадывать эндпоинты.** `/team`, `/about` у всех называются по-разному
(`/o-nas`, `/komanda`, `/nashi-specialisty`), а часто сайт вообще одностраничный.
Сайты малого бизнеса маленькие — дешевле скачать целиком:

```
1. sitemap.xml → если нет, собрать внутренние ссылки с главной (1 уровень)
2. Лимит 30 страниц, отсечь блог/новости/каталог по паттернам URL
3. Скачать текст всех оставшихся (обычно 5–15 страниц)
4. Сохранить в raw.fetches — LLM здесь НЕ вызывается
```

Пиксели и CRM-виджеты ищутся regex'ом по сырому HTML — они детерминированы, LLM для
них не нужен.

### 8.2 S4 — единственный вызов LLM

К этому моменту собрано всё: текст сайта, тексты вакансий, карточка 2GIS с отзывами.
Всё склеивается в **один промпт** и уходит одним вызовом `gpt-5.4-mini` со structured
output (`response_format: json_schema`, `strict: true`):

```
вход:  текст сайта (5–15 стр.) + вакансии + карточка 2GIS + отзывы
выход: {industry, size_hint, has_sales_team, people[], phones[], emails[],
        socials[], vacancy_signals[], review_signals[], icp_match, confidence}
```

> **Почему один вызов, а не пять по задачам.**
> - **Связи между источниками видны только в общем контексте** — вакансия «менеджер
>   по продажам» плюс отсутствие CRM на сайте вместе значат больше, чем порознь.
> - Дешевле по токенам: один системный промпт вместо пяти.
> - Меньше кода и меньше мест для рассинхрона схем.

Исключение — нормализация должностей: у неё свой кэш (одна и та же должность
встречается сотни раз), но в v1 она входит в тот же вызов.

### 8.3 S6 — контакты: приоритет корпоративным адресам

**80–90 % работающих писем уходят на общие адреса**, секретарь пересылает ЛПР.
Поэтому поиск имени ЛПР — опциональный бонус, а не обязательный этап.

```
1. Личные ЛПР      director@, ceo@, имя.фамилия@
2. Функциональные  sales@, marketing@, it@    ← классифицировать под оффер
3. Общие           info@, office@             ← это работает
```

Для КЗ телефон из 2GIS — тот же «общий корпоративный канал», попадающий к нужному
человеку через администратора.

## 9. Модель данных

Один Postgres. Три схемы: `raw` (сырьё) → `core` (нормализованное) → `mart` (витрина).

### 9.1 Схема

```sql
CREATE EXTENSION pg_trgm;

-- ─── RAW: сырые ответы, навсегда, никогда не удаляются ───
raw.fetches(id, source, source_key, fetched_at, payload jsonb, payload_hash)

-- ─── CORE ───
core.companies(
  company_id   text PRIMARY KEY,   -- 'dom:x.kz' | '2gis:id' | 'bin:...' | 'ig:user'
  bin          text UNIQUE,        -- NULL, если не нашли
  name, name_norm, city, industry, industry_confidence,
  domain, segment_id,
  size_est int, maturity_level,
  stage text, priority int,
  first_seen, updated_at
)

core.company_aliases(              -- склейка дублей из разных источников
  alias_id   text PRIMARY KEY,
  company_id text REFERENCES core.companies,
  match_rule text,                 -- 'domain'|'phone'|'ig'|'trgm_name_city'
  confidence numeric
)

core.contacts(
  contact_id uuid PK, company_id text FK,
  full_name, role_raw, role_normalized, seniority,
  source, source_url, confidence numeric
)

core.channels(                     -- мультиканальность
  channel_id uuid PK,
  company_id text FK, contact_id uuid NULL,
  kind text,                       -- phone|whatsapp|telegram|instagram|email|linkedin
  handle text,                     -- +7701... | @username | mail@x.kz
  addr_type text,                  -- personal|functional|generic  (для email)
  is_corporate bool,
  status text,                     -- valid|invalid|catch_all|unknown|unverified
  confidence numeric,              -- 0..1, НЕ булево
  verified_at, verifier, source_url,
  UNIQUE(kind, handle)
)

core.vacancies(                    -- ключевой intent-источник
  id, company_id text FK,
  title, description_full text,
  published_at, closed_at, city, salary_range, source_url,
  tsv tsvector GENERATED ALWAYS AS
      (to_tsvector('russian', title||' '||description_full)) STORED
)
CREATE INDEX ON core.vacancies USING GIN(tsv);

core.signals(                      -- события с затуханием, НЕ флаги
  id bigserial PK, company_id text FK,
  type text, source text, observed_at timestamptz,
  weight numeric, evidence_url, evidence_quote, payload jsonb
)

-- ─── MART: контракт с Системой №2 ───
mart.lead_profiles(
  company_id, contact_id, segment_id,
  fit_score, intent_score, best_channel,
  why_now text,                    -- обоснование с цитатой и ссылкой
  profile jsonb, built_at
)
```

### 9.2 Обоснование ключевых решений

| Решение | Почему |
|---|---|
| **`raw` неприкосновенен** | Нормализация будет меняться еженедельно, а перекачать данные дорого или невозможно (вакансия закрыта, страница удалена). Сырьё сохраняется всегда, `core` пересобирается из него сколько угодно раз |
| **`signals` — события, не флаги** | Вакансия вчерашняя и полугодовой давности — разные лиды. `intent_score` считается на лету: `Σ(weight × exp(-days_since / half_life))`. Колонка `has_hiring_signal boolean` через месяц станет незаметной ложью |
| **`channels.confidence` — число, не флаг** | Решение «слать или не слать» принимает Система №3 исходя из здоровья своих доменов. Бинарный `is_valid` эту развилку убивает |
| **`telegram` не порождается из `phone`** | Telegram-контакт бывает найден как `@username` в bio или на сайте, без всякого телефона. Все каналы равноправны и обнаруживаются независимо |
| **`segment_id` — первоклассная сущность** | Разброс конверсии между сегментами достигает двух раз (12,4 % против 17,5 % в известных кейсах). Сегменты запускаются и меряются отдельно |
| **`core.companies` глобальная** | Два клиента таргетят одну компанию → обогащаем один раз. Каждый следующий клиент дешевле предыдущего, а база со временем становится активом, который нельзя отобрать сменой чужой API-политики |

### 9.3 Identity resolution

Одна компания приходит из 3–4 источников под разными идентификаторами. Без склейки
получим дубли и напишем одному человеку трижды.

| Правило | Надёжность |
|---|---|
| Домен (после нормализации) | точно |
| Телефон (E.164) | почти точно — в КЗ номер редко делят два бизнеса |
| БИН | точно, если найден |
| Instagram username ↔ ссылка на сайте / в 2GIS | точно |
| `similarity(name_norm) > 0.8` **в пределах города** | нечётко → ручная проверка |

LLM здесь не нужен: правила точнее и дешевле.

## 10. Скоринг

Две независимые оси, **обе по правилам, не ИИ** — клиенту придётся объяснять, почему
выбран этот лид, а чёрный ящик объяснить нельзя.

**`fit_score`** — соответствие ICP: отрасль, город, размер, наличие сайта, не в
чёрном списке.

**`intent_score`** — нужна ли лидогенерация сейчас:

| Сигнал | Смысл | Вес |
|---|---|---|
| Вакансия «менеджер по продажам» (по тексту!) | Не хватает клиентов | **высокий** |
| Вакансия висит 60+ дней | Пытались решить наймом, не смогли | **высокий** |
| Рост числа вакансий за квартал | Компания растёт | высокий |
| Google Ads / Яндекс.Директ | Платят за лиды | высокий |
| Bitrix24 / amoCRM виджет | Есть отдел продаж и процесс | высокий |
| Отзывы «не дозвонились», «не ответили на заявку» | Теряют оплаченные лиды | высокий |
| Форма заявки, WhatsApp-виджет | Ждут входящих | средний |
| Каталог услуг, прайс на сайте | Готовы к продажам | низкий |

**Нет сигналов ≠ отрицательный вес.** Для B2B компания без рекламы, но с CRM и пятью
менеджерами — лучший лид из возможных: есть люди, которым нечего обзванивать.

**Недоступно в КЗ:** рост выручки (реестр закрыт, `dfo.kz` только крупняк). Замена —
рост числа вакансий, новые филиалы в 2GIS.

## 11. Границы ИИ

Правило: **ИИ извлекает и классифицирует. Правила решают.**

| Задача | Решение |
|---|---|
| Фильтры, дедупликация, скоринг | SQL / правила |
| Верификация каналов | SMTP / MX / детерминированные проверки |
| Пиксели, CRM-виджеты, соцсети | regex по сырому HTML |
| **Всё извлечение из текста** — отрасль, размер, люди и роли, нормализация должностей, сигналы из вакансий и отзывов | **1 вызов `gpt-5.4-mini` на компанию** (S4), structured output |
| `why_now` для топовых лидов | **Агент** на старшей модели OpenAI, только топ-300 |

**Провайдер — OpenAI.** Вызов идёт обычным HTTPS POST на
`https://api.openai.com/v1/chat/completions` через тот же `Fetcher`, которым ходят
коннекторы: SDK ради одного запроса не нужен. Ключ — `OPENAI_API_KEY` в `.env`.
Границы ИИ от смены провайдера не двигаются: схема ответа не содержит вердикта
«писать или нет», его по-прежнему выносят правила.

**Ровно два обращения к модели на компанию.** Никаких «по вызову на задачу»: пять
отдельных вызовов стоят дороже, теряют связи между источниками и дают пять схем
вместо одной.

### Агент — один на компанию, не по одному на канал

```
ОДИН агент, каналы = его инструменты:
  serp, fetch_site, get_2gis_card, get_vacancies, get_instagram_profile

Параллелизм ПО КОМПАНИЯМ, не по каналам внутри компании.
```

Пять причин против N агентов на N каналов:

1. **Браузерные аккаунты** — 10 параллельных агентов на один аккаунт = бан в первый час
2. **Стоимость** — 4 агента × 1 500 компаний на порядок дороже парсера плюс одного
   вызова `gpt-5.4-mini`
3. **Каналы зависимы последовательно** — SERP → сайт → телефон → WhatsApp; параллелить
   нечего, агенты будут ждать друг друга или работать вслепую
4. **Дублирование** — независимые агенты трижды скачают одну главную страницу
5. **Невоспроизводимость** — скоринг на недетерминированных данных нельзя отладить

Агент стоит на порядок дороже одного вызова. В бюджете заложен на **топ-300** — не потому,
что дороже нельзя, а потому что остальным `why_now` не нужен: им всё равно не будут
писать в этом цикле. Вся база в 1 500 компаний стоила бы ~$90, что тоже допустимо.

## 12. Оркестрация

**Postgres как очередь**, `FOR UPDATE SKIP LOCKED`. Стадия — состояние в строке,
воркер на стадию, `attempts` + `next_retry_at` + `last_error`. Это ~150 строк и ноль
новых зависимостей.

```
# ponytail: Postgres-очередь. При >1M компаний/мес или ветвящихся workflow → Temporal.
```

Не Airflow, не Temporal, не n8n. Про n8n отдельно: хорош для демо и первых двух
клиентов, но не версионируется по-человечески, теряет элементы на батчах и становится
нечитаемым на 40+ нодах — как продукт, который продаёшь, он не выживет.

**Две раздельные очереди с разной скоростью:**

| Очередь | Что | Темп |
|---|---|---|
| Медленная | Всё браузерное и авторизованное — в v1 пусто, наполняется из резерва (§6.5) | 1 воркер на профиль, паузы, circuit breaker |
| Быстрая | 2GIS, hh, SERP, сканер сайтов, LLM, верификация, скоринг | параллельно, с вежливым троттлингом |

Смешивать нельзя: один агрессивный воркер в медленной очереди стоит аккаунта. В v1
медленная очередь не используется, но разделение закладывается сразу — иначе первый же
авторизованный источник придётся вживлять в работающий конвейер.

**Rate limiting на источник** — токен-бакет. Один жадный воркер выносит доступ ко всем
источникам сразу.

## 13. Каналы связи

### Приоритет

```
channel_priority:        ["whatsapp", "email", "phone", "linkedin", "telegram"]
require_at_least_one_of: ["whatsapp", "phone", "email"]
```

Лид считается **готовым**, только если у него есть канал из тех, которыми реально
пользуются. Компания с прекрасным score, но без единого рабочего канала — не лид, а
мусор в отчёте.

**Почему телефон выше LinkedIn:**
- cold calling в Казахстане жив и остаётся рабочим каналом для B2B
- 2GIS отдаёт телефон практически всегда — канал с максимальным покрытием, страховка
  на случай, когда ни email, ни WhatsApp не нашлись
- один номер даёт и WhatsApp, и звонок: два канала за одно обнаружение

**Почему `telegram` последний** — не потому что слаб, а потому что его труднее найти:
обнаруживается как `@username` в bio, на сайте или в контактах, независимо от телефона
(см. §9.2). Когда найден — работает; систематически добыть нельзя.

### Проверенные ограничения платформ (август 2026)

| Канал | Ограничение |
|---|---|
| WhatsApp | ~60 новых диалогов/день до бана. Cloud API — только opt-in и шаблоны |
| Email | 50 писем/день на аккаунт. Единственный канал, где холодный первый контакт легален по дизайну платформы |
| LinkedIn | 100 connection requests/неделю, у новых аккаунтов 20–30 |
| Instagram DM | API инициировать диалог не позволяет; вручную работает |
| Telegram | `Telethon` архивирован 02.2026; массовый `importContacts` — триггер бана |
| Телефон | Cold calling в КЗ жив и работает |

### Отправка в v1 — ручная

WhatsApp Web, почта, руками. 30–50 сообщений это час работы. Никаких API, никакого
opt-in-контура, ноль риска бана номера — и юридически это индивидуальная деловая
переписка, а не рекламная рассылка (см. §15).

```
# ponytail: ручная отправка. WhatsApp Cloud API — при >500 лидов/мес и наличии
#           opt-in контура. Не раньше.
```

## 15. Юридический контур

Закон РК №94-V «О персональных данных и их защите»:

- ФИО + должность + рабочий контакт = персональные данные
- **отдельное согласие требуется именно на рекламную рассылку**
- штрафы для юрлиц выросли до 10 000 МРП (~40 млн ₸)
- уведомление регулятора об утечке в течение 72 часов

**Три следствия для архитектуры:**

1. **`suppression_list`** — глобальная таблица, проверяется до каждого касания,
   никогда не очищается. Отписки, жалобы, hard bounce, ручные исключения.
2. **Индивидуальная деловая переписка вручную ≠ рекламная рассылка.** Автоматическая
   рассылка по базе — уже рассылка со всеми требованиями 94-V. Ещё одна причина
   держать v1 ручной.
3. **Локализация хранения в РК** — закон допускает трансграничную передачу (ст. 16),
   жёсткого требования по типу российского 152-ФЗ не подтверждено. **Тема спорная,
   нужен юрист перед продажей услуги клиентам.**

## 16. Порядок реализации

Сбор первичных данных детализирован в отдельной
[спеке коннекторов](docs/superpowers/specs/2026-08-06-connectors-design.md).

1. **`2gis_list`** — списки по рубрикам: охват базы и её реальный размер
2. **`2gis_firm`** — карточки: телефон, сайт, email, Instagram, WhatsApp
3. **`2gis_rubrics`** — рубрикатор, чтобы выйти за пределы одной рубрики
4. **`hh_vacancies`** — тексты вакансий, главный intent-сигнал
5. **`serp`** — ЛПР и добор компаний вне 2GIS
6. **Postgres + схема**, загрузка JSONL в `raw.fetches`
7. **Сканер сайтов на Scrapling:** CRM, пиксели, признаки продаж
8. **LLM-классификатор + правила скоринга**
9. **Выгрузка топ-30 → ручная переписка**

Первые два пункта дают полный сегмент с проверенными каналами связи — минимальный
набор, на котором видно, годятся ли данные вообще. Всё, что раньше стояло первым
(Postgres, схема, SERP-утилита), сдвинуто за них: складывать пока нечего, а формат
`core` всё равно определится тем, что реально отдают источники.

# Приложение А — Проверено и отвергнуто

Чтобы через месяц не вернуться к тем же идеям. Все проверки — август 2026.

## А.1 Источники

| Идея | Почему отвергнута |
|---|---|
| `api.hh.ru` /vacancies, /employers | **403 подтверждён** живым curl. С самодельным UA — `bad_user_agent: blacklisted`. Закрыт с 2025 |
| ~~Прямой скрейп поиска `hh.kz`~~ | **Отменено.** `Disallow: *?*` запрещает строку запроса, а не поиск: SEO-урлы `/vacancies/{slug}` идут без параметров и работают. `403` на голом клиенте снимается TLS-impersonation. См. §6.3 |
| **hh через Google** (`site:hh.kz` в SERP) | Не нужен: hh отдаёт и поиск, и вакансии напрямую. Убирал бы ~200 SERP-запросов, лаг индексации Google и неполноту покрытия — все три проблемы исчезли вместе с обходным путём |
| `catalog.api.2gis.com` | Эндпоинт жив, но требует ключ. Ключи, вшитые во фронт, при прямом обращении дают `apiKeyIsBlocked`. Не нужен: SSR-страница отдаёт те же данные без ключа (§6.2) |
| Браузерный скрейп 2GIS | Работал бы, но избыточен: одна cookie `dg5_museum_accept=true` открывает SSR обычному HTTP. Экономит прокси (~$20/мес) и снимает потолок 200–400 стр/час |
| Дамп реестра юрлиц КЗ | `stat.gov.kz` перенёс поиск по БИН **в личный кабинет**, публичного дампа нет. Аналога ЕГРЮЛ-выгрузки не существует |
| Публичная бухотчётность (аналог `bo.nalog.ru`) | `dfo.kz` покрывает только «организации публичного интереса» — крупняк. Наш ICP (10–200 чел.) там отсутствует |
| **Meta Ad Library API** | Покрывает **только политическую/социальную рекламу** глобально + все типы только для EU/UK. Для КЗ коммерческой рекламы не отдаёт. Живой запрос → `OAuthException`, HTTP 500 |
| Meta Ad Library веб | **403** на прямой запрос даже с браузерным UA. Доступен только реальным браузером, серая зона ToS |
| Госзакупки `goszakup.gov.kz` | API бесплатный и рабочий, но в КЗ **мало кто участвует** — выборка нерепрезентативна для нашего ICP |
| 2GIS API (коммерческий) | Публичного прайса нет, только калькулятор через sales. SSR-страницы дают то же бесплатно |
| `job.kz`, `rabota.nur.kz`, `headhunter.kz` | Мертвы физически (connection refused / DNS не резолвится) |
| `enbek.kz` | `robots.txt` прямо запрещает `/search/*` |
| `flamp.ru`, `olx.kz` | 403 на первом же запросе |
| Контур.Компас, СПАРК, СБИС, 2GIS.Data | Только РФ. **В КЗ аналога не существует** |
| Apollo.io, ZoomInfo | Слабое покрытие Казахстана |
| Свой скрейпер Google | Serper.dev стоит $1/1 000. Прокси и капчи ради экономии $2 |

## А.2 Архитектурные решения

| Идея | Почему отвергнута |
|---|---|
| **N параллельных агентов по каналам** | ×14 стоимость, конфликт с браузерными аккаунтами (10 сессий на 1 аккаунт = бан), каналы зависимы последовательно, дублирование работы, невоспроизводимость. Заменено на 1 агента на компанию с каналами-инструментами |
| **Отдельный вызов LLM на каждую задачу** (отрасль / команда / вакансии / отзывы) | Дороже, теряет связи между источниками (вакансия + отсутствие CRM вместе значат больше, чем порознь), пять схем вместо одной. Заменено на один вызов на компанию в S4 |
| Поиск ЛПР через LinkedIn-аккаунт | Риск бана аккаунта, нужного для продаж. Заменено на Google dorks — не заходим на LinkedIn вообще |
| Обязательный поиск имени ЛПР | 80–90 % работающих писем идут на `info@`, секретарь пересылает. Понижено до опции для топа |
| Угадывание `/team`, `/about` | У сайтов малого бизнеса структура непредсказуема. Заменено на скачивание сайта целиком (5–15 страниц) |
| ICP из B2C-отраслей (клиники, риелторы, онлайн-школы, e-com) | Им нужен inbound, а не outbound по компаниям. Система нашла бы их, но продукт для них произвести не смогла бы |
| Телефон как родитель для Telegram | Telegram-контакт бывает `@username` без телефона. Каналы равноправны |
| Скоринг через LLM | Недетерминирован, неотлаживаем, необъясним клиенту. Только правила |
| Kafka / Airflow / Temporal / n8n | Избыточно для 1 000–2 000 компаний. Postgres-очередь = ~150 строк |
| Векторная БД / RAG | Нечего искать семантически. `pg_trgm` закрывает нечёткое сопоставление имён |
| Микросервисы, real-time, свой UI | Один репозиторий, батчи раз в сутки, Metabase поверх Postgres |

## А.3 Каналы

| Идея | Почему отвергнута |
|---|---|
| Instagram DM cold через API | Meta не позволяет бизнесу инициировать диалог — ни через API, ни через ManyChat. Вручную работает |
| WhatsApp cold без opt-in | Прямо запрещено политикой WhatsApp, не просто рискованно |
| Telegram массовая рассылка | `Telethon` архивирован 02.2026; `importContacts` в объёме — триггер бана номера |
| LinkedIn connection-автоматизация | Кап 100/неделю, у новых аккаунтов 20–30. Прямое нарушение ToS |
| WhatsApp Cloud API для v1 | Не нужен при 30–50 лидах. Ручная отправка проще, дешевле и юридически чище |

# Приложение Б — Открытые вопросы

| # | Вопрос | Статус |
|---|---|---|
| 1 | **Krisha.kz / отраслевые каталоги** | Нужны, если ICP расширится за пределы бизнес-услуг |
| 2 | **Работа email-верификаторов на `.kz`** | Бенчмарков нет ни у одного вендора, требует теста на реальной базе. Кандидаты: Reoon, MillionVerifier (~$0.5–1.5/1 000), `check-if-email-exists` (self-hosted, AGPL) |
| 3 | **Локализация хранения ПД в РК** | Юридически спорно, нужна консультация до продажи услуги внешним клиентам |
| 4 | **LinkedIn-покрытие КЗ в цифрах** | Точной статистики не найдено. По оценке владельца проекта, для данного ICP канал живой |
| 5 | **Реальные веса `intent_score`** | Калибруются только после первых 30 ответов. Текущие значения — гипотеза |
| 6 | **Хватит ли охвата при потолке 60/рубрика/город** | Оценка ~3 000 по ветке «Бизнес-услуги» близка к целевой без запаса. Если мало — обход через `spatial.districts`, URL-форма фильтра не выяснена |

| 8 | **Склейка работодателя hh с компанией 2GIS** | hh даёт имя строкой, 2GIS — «имя, ТОО». Точный путь через `/employer/{id}` → сайт → домен стоит лишнего GET на вакансию. Не в MVP |
