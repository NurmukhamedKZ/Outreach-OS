# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

**Перед любым изменением кода спроси пользователя, создавать ли для этих изменений отдельный git worktree.** Не начинай правки, пока не получишь ответ. Исключения: кодер, запущенный `/workflow:launch-main`, — он уже в worktree; main-сессия с маленьким изменением (`docs/agents/workflow.md`, «Маленькое изменение — сразу, без тикета») — она всегда делает его в своём worktree, не спрашивая.

**Worktree создаются только внутри проекта:** `git worktree add .claude/worktrees/<ветка-без-слешей> -b <ветка>`. Папка `.claude/worktrees/` — в `.gitignore`.

**Лучшее решение — предлагай.** Спека, тикет и ADR — не догма. Видишь решение лучше записанного (проще, надёжнее, безопаснее, дешевле в поддержке) или записанное не работает на практике — предложи его пользователю до реализации: что записано, что предлагаешь, плюсы и минусы, рекомендация. Молча не отступай; новое реализуй после согласия, затем обнови спеку и заведи ADR.

**Разделы writer/ и sender/ ниже описывают код до редизайна** (решения — #4, `docs/adr/`); их переписывает #7. Система 1 и слои данных описаны по новому устройству (#13). Новый код пишется по разделу «Принципы кода» и `backend/CLAUDE.md`; где они расходятся с описанным устройством, побеждают принципы.

## Что это

AI lead-generation продукт: находит нужных людей, пишет им персонализированные
письма и доставляет их так, чтобы они не попали в спам. Продукт — это три
взаимосвязанные системы, а не одна:

1. **Targeting & Enrichment** — сегменты 2GIS, компании, исследование партиями,
   досье с цитатами, сигналы и лиды. Живёт в модулях `companies/`, `research/`,
   `refusals/` поверх ядра `core/` (см. секцию ниже).
2. **AI-персонализация** — тред переписки на каждого лида и черновик следующего
   сообщения. Живёт в `writer/` (см. секцию ниже).
3. **Sending infrastructure** — WhatsApp как главный канал: пул номеров,
   прогрев SIM, очередь исходящих, автопилот. Живёт в `sender/` (см. секцию).

Все три системы физически лежат в `backend/` под одним venv и одним
`backend/main.py`; ниже относительные имена модулей (`companies/`, `writer/`,
`sender/`, …) всегда подразумевают путь внутри `backend/`. `collector/` после #13
— не система, а сборщик приложения (`collector/api.py`), очередь джоб и старые
ручки дашборда; разносит его #7.

Реализованы системы 1, 2 и транспорт с пулом номеров системы 3; у первой и
второй есть своя секция ниже, у третьей — секция в «Веб как обвязка». Веб —
продуктовый дашборд (сайдбар, страница на систему, живые процессы по SSE),
не консоль запуска скриптов.

Бизнес-контекст, ICP и полная спецификация — в `docs/` (см. ниже).

## Команды

Продуктовый дашборд — во `frontend/`. Команды ниже, кроме веба, запускаются
из `backend/`. Сбор сегментов и партия исследования запускаются кнопкой
«Исследовать партию» на `/leads` (`POST /api/research/batches`), а не скриптами.

```bash
uv run pytest                                    # тесты всех систем, без сети
uv run pytest companies/tests/test_domain.py     # один раздел — одним файлом
```

Веб — два процесса, браузеру нужен только порт 3000:

```bash
cd backend && uv run python main.py                            # FastAPI, все три системы
cd frontend && npm run dev                                    # Next.js -> http://localhost:3000
cd backend/sender/node && npm start                           # сокеты WhatsApp, порт 8788
```

`main.py` поднимает то же приложение, что раньше собирал `collector/api.py`
через `uvicorn api:app` — включая роутеры writer'а и sender'а. Для
reload-режима: `uv run uvicorn main:app --port 8787 --reload --timeout-graceful-shutdown 5`.
Флаг обязателен: `/api/events` — бесконечный SSE-стрим, и без таймаута
`Ctrl+C`/перезагрузка на файле виснут на «Waiting for connections to close»,
пока не закроется вкладка фронтенда — у graceful shutdown в uvicorn нет
таймаута по умолчанию.

**`config.py` — единственное место чтения переменных окружения**, общее для
всех трёх систем: `pydantic.BaseSettings` сам подхватывает `backend/.env` при
импорте, поэтому `--env-file` и `os.environ` в коде систем не нужны — ключ,
которому он нужен, импортирует `from config import settings`.

`OPENROUTER_API_KEY` берётся из `backend/.env` (шаблон — `backend/.env.example`);
без него работают сбор сегментов и веб, но не партия исследования (503
`errors.modelKeyMissing`) и черновики системы 2.

**`observability.py` — единственная точка подключения Langfuse**, тем же
принципом, что `config.py` для секретов: берёт `LANGFUSE_PUBLIC_KEY`/
`LANGFUSE_SECRET_KEY`/`LANGFUSE_HOST` из `settings`, отдаёт
`langfuse.langchain.CallbackHandler` (`None`, если ключей нет — трейсинг молча
выключен, LLM-вызовы работают как обычно). Handler цепляется в
`config={"callbacks": [...]}` в `core/model.py::OpenRouterModel` (исследование) и
в `writer/services/agent.py`, `writer/services/seller.py` (переписка). Трейсы
группируются в сессию Langfuse по компании (research) или `thread_id` (writer).
Self-host Langfuse — `http://109.199.125.111:3000`.

## Архитектура системы 1

Путь лида: **сегмент → компания → партия → исследование → досье → лид** (#4,
ADR 0001–0005; устройство и причины — `docs/ARCHITECTURE_v3.md`, техническое
резюме и замер — `docs/TRD.md`). Модули — `core/` (база, миграции, настройки
оператора, адаптеры `Pages` и `Model`, канонические формы), `companies/`,
`research/`, `refusals/`, `backup/`; зависимости идут в одну сторону `companies` →
`research` → writer → sender, `refusals` зовут все, чужой модуль виден только через
`public.py`. Единственная копия разбора 2GIS и склейки — `companies/domain.py`,
исследования и сигналов — `research/domain.py`; обе — чистые функции, тесты — на
эталонных страницах `*/tests/fixtures/`.

Источников сигналов два: отзывы 2GIS и сайт компании. hh.kz отклонён 18 августа
2026 (пересечение работодателей с ICP около 5%), Instagram и поиск Google (Serper)
сняты в #13 — `docs/TRD.md` §8. Настройки оператора (сегменты, размер партии,
модель, веса, период полураспада) — в базе, на «Настройках» (ADR 0003); темп сети,
потоки и ретраи — константы в коде модуля.

**Компании (модуль `backend/companies/`, #11).** Сегмент — город плюс рубрика
2GIS; выбор оператора — настройка модуля (`operator_settings`, раздел
`companies`), умолчание — Алматы и рубрики 653, 339, 326, 112624, 527, 1238,
справочник 36 рубрик и двух городов — `companies/domain.py`. Сбор —
`POST /api/companies/collect` (202): сегменты не собранные и с ошибкой
помечаются «собирается» условным `UPDATE` и собираются в фоне по одному —
списки рубрики до потолка пагинации (подмену ловит `currentPage`), затем
карточки филиалов пулом из 16 потоков (`MAX_WORKERS`: запросы ждут сеть, темп
по хосту держит адаптер) через `core.pages` с cookie `dg5_museum_accept`.
Карточка, которой больше нет (404, 410), выбрасывает филиал; любой другой отказ
(403, 429, проверка робота, сеть) валит сегмент целиком — иначе троттлинг
источника молча уменьшал бы выдачу. Запись сегмента — одна транзакция
`BEGIN IMMEDIATE`. Сбор идёт в `BackgroundTasks` (исключение из правила
`backend/CLAUDE.md`: потеря задачи с процессом стоит только статуса). Состояние —
в таблице `segments` (`new|collecting|collected|failed`, филиалы, потолок,
причина); старт приложения возвращает оставшиеся «собирается» в «не собран».
Склейка — прежние правила `resolve.py`, перенесённые в `companies/domain.py`;
идентификатор компании не меняется никогда: новый филиал присоединяется к
существующей компании, а находка, связавшая две существующие, оставляет их
раздельными и пишется в лог. Контакты — в канонической форме `core.contacts`.
Фасад: `companies.public.collect_chosen(db, pages, now)` синхронно собирает
выбранные несобранные сегменты (для партии #12),
`companies.public.prioritized(db, limit, exclude)` отдаёт только достижимые
компании выбранных сейчас сегментов (WhatsApp или казахстанский мобильный, код не 71x/72x) в
порядке «WhatsApp → отзывы → сайт»; отказы проверяет вызывающий;
`by_id(db, ids)` — компании по идентификатору из любого сегмента, `channel(company)` —
контакт для WhatsApp (WhatsApp, иначе мобильный), `site_domain(company)` — свой сайт
компании (соцсеть и виджет сайтом не считаются), `counts(db)` — компании в базе и с
каналом для WhatsApp (счётчики «Сегодня»), `segment_labels(db, ids)` — «рубрика ·
город» именами по первому сегменту компании (разрез аналитики). Отдельной кнопки
сбора нет — сегменты собирает партия («Исследовать партию» на `/leads`).

**Исследование (модуль `backend/research/`, #12, ADR 0001).** Партия —
`POST /api/research/batches` (202) и идёт в фоне (`BackgroundTasks`, то же
исключение, что у сбора сегментов): если выбранные сегменты не собраны — собирает их
через `companies.public.collect_chosen`, затем берёт по приоритету до размера партии
компании без досье, с неисчерпанными попытками (три неудачи — компания больше не
берётся) и без отказа, и исследует их пулом из 16 потоков (`MAX_WORKERS`: вызов
модели ждёт 15–30 с). Одна партия за раз — частичный уникальный индекс
`one_running_batch`, второй запуск — 409 `errors.batchRunning`; без ключа модели —
503 `errors.modelKeyMissing` до старта. Остановка —
`POST /api/research/batches/current/stop`: флаг проверяется перед каждой следующей
компанией, начатые дорабатывают. Состояние — `batches`
(`collecting|researching|done|stopped|interrupted`) и `batch_companies`
(`pending|researching|done|failed`, номер попытки, причина, отброшенные цитаты);
прогресс — `GET /api/research/batches/current` опросом, без джоб и SSE. Старт
приложения помечает идущую партию прерванной, а «исследуется» возвращает в «ждёт»;
сама она не возобновляется — её доделывает следующий запуск. Исследование компании:
отзывы каждого филиала (публичный API отзывов 2GIS, 404 — отзывов нет, любой другой
отказ — неудача, а проверка робота останавливает всю партию: компания возвращается в «ждёт»
без траты попытки, причина — в `batches.error`), главная сайта (откат на `http://` при ошибке сертификата) и до
шести внутренних страниц по словарю ссылок; сайт не ответил — по отзывам, адрес
не в интернете (localhost, частная сеть, в том числе после редиректа) не читается вовсе.
Нет ни отзывов с текстом, ни сайта — модель не зовётся, неудача «нечего читать». Один вызов модели (`research/domain.py::SYSTEM`, схема `ResearchAnswer`:
факты и досье; модель отдаёт угол и дословную цитату, а ссылку, источник и дату
ставит код — по месту, где нашёл цитату, а из нескольких мест — по самому свежему). Цитату жалобы, вакансии и зацепки код ищет
в собранном тексте после нормализации пробелов, кавычек, тире и регистра (короче 12
знаков не принимается); ненайденное отбрасывается и считается. Неудача — ни одной
подтверждённой зацепки (`domain.judge`), `ModelError` или отказ источника отзывов:
компания вернётся в следующую партию; три `ModelError` подряд останавливают партию с
причиной (опечатка в модели или пустой баланс иначе сожгли бы попытку у каждой).
Компания в отказе перед стартом исследования помечается неудачной без вызова модели,
повторное исследование её — 409 `errors.companyRefused`; партия без компаний
заканчивается с причиной в `batches.error`. Сигналы выводит код (`domain.findings`): жалоба
«не дозвонились»/«не ответили на заявку» → `reviews_missed_lead`, прочая жалоба в
отзыве без ответа → `reviews_unanswered_complaint`, вакансия в продажах →
`site_hiring_sales`, нет цен на прочитанном сайте → `site_no_pricing`, разметка
сайта → `crm_widget`/`ads_platform`/`inbound_widget`; один на тип. Досье хранится
версиями (`dossiers`: модель, полный промпт, ответ, проверенное досье), сигналы —
`signals`; повторное исследование — `POST /api/research/companies/{id}` (партия из
одной компании). Оценка считается при чтении: вес из настроек, затухание вдвое за
период полураспада от `now`, разбивка «сигнал — вклад — цитата — ссылка». Лид —
досье с подтверждённой зацепкой, канал для WhatsApp — WhatsApp или казахстанский
мобильный (`companies.public.channel`) — и нет
отказа ни по одному контакту — отказ проверяется при чтении. `why_now` — самая свежая
зацепка. Чтение — `GET /api/research/leads`, `GET /api/research/companies/{id}`;
настройки — `GET/PUT /api/research/settings` (размер партии 1–200, модель, веса,
период полураспада). Фасад: `research.public.leads(db, now)`,
`company(db, id, now)` (неизвестная компания — `research.public.CompanyNotFoundError`),
`forget_interrupted(db)`; лидов через него читают `writer` и песочница (#17). Когда
партия закончилась — удачно, остановлена или сломалась (в том числе партия из одной
компании), — фоновая задача партии делает снимок бэкапа (`backup.public.back_up` тем же
`BackupService` процесса, `app.state.backup`, вне транзакций партии); ошибка бэкапа
партию не меняет, исход — в журнале актором `backup`.

**Юридический контур (модуль `backend/refusals/`, PRD F21).** Источник истины —
таблица `refusals` в `state.db`, невосстановимый слой (схема — ревизия Alembic
`0002`). Писатель один —
`refusals.public.record`: контакт в канонической форме (`core/contacts.py`:
телефон и ссылка WhatsApp на него — `+7XXXXXXXXXX`, остальное — в нижнем
регистре), причина обязательна, повтор возвращает первую запись. `DELETE`,
`UPDATE` и `INSERT OR REPLACE` таблицы гасят триггеры. Проверка нового кода —
`refusals.public.is_refused(db, контакты компании)`: отказ по любому контакту
закрывает компанию целиком; число отказов для «Сегодня» — `refusals.public.count`.
Старое имя `suppression(handle, added_at, reason)` — представление над `refusals`:
его до #7 читает sender (`worker._suppressed`), сравнивая контакт через
`refusals.public.canonical(handle)`, и отказ там по-прежнему снимает один канал, а
не компанию. Представление удалит ревизия Alembic #7, когда читателей не останется. API — `GET/POST
/api/refusals`, выгрузка — `GET /api/refusals/export.csv` по требованию.

**Веб как обвязка, не источник правды.** Очередь джоб (`collector/services/jobs.py`,
`state.jobs`, до #7) после #13 несёт одну операцию — «Черновики топ-N» writer'а
(`POST /api/pipeline/write`); реестр `OPERATIONS`/`PIPELINES` пуст, пока его не
наполнит сборщик `collector/api.py`. Воркер исполняет шаги в том же процессе:
`OPERATIONS[name](ctx)` через `asyncio.to_thread`, одно за раз, ставить можно
несколько. Шаг имеет стадию, дорожку и статус (`pending|running|done|failed|cancelled`) и прогресс. Прогресс и лог идут
по SSE `GET /api/events` (события `snapshot`, `job`, `log`, `refresh`,
`activity`); хвост
лога добирается `GET /api/jobs/{id}?offset=`. Операции исполняются в потоке
(`asyncio.to_thread`), поэтому `events.publish` возвращается в цикл через
`call_soon_threadsafe`: `put_nowait` из чужого потока цикл не будит, и ждущий
подписчик просыпается только когда цикл проснётся сам. Отмена кооперативная: флаг в
RunContext, операция проверяет его в `check_cancelled`. Счётчики трёх систем —
`GET /api/stats` (`services/metrics.py`; «Сбор лидов» — компании и с каналом из
`companies.public.counts`, лиды из `research.public.leads`, отказы из
`refusals.public.count`), журнал фоновой работы и пульс
демонов — `GET /api/activity` (`collector/routes/activity.py`: порог молчания
считает бэкенд, потому что интервалы тиков живут в `sender/config.toml`), воронка
холодной переписки — `GET /api/analytics` (`backend/analytics.py`: читает базу в ro, считает тредами, отдаёт diagnosis и
три разреза; сегмент треда — `companies.public.segment_labels`), список задач
оператора на «Сегодня» — `GET /api/tasks` (`backend/tasks.py`: тот же приём —
базы в ro, имя компании — `companies.public.by_id`, — но порядок срочности (эскалированный тред важнее
непроверенного черновика) считает бэкенд, а не страница). Система 3 (транспорт, пул номеров и
очередь): пул живёт в той же `state.db` (таблицы `numbers`, `outbox`),
`sender/transport.py` — единственный модуль системы, ходящий в сеть (сторожит
`sender/tests/test_import_graph.py`), за швом — Node-сервис на Baileys
(`backend/sender/node`, отдельный процесс, порт 8788). В lifespan — часовой
монитор здоровья (`sender/routes/sender.py::monitor_numbers`), тик прогрева
(`warm_numbers`) и воркер очереди (`sender.send_queue` → `sender/services/worker.py`:
тик раз в 20 секунд, одна созревшая строка за тик, исходы в `TICK_OUTCOMES`):
прогрев работает при `autopilot = off`, потому что пишет
нашим же номерам, а не лидам. **Ни один из них не работает молча**: исход
каждого тика ложится в журнал `state.activity` (`backend/activity.py`, путь к
базе приходит швом `use()` из `collector/api.py` — модуль верхнего уровня, как
`config.py`, потому что писать в него обязаны и система 1, и система 3).
Подряд идущие одинаковые `(actor, outcome, subject)` схлопываются в `repeats`:
тик раз в 20 секунд иначе давал бы 4300 строк в сутки и топил бы в них
единственное важное событие. Решение агента по входящему (`answered`,
`escalated`, `closed`) ложится туда же актором `sender.tick`, а его причина —
ещё и в `threads.status_reason`: журнал чистится через 14 дней, а вопрос
«почему автомат отдал этот тред человеку» задаётся и через месяц. Пульс
демона — `MAX(last_at)` по актору, а не
переменная в памяти процесса: так он переживает перезапуск и не врёт после
него. Запись идёт своим соединением и **вне транзакции вызывающего** — след
«пытались, и вот что вышло» обязан пережить откат тика, а внутри чужого
`with db:` он ждал бы освобождения базы, которое наступит только после его же
возврата. Из `except` демона пишет `record_crash()`, единственное место, где
журнал молчит о собственной беде: исключение оттуда убило бы asyncio-задачу,
ради живучести которой этот `except` и стоит. Ретенция — 14 дней, чистится на
часовом тике монитора. Номер приводится к канонической форме на
границе — из этой строки Node собирает путь к каталогу сессии. Постановка в
очередь — `POST /api/sender/queue`, а не эндпоинт writer'а: кнопка оператора и
тик воркера при `autopilot = "full"` проходят через одну
`sender/services/queue.py`. Гейты перед каждой отправкой (`services/gates.py`),
порядок не косметический: отказ и закрытые треды отменяют строку, окно
10:00–18:00 Asia/Almaty, дневной лимит и джиттер — переносят. `sent_text` пишет
ровно один автор — воркер, после ответа транспорта (`sent: false` — ретрай с
backoff 1/5/30, неопределённость — `stuck` человеку, не слепой повтор).
`autopilot` переключается файлом `backend/sender/autopilot` (off | manual |
replies | full, он же kill switch — на каждом тике читается заново; умолчание из
`sender/config.toml` — `manual`, неизвестное значение в файле или в
`config.toml` — `off`: опечатка не имеет права открыть очередь). `off` держит и то, что уже стоит в
очереди; `manual` очередь отправляет, но сам в неё ничего не ставит — ни ответ
на входящее, ни follow-up, ни холодное касание: модель готовит черновики, уходит
поставленное оператором. Строки, которые автомат поставил в `replies`/`full` до
перехода в `manual`, уйдут: у строки `outbox` нет автора, и полный стоп — только
`off` (автор строки и её удержание в `manual` — #7). В режиме `full` тик
ставит в очередь не больше, чем пул успеет отправить за сутки. `POST
/api/sender/webhook` принимает статусы доставки (доставкой считаются ровно коды
3 и 4: Node форвардит каждый `messages.update`, а ack сервера, принятый за
доставку, ослепил бы детектор `min_delivered_rate`) и входящие: `kind: "incoming"`,
подпись заголовком `X-Sender-Secret` (пустой секрет из `SENDER_WEBHOOK_SECRET`
выключает проверку — так работает локальная разработка). Ручка делает только
быстрое и детерминированное: канонизует JID отправителя в `thread_id`, пишет
входящее в `messages` (`sent_text` сразу: ответ лида правкам не подлежит),
дедуплицирует по `provider_id`, одной транзакцией гасит расписание треда
(`outbox -> cancelled`, `next_touch_at = NULL`), проверяет стоп-слова регуляркой
из `config.toml` ([stopwords], ДО модели: классификатор вероятностный, а
проценты его ошибок приходятся ровно на тех, кто и жмёт Report), и отдаёт 200.
Стоп-слово закрывает тред в `closed_refused` и пишет отказ: `sender/services/refusal.py`
— шов, зарегистрированный из `collector/api.py` (отказ — юридический контур
F21, и система 3 не имеет права знать collector). Пустое `text` (голосовое, фото)
эскалирует и помечает сообщение `[медиа]`; ответ в `exhausted` возвращает тред
в `active`; ответ в `escalated` уходит человеку в Telegram, автомата не будит.
Всё остальное — на тике: `sender/services/incoming.py` зовёт агента-продавца
(`writer/services/seller.py`, `create_agent` с единственным инструментом
`classify(return_direct=True)`) и держит четыре предохранителя, и все четыре —
`if`: один автоответ на тред (`limits.auto_replies_per_thread`; действует и
считает только в `replies`/`full`, где ответ встаёт в очередь сам, — в `off` и
`manual` черновик пишется на каждое входящее),
`recursion_limit = 2` (`seller.RECURSION_LIMIT`), эскалация вместо отправки на
длинный ответ или цифру с валютой, три попытки на входящее
(`messages.handle_attempts`). Ответ уходит через тот же `outbox` и те же гейты,
но по своему окну (`[window.reply]`, круглосуточно и семидневно): лид написал
сам и ждёт сейчас. Follow-up планируется сроком (`threads.next_touch_at`, ставит
`conversation.bump_touch` той же транзакцией, что расходует касание), а текст
рождается в момент срока (`sender/services/followup.py` →
`writer/services/followup.py`): текст, сгенерированный заранее, пролежал бы в
очереди десять дней и ушёл устаревшим. Каденция `[3, 7]` и `max_touches` живут
только в `sender/config.toml`. Ответ лиду пишет один автор — seller: старый
одноходовый `agent.REPLY` удалён, ход `kind='reply'` в инбоксе зовёт того же
агента, что отвечает автоматически (промпт два раза на одну ситуацию дал бы
две калибровки).
Уникальность в `outbox` — по живым строкам, а не по всем: кончившуюся в
`failed`/`stuck` строку оператор имеет право поставить заново, иначе транспортная
авария хоронила бы лида навсегда. Статус
переписки с лидом в базу
системы 1 не возвращается — переписку ведёт система 2 в той же `state.db`;
обратно сюда приходит только отказ (`refusals`). Прогресс шага — `ctx.progress(current,
total, label)` из операций, а не парсинг вывода.

## Архитектура writer/ (система 2)

Тот же venv, что у collector'а (`backend/pyproject.toml`), но свой пакет:
`writer.*` не импортирует `collector.*` напрямую, только через шов в
`collector/api.py`. **Лидов читает через `research.public`** (`writer/db/leads_source.py`,
#17) — других модулей не знает, граф сторожит `writer/tests/test_import_graph.py`.
Кто лид (зацепка, канал, отказ — F19, F21), решает research, второй копии этих
правил у writer'а нет. Writer решает только, о чём писать: в seed треда идут досье
(`summary`, `decision_maker` из `decision_maker_hint`, `approach`, `pains`), его
зацепки и сигналы `breakdown` типов `[signals].pitchable` — зацепки и сигналы не
старше `[signals].max_age_days`. `thread_id` — канал лида (`channel.handle`,
`+7XXXXXXXXXX`). Research читается из боевой `state.db` только на чтение
(`paths.PRODUCTION_STATE`), треды — из `paths.state_db()`: в бою это один файл, в
песочнице — разные. Первый черновик открывает тред только лиду (не лид — 409), ход
в открытом треде требует канала и отсутствия отказа (иначе 409). Компании с общим
контактом `companies` оставляет раздельными, поэтому номер, занятый тредом другой
компании, — тоже 409, а «Черновики топ-N» отдают номер первой по оценке. Операция
не берёт и лида, которому нечего назвать свежим (ни зацепки, ни сигнала): модель
сказала бы stop, а открытый тред навсегда исключил бы компанию из отбора.

```bash
cd backend
uv run pytest writer/tests/    # schema, threads, leads, prompt, operations
```

«Черновики топ-N» — не скрипт, а операция очереди `writer.outreach`
(пайплайн `write`): кнопка «Черновики топ-N» на странице «Холодные» (`/cold`)
или `POST /api/pipeline/write`. Она всегда обрабатывает N **новых**
компаний: у кого тред уже есть — на канале или на любом номере, — того пропускает
и идёт дальше по списку.

**`state.threads`/`state.messages` — невосстановимый слой**, как `data/raw/` у
системы 1: схема создаётся через `CREATE TABLE IF NOT EXISTS`, `DROP` запрещён,
в git не лежит. Переписка живёт в той же `state.db`, что отказы и ответы модели.
Этап переписки живёт в `threads.stage`, а вариант оффера — в `messages.offer_variant`.

**Черновик ≠ отправленное.** Ответ модели ложится в `messages.draft_text`, а в
историю треда попадает только `sent_text` — то, что оператор реально отправил
после правки. Между ними ещё `messages.queued_text`: что подтвердил оператор
нажатием «Поставить в очередь», но что транспорт ещё не подтвердил. Историей
агента считается ровно `WHERE sent_text IS NOT NULL`:
иначе следующий ход строился бы на сообщении, которого лид не получал. Разница
draft/sent — единственная бесплатная разметка для калибровки промпта.

**Промпт хранится, а не реконструируется.** `agent.draft()` возвращает
`Attempt(draft, prompt, model)`, и полный запрос ложится в `messages.prompt`
(json пар `[["system", …], ["human", …]]`) рядом с ответом. Пересобрать его
задним числом нельзя: `seed` и история к тому времени другие, а текст писался
по тогдашним — это был бы не аудит, а догадка. Отдаётся отдельной ручкой
`GET /api/threads/{company_id}/messages/{message_id}/prompt`: промпт весит
2–4 КБ, и в каждой строке инбокса он не нужен. Черновики старше этой правки
промпта не имеют, и интерфейс говорит об этом прямо, а не рисует прочерк.
Автоответ продавца собирает `create_agent`, его промпт остаётся в Langfuse.

**Ни langgraph, ни чекпойнтера.** Инструментов у агента нет, на ход нужен один
вызов со structured output — `agent.py` это три функции и `with_structured_output`,
как в `analyze.py`. Чекпойнтер дописывал бы неподтверждённый черновик в
состояние сам и дал бы второй источник правды рядом с `messages`.

**Запрет пустых follow-up — в схеме, а не в промпте** (`schemas/outreach.py`):
`with_structured_output` повторит вызов на невалидном ответе, а инструкция в
промпте была бы просьбой, которую модель нарушает именно там, где важно.

**Веб — та же консоль.** `collector/api.py` монтирует роутер `writer/routes/threads.py`
(`/api/threads/*`: инбокс `GET /api/threads` одной сводкой + карточка, ходы
`draft/queue/incoming`, плюс `GET /api/threads/drafts` — очередь проверки
первых писем), фронтенд получает две страницы: `/cold` — конвейер холодных
черновиков, `/threads` — инбокс диалогов. Карточка лида композера не несёт:
переписка живёт на своих страницах, а не второй копией внутри неё. Эндпоинт `/draft` ходит в сеть, поэтому ключ
должен быть в `backend/.env` (см. `config.py` выше):

```bash
cd backend && uv run python main.py
```

Без ключа `/draft` отвечает 503 с инструкцией задать его в `backend/.env`, а
не трассировкой. Отказ
по-прежнему оформляется модулем `refusals` (`POST /api/refusals`): вторая точка
входа в юридический контур — второй шанс разойтись со списком отказов.

## Архитектура frontend/ (дашборд)

Продуктовый дашборд: восемь страниц по сущностям, а не по границам систем.
`/` — «Сегодня»: список задач оператора (`GET /api/tasks`, кто и почему, а не
просто счётчик) первым, ниже — счётчики трёх систем и последние запуски;
`/leads` — лиды модуля `research` (`GET /api/research/leads`: угол, цитата и
ссылка `why_now`, канал, оценка) под панелью партии («Исследовать партию» /
«Продолжить партию», прогресс опросом раз в 3 секунды, пока идёт, и раз в 30 в
покое, «Остановить», итог и причина остановки), клик ведёт на
`/leads/[id]` (карточка `GET /api/research/companies/{id}`: досье, разбивка оценки
по сигналам, контакты, попытки, «Исследовать заново», форма отказа);
`/cold` — конвейер проверки первых писем с полным промптом; `/threads` —
инбокс диалогов с видом касания; `/analytics` — воронка холодной переписки и
три разреза; `/sender` — пул номеров, очередь и kill switch; `/activity` —
«Процессы»: демоны и живой журнал фоновой работы; `/settings` — «Настройки»
оператора (ADR 0003): раздел на модуль, пишется руками под него, страница
опрашивает API и SSE не использует. Разделы — «Сегменты» модуля
`companies` и «Исследование» модуля `research` (размер партии, модель, период
полураспада, веса семи сигналов; сохраняется целиком).
Содержимое целиком приезжает с бэкенда, не хардкодом: пороги молчания демонов
(`silent_after_seconds`), порядок инбокса и календарь прогрева считает бэкенд.

**Одна SSE-подписка на всё дерево.** `components/live.tsx` (LiveProvider)
держит EventSource, кладёт в контекст снапшот, апсерт джоб, хвост лога,
`activityTail` (живая лента журнала) и `refreshTick` (сигнал спискам перечитать
данные после пересборки базы). Страницы не открывают своих стримов.

**SSE ходит на API-оригин напрямую, минуя rewrite next** (`.env.local`:
`NEXT_PUBLIC_API_ORIGIN`): dev-прокси Next отдаёт заголовки стрима, но
буферизует тело бесконечного ответа — события до страницы не доезжают.
JSON-эндпоинтам прокси не мешает. Сломается снова — первым делом проверь,
куда смотрит EventSource.

**Активная джоба видна отовсюду.** `components/RunBar.tsx` — полоска в
`layout.tsx` над всем деревом: заголовок, шаг, ссылка на «Процессы», «прервать».
Возвращает `null`, когда очередь свободна.

**Дизайн-система** (`globals.css`, токены в `:root`): белый канвас, чёрный
CTA, Inter + JetBrains Mono (`next/font`), hairline-границы, тёмные блоки
только у кода и лога. Тема светлая и залочена — инверсий секций нет. Иконки —
`@phosphor-icons/react`, свои SVG не рисуем.

## Слои данных

- **`backend/data/state.db`** — единая невосстановимая база (#9, ADR 0002):
  отказы, джобы, переписка системы 2 (включая `messages.prompt`/`model` —
  полный запрос, ушедший в модель), журнал фоновой работы (`activity`) и
  таблицы модулей: сегменты, компании, партии, досье, сигналы, настройки.
  Путь — `paths.PRODUCTION_STATE`; рядом в `backend/data/` лежат скачанные
  страницы (`pages/`, `core/pages.py`: страница меняется, повторное исследование
  читает её без сети) и прогоны песочницы (`sandbox/`). Каталог в git только пустым (`.gitkeep`). Схема новых модулей
  — история Alembic в `backend/migrations/` (ADR 0004, `backend/CLAUDE.md`,
  «Миграции»), старые таблицы (`jobs`, `threads`, `messages` — `collector/db/schema.sql`
  до #7) — через `CREATE TABLE IF NOT EXISTS`, `DROP` запрещён, в git не лежит.
  Таблица `llm_answers` старого конвейера в существующих базах осталась, но не
  создаётся и не читается. Открывается модулями через `core.db.connect`, writer'ом
  — напрямую, журналом — своим коротким соединением на запись.
  Владелец таблицы доливает свои колонки сам (`thread_store` — `prompt`/`model`,
  `sender/db/migrate.py` — состояние треда): полагаться на то, что до базы
  добежит чужая миграция, значит падать везде, где та система не стартовала.
  Обратное тоже верно — чужую колонку не доливают, а терпят её отсутствие
  (`inbox` без `threads.status`, `history` без `outbox`): колонка, созданная
  раньше владельца, украла бы у его миграции разметку старых строк.
- **`backend/sender/node/sessions/`** — невосстановимый слой: ключи сессий
  WhatsApp (сохранение сессии — «детка», потерянная ключ — переподключение
  телефоном). Не в git, в тот же бэкап, что `state.db`.
- **Бэкап** (модуль `backend/backup/`, #8) — `state.db` (снимком SQLite
  `Connection.backup` и `PRAGMA integrity_check`), `backend/data/pages/` и
  сессии WhatsApp — в папку iCloud Drive (`settings.backup_dir`). Снимок —
  каталог `<UTC-время>` с базой и сессиями, собирается во временном каталоге и
  переименовывается; хранится последний удачный за каждые из 14 последних
  суток UTC (ручной запуск в тот же день заменяет сегодняшний), лишние
  удаляются только после записи и проверки нового. Страницы — одно зеркало `pages/`, докладываются только новые.
  Демон `backup.loop` — поток из lifespan (ADR 0005) — проверяет раз в час и делает снимок, если
  последнему сутки или его нет; исход — в `activity` актором `backup`.
  `GET/POST /api/backup`; время бэкапа — настоящее (`backup.public.now`), без
  сдвига песочницы. Задача на «Сегодня» — если бэкап выключен (нет каталога
  iCloud Drive), ни разу не записался или удачного нет двое суток. Кроме демона,
  снимок делается после каждой партии исследования (абзац «Исследование»). Базы песочницы не
  бэкапятся. Восстановление — `README.md`, «Бэкап».
- **`backend/collector/data/`** — данные старого конвейера (`raw/`, `derived.db`,
  `cookies.json`). После #13 код их не открывает; каталог в `.gitignore` и на диске
  не тронут — удалять его или нет, решает владелец.

## Песочница (`backend/sandbox/`)

Стенд, на котором аутрич проходится целиком без единого сообщения в WhatsApp.
Включается флагом `SANDBOX=1` в `backend/.env` вместе с
`SENDER_NODE_URL=http://127.0.0.1:8787/api/sandbox/node`; без флага роутеров
песочницы в приложении нет вовсе, а с флагом и боевым адресом транспорта
приложение не стартует — тестовый прогон, ушедший живым людям, дороже падения.

**Прогон — отдельный файл базы** (`backend/data/sandbox/<run>.db`): `thread_id` — это
номер телефона и первичный ключ `threads`, поэтому второй прогон по тому же
лиду упёрся бы в занятый ключ, а «чистый контекст» пришлось бы изображать
фильтром в пяти местах. Схему наполняют настоящие владельцы таблиц. Лид в
прогоне — настоящая компания: прогон заводится только по лиду research (`POST
/api/sandbox/runs`: компании нет — 404, не лид — 409), выбор лида — `GET
/api/sandbox/leads`, а досье writer читает из боевой `state.db` только на чтение:
ручки research (`/api/research/*`) и страницы `/leads` при `SANDBOX=1` читают базу
прогона, где research пуст. Id компании входит в имя файла прогона, и
`runs.create` не даёт ему вывести файл из `data/sandbox/`. Отказ, записанный
внутри прогона (стоп-слово), writer не видит — research проверяет отказы боевой
базы; черновик в таком треде создать можно, отправку держат `closed_refused` и гейты.

**`backend/paths.py`** — единственный владелец пути к невосстановимому слою на
три системы (раньше его называли пять мест). **`backend/clock.py`** — «сейчас»
продукта; шесть мест зовут его вместо `datetime.now`. Смещение принадлежит
прогону и лежит в его базе: иначе прогон, начатый со сдвигом «+3 дня», после
перезапуска бэкенда откатился бы назад во времени. В бою смещение нулевое.
Тем же основанием, что `paths.py`, `clock.py`, `activity.py` и `analytics.py`,
на верхнем уровне лежит и `backend/tasks.py`: список задач оператора собирается
из тех же трёх систем, и ни одна из них не имеет права знать две другие.
Там же `backend/sqlite_tools.py` — `has_table`/`has_column`/`connect_readonly`:
чужую колонку терпят все три системы, и проверка наличия живёт в одной копии.

**Подменный Node** (`sandbox/node.py`) отдаёт те же пять ручек, что
`sender/node/index.js`, и события шлёт в свой же `POST /api/sender/webhook` —
тем же HTTP, с тем же секретом, через тот же дедуп. Статус доставки уезжает
фоном с повтором, пока вебхук не подтвердит: без сети он обогнал бы запись
`provider_id` в `outbox`. Четыре тумблера аварий (`sandbox/faults.py`) живут в
памяти процесса — авария, пережившая перезапуск, объяснялась бы потом полдня.

Песочница знает про все три системы; её не импортирует никто, кроме сборщика
`collector/api.py` — сторожит `sandbox/tests/test_import_graph.py`.

## Принципы кода

Принципы описывают новый код. Существующие три системы написаны до них и заменяются модулями предметной области при переписывании (#9–#13, затем #7), а не отдельной кампанией. Правила FastAPI, структура модуля и анти-паттерны — `backend/CLAUDE.md`.

### CUPID — обязательно, все пять

- **Composable.** Маленькая поверхность: функция принимает то, что ей нужно, а не «контекст на всё». Минимум зависимостей, никаких скрытых глобальных синглтонов — соединение с базой, транспорт, модель и конфиг приходят в конструктор сервиса или параметром. Новых модульных швов `use()` не заводим.
- **Unix philosophy.** Одна функция — одно дело, и делает его целиком. Гейт только отвечает «можно ли отправлять сейчас», не пишет в базу и не шлёт сообщение.
- **Predictable.** Одинаковый вход — одинаковый результат; побочные эффекты видны из имени (`enqueue`, `record_refusal`, `activate_run`). Время читает одна функция (`clock.now()`) на границе — в роуте или в тике, дальше оно идёт параметром `now`; случайность (джиттер) передаётся так же. Ошибки — доменные исключения (`AlreadyQueuedError`, `ClosedThreadError`, `UnknownThreadError`), а не `None` или магические значения.
- **Idiomatic.** Пишем как принято в Python 3.13, FastAPI и Pydantic v2: аннотации типов на всех сигнатурах, pydantic или `dataclass` для DTO, `pathlib`, `StrEnum`/`Literal` вместо голых строк, контекстные менеджеры для ресурсов. Фронт — Next 16, React 19, TypeScript; эта версия Next отличается от привычной, перед правкой читай `frontend/AGENTS.md`. Не переносим паттерны из других экосистем.
- **Domain-based.** Имена — из `GLOSSARY.md`. Структура кода повторяет модули предметной области, а не технические слои (`utils/`, `helpers/`, `managers/`, `common/` не заводим). Общее ядро без бизнес-логики — `backend/core/`; до переезда его роль играют модули верхнего уровня `backend/` (`config.py`, `clock.py`, `paths.py`, `sqlite_tools.py`).

### SOLID — только S и D

Из SOLID обязательны два принципа. Остальные три не применяем как цель: запрещены не классы, а **лишние абстракции**, и абстракция появляется, только когда у неё есть вторая реальная причина существовать.

**S — Single Responsibility: одна причина для изменения.**

- Слои модуля не смешиваются: `api.py` — только HTTP, `service.py` — бизнес-правила и транзакция, `repository.py` — только запросы своих таблиц, `domain.py` — чистые правила без ввода-вывода.
- Модуль отвечает за одну область предметной модели; правило живёт у владельца данных (Tell, Don't Ask).
- Сервис начал меняться из-за двух разных сценариев или актёров — делим на два, а не растим один на 30 методов.

**D — Dependency Inversion: бизнес-логика не создаёт и не знает конкретную инфраструктуру.**

- Зависимости приходят снаружи — через конструктор и `Depends` FastAPI; сервис никогда не создаёт клиентов и SDK сам. Сборка — в `dependencies.py` модуля для запроса и в `backend/main.py` для фоновых задач.
- От внешних систем сервис зависит через `Protocol` с реальной и Fake-реализацией. Таких систем три: модель (OpenRouter), транспорт WhatsApp (Node), сетевой сбор (scrapling). Код домена не импортирует SDK.
- Между модулями — зависимость от фасада `public.py`, а не от внутренностей чужого модуля. Фасад появляется вместе с первым внешним вызовом.
- Реализация одна и заменять её не нужно — интерфейс не заводим: инверсию даёт внедрение через конструктор.

**O, L, I — не цель.** Не строим точек расширения «на будущее»; наследования, кроме исключений, нет; узкие интерфейсы на границах получаются сами собой.

**Под запретом:** интерфейс с одной реализацией, наследование ради переиспользования кода, базовые `BaseService`/`BaseRepository`, generic-репозитории, фабрики одного продукта, DI-контейнеры, стратегии из одного варианта, классы-«менеджеры» и «хелперы», слои-обёртки без логики. Дублирование двух-трёх похожих строк лучше неверной общей абстракции — обобщаем на третьем реальном повторе. Границы модулей (`public.py`, тест графа импортов) — обязательны.

### Где классы, а где функции

Класс — когда есть состояние (в том числе зависимости запроса), несколько реализаций или его требует фреймворк. Без состояния — функция. Наследование — только в иерархии исключений и от общей базы схем.

- **Классы:** сервис модуля с зависимостями в конструкторе; репозиторий; Pydantic-схемы и DTO; доменные исключения; адаптеры трёх внешних систем; инфраструктура с состоянием (темп сети `Pacer`).
- **Функции:** чистые правила домена (гейты, скоринг, разбор страниц); фасады `public.py`; роуты; компоненты React и хуки.

### ACID — транзакции

- **Одна бизнес-операция — одна транзакция.** Открывает и коммитит её сервис (`with db:`). Операцию не дробим на несколько коммитов.
- **Atomicity.** Сеть и вызов модели — никогда внутри транзакции: `sent_text` пишется после ответа транспорта. Изменения наружу (SSE, Telegram) — только after-commit: откат не должен оставлять следов. Единственное исключение — журнал `activity`: он пишется своим соединением вне транзакции вызывающего, потому что след «пытались, и вот что вышло» обязан пережить откат.
- **Consistency.** Инварианты данных охраняет схема: `CHECK`, `UNIQUE`, частичные индексы (уникальность живых строк `outbox`). Проверка в сервисе — для понятной ошибки оператору, но не вместо ограничения в базе.
- **Isolation.** Гонки закрываем явно: смена статуса — `UPDATE … WHERE status = :from` (0 строк → конфликт). Не читаем «проверил, потом записал» без условного `UPDATE`: тик воркера и кнопка оператора работают с одними строками.
- **Durability.** Ответ «успешно» — только после коммита. Запись в базу не ретраим; ретраи — только идемпотентных внешних вызовов, а неопределённый исход отправки уходит человеку (`stuck`), не в слепой повтор.
- Транзакции короткие: никаких сетевых ожиданий и тяжёлых вычислений внутри.

### Postel's Law — строго отдаём, терпимо принимаем

«Терпимо» значит нормализовать безобидные различия, а не угадывать смысл кривого ввода. На границе доверия неоднозначное или неверное отклоняется явной ошибкой.

- **Принимаем терпимо.** Обрезаем пробелы по краям строк; телефон приводим к канонической форме, домен — к нижнему регистру, ник Instagram — без `@`; лишние поля в теле запроса игнорируются, а не роняют запрос.
- **Не угадываем.** Неоднозначное значение, неизвестный код, переход статуса не по таблице — 422/409 с кодом ошибки, а не «примерно подходящее» значение.
- **Отдаём строго.** Ответы точно по схеме API; ошибки — `detail` и стабильный `code` (`errors.numberExists`), фронт ветвится по `code`, а не по тексту; время — ISO 8601 с таймзоной, в базе UTC, Asia/Almaty — только в гейте окна и на показе.
- **Читаем чужое терпимо (tolerant reader).** Ответы 2GIS, Instagram и Node разбираем только по нужным полям, неизвестные игнорируем.
- **Контракт меняем одним PR с фронтом.** Потребитель API один — свой дашборд, поэтому expand/contract не нужен; появится второй потребитель — правило меняется.

### Tell, Don't Ask — решает владелец данных

Не вытаскивай чужое состояние, чтобы принять решение за его владельца: скажи владельцу, что сделать, и пусть он решит сам.

- **Между модулями — команды, а не расспросы.** Отказ оформляет только владелец юридического контура, остальные зовут его фасад и не пишут в `refusals` сами. В очередь ставит только `enqueue` — и кнопка оператора, и тик воркера.
- **Правило живёт рядом с данными, которыми оно управляет**, и существует в одном месте. Два модуля проверяют одно условие — одно из мест лишнее.
- **Клиент не дублирует правила домена.** API отдаёт готовые решения — порядок срочности задач, пороги молчания демонов, доступные действия; дашборд показывает их как есть.
- **Чтение — можно.** Запросы данных для показа — не нарушение; нарушение — бизнес-решение по прочитанному чужому состоянию.

## Безопасность

### Least Privilege

- **Ключи и секреты** — только в `backend/.env` через `config.py`, никогда в репо. Фронт знает только адрес API (`NEXT_PUBLIC_API_ORIGIN`).
- **Невосстановимый слой** — `state.db`, `data/raw/`, сессии WhatsApp — в git не попадает никаким способом и бэкапится отдельно.
- **API без авторизации и слушает `127.0.0.1`.** Наружу не выставляется без отдельного решения (ADR): у дашборда нет входа, а за ним — отправка сообщений живым людям.
- **Вебхук** в бою работает только с `SENDER_WEBHOOK_SECRET`; пустой секрет — только локальная разработка.
- **Данные лидов** уходят в модель и в логи по необходимости: телефоны и тексты сообщений не логируем.

### Defense in Depth

Ни одна проверка не должна быть единственной защитой: подпись вебхука → валидация входа Pydantic → стоп-слова до модели → гейты перед отправкой → проверка отказа до выдачи и до отправки → ограничения схемы → песочница не стартует с боевым транспортом → журнал `activity`.

- **Фронт — не защита.** Скрытая кнопка — это UX; гейты и отказ бэкенд проверяет сам.
- **Самые чувствительные пути** — отправка лидам (гейты, очередь, автопилот), отказы (F21), вебхук, песочница — закрыты минимум двумя слоями и тестом.

## Работа с тикетами

Факты о проекте для воркфлоу (ветки, команды проверок, QA) — `docs/agents/workflow.md`. Процедуры — в скиллах плагина `workflow` (репо `NurmukhamedKZ/claude-workflow`, включён в `.claude/settings.json`), а не здесь. Меняется процесс — правка в репо плагина; меняется факт о проекте — правка `workflow.md`.

**Main ведёт тикеты сам, кодер пишет код.** Main-сессия берёт тикет через `/workflow:launch-main`: изучает код, спрашивает пользователя только о решениях из списка «Когда звать пользователя» (`docs/agents/workflow.md`, «Автономия main»), остальное решает сама, пишет спеку в тело issue («Решения грилинга»), выбирает effort, создаёт worktree и запускает кодера `/workflow:launch-coder <N>`. Кодер ведёт тикет до PR: `/tdd`, `/workflow:review-axes`, `/workflow:manual-qa`; с main переписывается через `cmux agent message`. Main мержит PR по «Условиям мержа» и сразу берёт следующий тикет. `/implement` не используем — его заменяет `/workflow:launch-coder`.

- Тикеты — sub-issues #3 со связями «blocked by». Брать только тикет, все блокеры которого закрыты. Один тикет — одна ветка `ticket/<номер>-<slug>` от свежей `main`, один кодер в своём worktree.
- **Сначала падающий тест, потом код** (`/tdd`) во всех частях репо.
- **Сначала ревью, потом PR.** Ветка не пушится и PR не открывается, пока не пройден `/workflow:review-axes` и не закоммичены исправления.
- **Документацию обновляй тем же PR, что и код:** затронутые `CLAUDE.md`, `backend/CLAUDE.md`, `docs/PRD.md`, `docs/TRD.md`, `docs/agents/workflow.md`.
- Мержит main-сессия: тикеты в `main` — squash, по «Условиям мержа» из `docs/agents/workflow.md`. Пользователь получает доклад после каждого мержа.

## Отладка

- **Сначала журнал:** поищи симптом в `docs/agents/bugs.md` (`grep` по тексту ошибки, поведению). Файл не грузится в сессию сам — открывай его при каждой отладке.
- **Корень одной строкой — до правки кода.** Гипотеза без доказательства (трейс, лог, воспроизведение) — не корень.
- **Не воспроизводится стабильно — сначала воспроизведи:** падающий тест или повтор. Исправление рабочее, когда повтор зелёный.
- **Порядок поиска:** данные и контракт API → сервис и база → фоновые тики и очередь → SSE и клиентское состояние → окружение (Node, песочница, `backend/.env`).
- **Чини у владельца данных или механизма**, а не заплаткой в слое-потребителе. Перед правкой в одном файле объясни, почему остальные слои не затронуты.
- **После исправления — запись в `docs/agents/bugs.md`** (симптом, корень, исправление, класс, как ловили). Класс встретился второй раз — предложи пользователю правило для `CLAUDE.md`; вписывай после согласия, сначала найди похожее правило и уточни его вместо дубля.
