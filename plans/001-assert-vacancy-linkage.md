## Зачем это нужно

В `collector/scripts/check.py` есть 60+ ассертов, и набор зелёный. При этом одна
из трёх ветвей сигналов проекта тихо упала в ноль: из 384 собранных вакансий hh к
компаниям привязано 4, и в таблице `signals` нет ни одной строки типа
`vacancy_sales` или `vacancy_stale`. Набор этого не заметил, потому что число
привязок он **печатает**, а не утверждает (`check.py:490`), а общий ассерт на
сигналы (`check.py:498`) требует лишь `total > 0` — его закрывают сигналы сайта.

Этот план не чинит склейку (это план 002). Он ставит на её результат ассерт с
зафиксированным сегодняшним числом, чтобы, во-первых, деградация до нуля больше
не проходила зелёной, а во-вторых — чтобы у плана 002 была метрика, по которой
можно судить об успехе. Без этого шага чинить склейку будет нечем измерить.

## Шаги

### Шаг 1: зафиксировать привязку вакансий ассертом

В `collector/scripts/check.py`, в функции `check_resolve()`, замени блок со
строк 485-490 так, чтобы `fuzzy` проверялся, а не только печатался. Нужная форма
(число 4 — это сегодняшний факт, а не цель):

```python
    # Привязка работодателя hh к компании 2GIS — самое слабое место конвейера:
    # из 384 вакансий привязаны 4. Число зафиксировано, чтобы падение до нуля
    # не проходило зелёным. Ветку чинит отдельный план; когда починят — поднять
    # порог здесь тем же коммитом, иначе ассерт перестанет что-либо значить.
    LINKED_VACANCIES_FLOOR = 4
    fuzzy = db.execute(
        "SELECT count(*) FROM vacancies WHERE company_id IS NOT NULL"
    ).fetchone()[0]
    total = db.execute("SELECT count(DISTINCT employer) FROM vacancies").fetchone()[0]
    assert fuzzy >= LINKED_VACANCIES_FLOOR, (
        f"вакансий привязано к компаниям {fuzzy}, было {LINKED_VACANCIES_FLOOR} — "
        "склейка работодателей стала хуже, сигналы вакансий исчезнут из скоринга"
    )
```

Константу `LINKED_VACANCIES_FLOOR` объяви прямо в функции, рядом с
использованием — в этом файле нет модуля констант, а числа разделов `parsers`
живут на уровне модуля только потому, что их используют несколько функций.

`print` со строки 490 оставь как есть.

**Проверка**: `uv run -m scripts.check resolve` → выход 0, в выводе строка
`вакансий привязано к компаниям 4, работодателей всего 321`, последняя строка
`check ok: resolve`.

### Шаг 2: убедиться, что ассерт действительно ловит поломку

Временно подними `LINKED_VACANCIES_FLOOR` до `5`, запусти раздел, убедись, что он
падает с твоим сообщением, и верни `4` обратно.

**Проверка**: с порогом 5 — `uv run -m scripts.check resolve` завершается
ненулевым кодом и печатает `AssertionError: вакансий привязано к компаниям 4,
было 5 …`. После возврата на 4 — снова выход 0.

### Шаг 3: сделать видимым отсутствие сигналов вакансий

В `check_signals()` добавь проверку по семействам сигналов. Сегодня
`vacancy_sales` и `vacancy_stale` отсутствуют полностью, и `total > 0` этого не
показывает.

Место вставки точное: **между строкой 523** (`assert doubled == 0, …`) **и
строкой 525** (`check_instagram_signals(db)`). Соединение `db` там уже открыто
(строка 496) и закрывается на 532 — своё не заводи. Нужная форма:

```python
    # Ветвь vacancy_* сегодня пуста: вакансии почти не привязываются к компаниям
    # (см. LINKED_VACANCIES_FLOOR в check_resolve). Ассерт на конкретные типы
    # поставить нельзя, пока их ноль, — вместо него на виду держится состав
    # семейств, чтобы исчезновение site_* или ig_* не спряталось за общим total.
    families = {row[0] for row in db.execute("SELECT DISTINCT type FROM signals")}
    site_types = {"ads_platform", "crm_widget", "inbound_widget", "service_catalog"}
    assert site_types <= families, (
        f"сигналы сайта потеряны: есть {sorted(families & site_types)}, "
        f"нет {sorted(site_types - families)}"
    )
    assert any(t.startswith("ig_") for t in families), \
        "ни одного сигнала инстаграма — лента не разобрана или склейка аккаунтов сломана"
    if not any(t.startswith("vacancy_") for t in families):
        print("    ! сигналов вакансий нет — ветка hh не работает, см. plans/002")
```

Именно `print` с предупреждением, а не ассерт: ассерт на непустой
`vacancy_*` сегодня уронил бы зелёный набор, а задача этого плана — сделать
дыру видимой, не сломав конвейер.

**Проверка**: `uv run -m scripts.check signals` → выход 0, в выводе есть строка
`    ! сигналов вакансий нет — ветка hh не работает, см. plans/002`, последняя
строка `check ok: signals`.

## План тестирования

Отдельных тестов писать не нужно: `check.py` **и есть** тестовый набор проекта,
и этот план дописывает в него ассерты. Покрываемые случаи:

- привязка вакансий упала ниже сегодняшних 4 — падает `check_resolve` (шаг 1,
  проверено вручную на шаге 2);

- исчезли сигналы инстаграма — падает `check_signals`;
- сигналов вакансий по-прежнему нет — набор зелёный, но печатает предупреждение.

Структурный образец — соседние ассерты в `check_resolve` (`check.py:459-483`).
