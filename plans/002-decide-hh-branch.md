## Зачем это нужно

Вакансии hh — один из трёх источников сигналов проекта и, по BRD, самый прямой:
компания нанимает продавцов, потому что ей не хватает клиентов. Сегодня эта ветвь
не работает совсем:

| Величина | Значение |
|---|---|
| вакансий собрано | 384 |
| уникальных работодателей | 321 |
| вакансий привязано к компании (`company_id IS NOT NULL`) | 4 |
| строк `signals` типа `vacancy_sales` | 0 |
| строк `signals` типа `vacancy_stale` | 0 |

Веса `vacancy_sales = 3.0` и `vacancy_stale = 3.0` в `config.toml` — самые
высокие в системе наравне с `crm_widget` — не применяются ни к одному лиду.
Шаблоны `why_now` под них (`report.py:157-164`) не срабатывают ни разу.

**Важно, и именно это отличает эту находку от «слабого порога»:** дело не в
настройке сравнения имён. Замерено (методика — в шаге 1): даже если убрать
фильтр по городу и опустить порог сходства с 0.88 до 0.75, похожая компания
находится всего у **15 работодателей из 321**. Потолок ветки — около 5%. Причина
структурная: вакансии собираются по общегородским SEO-страницам профессий
(`config.toml`, `[hh].slugs` — «менеджер по продажам», «бухгалтер», «юрист» и
т.д. по всему городу), а компании — по 36 узким рубрикам B2B-услуг 2GIS. Это две
почти непересекающиеся популяции, и никакая настройка сравнения имён их не сведёт.

Значит, выбор не «как настроить порог», а «что делать с веткой». План измеряет
цену и отдачу трёх путей и оставляет владельцу продукта записку с числами.

```python
def link_employers(db):
    """Работодатель hh к компании — только нечётко по имени в пределах города.

    Точный путь (/employer/{id} -> сайт -> домен) стоит лишнего запроса на вакансию,
    а hh и без того блокирует сбор. Остаётся открытым вопросом №1 TRD.
    """
    companies = db.execute(
        "SELECT company_id, name_norm, city FROM companies WHERE name_norm <> '' ORDER BY company_id"
    ).fetchall()
    by_city = {}
    for company_id, name_norm, city in companies:
        by_city.setdefault(city, []).append((company_id, name_norm))

    for vacancy_id, employer, city in db.execute(
        "SELECT id, employer, city FROM vacancies WHERE employer IS NOT NULL ORDER BY id"
    ).fetchall():
        name = normalize_name(employer)
        best_id, best_score = None, 0.0
        for company_id, company_name in by_city.get(city, []):
            if not company_name or company_name[0] != name[:1]:
                continue
            score = similarity(name, company_name)
            if score > best_score:
                best_id, best_score = company_id, score
        if best_id and best_score >= NAME_SIMILARITY:
            db.execute(
                "UPDATE vacancies SET company_id = ?, match_confidence = ? WHERE id = ?",
                (best_id, round(best_score, 3), vacancy_id),
            )
```

### Шаг 1: воспроизвести замер пересечения

Напиши временный скрипт (например `/tmp/hh_overlap.py`), запусти его из

```python
import sqlite3
from services.resolve import normalize_name, similarity

db = sqlite3.connect("db/leads.db")
companies = [(cid, n) for cid, n in db.execute(
    "SELECT company_id, name_norm FROM companies WHERE name_norm <> ''")]
employers = sorted({e for (e,) in db.execute(
    "SELECT DISTINCT employer FROM vacancies WHERE employer IS NOT NULL")})

reachable = 0
for employer in employers:
    name = normalize_name(employer)
    if not name:
        continue
    # без фильтра по городу и с заниженным порогом — это ПОТОЛОК ветки,
    # а не то, что даёт текущий код
    if max((similarity(name, cn) for _, cn in companies), default=0) >= 0.75:
        reachable += 1

print(f"работодателей {len(employers)}, компаний {len(companies)}, "
      f"достижимо при любом смягчении сравнения имён: {reachable}")
```
