## Зачем это нужно

`build.fill_profiles()` раздаёт оплаченные ответы модели по компаниям, опознавая
компанию по её названию из первой строки промпта. Названия в базе не уникальны:
сегодня их пять пар.

| Название | Компании |
|---|---|
| Deloitte, аудиторско-консалтинговая компания | `dom:deloitte.com` (astana), `dom:deloitte.kz` (almaty) |
| 1С Казахстан, официальный представитель в Казахстане | `dom:1c.kz` (astana), `2gis:70000001113535322` (almaty) |
| Диалог, группа компаний | `2gis:70000001035672011` (astana), `dom:dialogs.kz` (almaty) |
| Фотосалон | `2gis:70000001036939575` (astana), `2gis:70000001042205223` (almaty) |
| Schneider Electric | `2gis:70000001053128207` (astana), `2gis:9429948590736959` (almaty) |

Словарь `{название: company_id}` в `fill_profiles` строится обходом, и при
повторе названия побеждает последняя запись. То есть профиль, оплаченный за
алматинскую компанию, может лечь астанинской. Профиль — это `why_now` и `quote`,
то самое, что оператор произносит в разговоре (PRD F20): цитата с чужого сайта в
письме конкретному человеку — худший вид ошибки, какой эта система может сделать.

Сейчас не выстрелило: профилей 40, и ни один из них не принадлежит компании из
таблицы выше. Но `config.toml [llm].top_n` растёт, и вопрос только в том, когда.

Починка дешёвая, и главное — **не обесценивает уже оплаченные ответы**: город уже
лежит второй строкой каждого промпта, менять сам промпт не нужно, а ключ кэша
(`sha256(модель + промпт)`) остаётся прежним.

```python
def fill_profiles(db):
    """Профили от модели из raw/*.llm.json. Сети здесь нет: ответы уже на диске.

    Компания опознаётся по названию в промпте — company_id в него не входит, чтобы
    смена схемы идентификаторов не обесценивала оплаченные ответы.
    """
    names = {
        name: company_id
        for company_id, name in db.execute(
            "SELECT c.company_id, coalesce(o.org_name, o.name, c.name_norm)"
            " FROM companies c"
            " LEFT JOIN company_links l ON l.company_id = c.company_id AND l.rule = 'self'"
            " LEFT JOIN orgs o ON o.branch_id = l.branch_id"
        )
    }
    for answer_path in sorted(RAW.glob("*.llm.json")):
        answer = json.loads(answer_path.read_text(encoding="utf-8"))
        # Рядом лежат ответы classify_ig.py с другой схемой. Ответы, записанные до
        # появления метки, — профили компаний: тогда другого вида и не было.
        if answer.get("kind", "company_profile") != "company_profile":
            continue
        first_line = answer["prompt"].splitlines()[0].removeprefix("Компания: ")
        company_id = names.get(first_line)
        if not company_id:
            continue
        profile = answer["profile"]
```

```python
def build_prompt(company, text, config):
    parts = [
        f"Компания: {company['name']}",
        f"Город: {company['city']}",
        f"Сайт: {company['domain'] or 'нет'}",
    ]
    if company["signals"]:
        parts.append("Найдено на сайте: " + "; ".join(company["signals"]))
    parts.append("Текст сайта:\n" + (text[: config["site_chars"]] or "(не собран)"))
    return "\n".join(parts)
```

Проверено на всех 40 существующих ответах вида `company_profile` в `data/raw/`:

Нестандартных нет.

**Соглашения проекта, которым обязан следовать новый код:**

1. `build.py` не ходит в сеть и не импортирует `services/fetch.py` или
   `scrapling` — это проверяет `scripts/check.py`. Новый код читает только диск
   и базу.
2. Промпт менять **нельзя**: ключ кэша — `sha256(модель + промпт)`
   (`classify.py:212-214`), и любая правка `build_prompt` обесценит все 40
   оплаченных ответов. Город берётся из уже существующей второй строки.
3. Комментарии по-русски, объясняют «почему», а не «что» — образец в шапке
   самой `fill_profiles`.
4. Обход `RAW.glob` отсортирован (`sorted`) — сборка обязана быть
   воспроизводимой побайтово, это проверяет `check_rebuild_is_identical`
   (`scripts/check.py:353-363`). Не убирай `sorted`.

## Шаги

### Шаг 1: ключевать словарь компаний парой (название, город)

поиск компании. Нужная форма:

    # (Deloitte, Schneider Electric и ещё три пары стоят в двух городах), и по
    # одному названию оплаченный профиль ложился бы той компании, что попалась
    # обходу последней. Город уже есть второй строкой промпта, поэтому сам промпт
    # не меняется и кэш ответов остаётся в силе.
    companies = {
        (name, city): company_id
        for company_id, name, city in db.execute(
            "SELECT c.company_id, coalesce(o.org_name, o.name, c.name_norm), c.city"
            " FROM companies c"
            " LEFT JOIN company_links l ON l.company_id = c.company_id AND l.rule = 'self'"
            " LEFT JOIN orgs o ON o.branch_id = l.branch_id"

    }

и ниже, в теле цикла, вместо разбора одной первой строки:

### Шаг 3: закрепить ассертом в наборе проверок

`check_build()` (строки 255-265) — диспетчер: он открывает соединение и зовёт
`check_orgs(db)`, `check_vacancies(db)`, `check_contacts(db)`, `check_fetches(db)`,

1. Добавь вызов `check_profiles(db)` в `check_build()` — **между** строкой 263
   (`check_fetches(db)`) и строкой 264 (`db.close()`).
2. Объяви функцию `check_profiles(db)` рядом с остальными помощниками, после
   `check_fetches` (то есть после строки 350). Нужная форма:

```python
def check_profiles(db):
    """Профили от модели дошли до своих компаний, и ни один не потерялся."""
    import build

    # Профиль опознаёт компанию по паре (название, город) из промпта: названия в
    # базе не уникальны, и по одному названию оплаченный профиль лёг бы чужой
    # компании — это цитата с чужого сайта в письме живому человеку (F20).
    orphan = db.execute(
        "SELECT count(*) FROM profiles p"
        " WHERE NOT EXISTS (SELECT 1 FROM companies c WHERE c.company_id = p.company_id)"
    ).fetchone()[0]
    assert orphan == 0, f"{orphan} профилей у несуществующих компаний"

    # Ответ модели стоил денег: если он лежит в raw/, а до базы не доехал, значит
    # ключ разошёлся с промптом, и молча теряется оплаченная работа.
    answers = len(build.load_llm_answers("company_profile"))
    stored = count(db, "profiles")
    assert stored == answers, (
        f"ответов модели в raw/ {answers}, профилей в базе {stored} — "
        "оплаченные ответы не находят свою компанию"
    )
    print(f"  профилей {stored}, все у существующих компаний")
```

Ассерт на `doubled` не нужен: `company_id` — PRIMARY KEY таблицы `profiles`
(`db/schema.sql:113-114`), двух профилей у одной компании не бывает по схеме.

Образец соседних ассертов на «сироты» — `check_resolve` (`scripts/check.py:464-468`)
и `check_signals` (`scripts/check.py:511-515`). Следуй их форме и тону сообщений.
`build.load_llm_answers` уже существует (`collector/build.py:155-166`) и читает
`data/raw/*.llm.json` без сети — второй копии этого чтения писать не надо.

**Проверка**: `uv run -m scripts.check build` → выход 0, в выводе строка
`профилей 40, все у существующих компаний`.

## План тестирования

Отдельного тестового фреймворка в проекте нет: `scripts/check.py` **и есть**
тестовый набор. Покрываемые этим планом случаи:

- профиль ссылается на несуществующую компанию (шаг 3, `orphan`);
- оплаченный ответ лежит в `data/raw/`, но не доехал до базы (шаг 3, сверка
  `answers` и `stored`) — это и есть регрессия, которую может внести неверный
  ключ;
