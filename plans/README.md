## Зависимости

- **002 требует 001.** План 001 ставит ассерт `LINKED_VACANCIES_FLOOR = 4` на
  число привязанных вакансий. Без него у решения по ветке hh нет метрики: любой
  из вариантов 002 нечем будет измерить, а деградация обратно к нулю пройдёт
  зелёным набором. Ассерт удалён вместе с веткой — план 002 закрыт как
  `REJECTED` (задача 2 `2026-08-18-remove-hh-source.md`).
- **003 и 004 независимы** — их можно брать в любой момент и параллельно с
  остальными. Оба трогают `scripts/check.py`, но в разных функциях
  (`check_build` против `check_leads`), конфликта не будет.

## Что нашлось и почему именно это

**001 + 002 — главное.** Ветка вакансий hh не даёт ни одного сигнала: из 384
собранных вакансий к компаниям привязано 4, строк `signals` типа `vacancy_sales`
и `vacancy_stale` — ноль. Веса `vacancy_sales = 3.0` и `vacancy_stale = 3.0` —
самые высокие в `config.toml` наравне с `crm_widget` — не применяются ни к одному
лиду. Причина структурная, а не в пороге сравнения имён: вакансии собираются по
общегородским SEO-страницам профессий, компании — по 36 узким рубрикам B2B-услуг
2GIS, и даже при снятом фильтре по городу и пороге 0.75 похожая компания
находится всего у 15 работодателей из 321. Потолок ветки ~5%. Поэтому 002 —
план-разведка с запиской и рекомендацией, а не план-починка: выбор между
«дотянуть до 5%» и «убрать ветку» продуктовый.

**003 — предотвращение, не исправление.** `build.fill_profiles` раздаёт
оплаченные ответы модели по названию компании, а названия не уникальны — сегодня
пять пар. Профиль это `why_now` и цитата, которую оператор произносит в
разговоре (F20). Сегодня ни у одной из пяти пар профиля нет, так что ошибка ещё
не случилась; `top_n` растёт, и вопрос только в том, когда.

**004 — две мелкие неправды.** `report.available()` считает потолок выдачи своим
SQL-запросом и не вычитает отказы; расхождение сегодня нулевое (список отказов
пуст) и растёт с каждым отказом. И 13 телефонов из 2706 — короткие сервисные
номера 2GIS (`1400`, `5151`, `349550`); двое лидов из 995 получают такой номер
как единственный канал, то есть F19 соблюдён формально, а набрать нечего.

## Что вскрылось при выполнении

Две ошибки в самих планах, найденные при приёмке. Обе исправлены в файлах
планов, чтобы повторный прогон не спотыкался о них снова.

- **План 004 обещал `available() == 992`, верно 993.** В арифметику плана попал
  счёт «3 лида», полученный ранним замером через `services.resolve.e164`, тогда
  как сам план предписывает правило «не меньше 10 цифр» — а оно намеренно
  сохраняет номера с добавочным. `Ensoft, ТОО` с номером `+77273398932,,,2405`
  (15 цифр) обязан был остаться. Единственный канал теряют двое:
  `Freedom Telecom` (`4000`) и `PingOcean` (`349550`). Исполнитель остановился на
  стоп-условии и не стал подгонять `MIN_PHONE_DIGITS` — стоп-условие сработало
  как задумано.
- **План 004 не предусмотрел `collector/api.py`.** Его `demo()` использовал
  заглушку телефона `"+7700"` — четыре цифры, — и после появления `reachable()`
  падал. `scripts/check.py` этого не ловит, потому что не вызывает `api.demo()`.
  Починена заглушка (теперь `"+77010000000"`), а не порог. Урок для будущих
  планов: список команд проверки обязан включать `uv run api.py` наравне с
  `uv run -m routes.runs` — demo-функции модулей живут вне общего набора.

## Рассмотрено и отклонено

- **`classify.site_texts()` разбирает все 996 сайтов вместо `top_n = 40`.**
  Выглядит как лишняя работа, замерено — 1.8 с. Не стоит правки.
- **`routes/runs.py` пробрасывает произвольный `args` в argv команды.** Оболочки
  нет (`asyncio.create_subprocess_exec` со списком), команды из белого списка,
  инструмент локальный, для одного оператора. Не находка.
- **Секреты.** `collector/.env`, `collector/db/leads.db`,
  `collector/data/cookies.json` — все в `.gitignore`, в индексе git ничего
  лишнего. Чисто.
- **Смягчить порог `NAME_SIMILARITY` для работодателей hh.** Замерено: 0.88 → 4
  привязки, 0.80 → 7, 0.75 → 10, с вложением множеств слов → 14, и среди них
  заведомо ложные (`Bridge → dom:sbinvest.kz`). Отклонено как самостоятельная
  правка — это один из вариантов в плане 002, а не решение.
- **Чистить короткие номера из таблицы `contacts` при разборе.** Сырьё в проекте
  не правят; отбраковка живёт на границе выдачи (план 004), а в карточке лида
  оператор по-прежнему видит все каналы.

## Не аудировано

Аудит был быстрым: корректность, безопасность, тесты по горячим местам. Не
смотрели: `frontend/` вглубь, зависимости (`uv.lock`, `package-lock.json`,
`npm audit`/`pip-audit`), производительность конвейера, `collector/ig/`,
`collector/services/probes/`, документацию в `docs/` на актуальность.

Отдельно осталось направление, план по которому не заказывали: `parse_serper`
(`services/sources.py:184`) написан, `services/probes/serp.py` умеет ходить,
`SERPER_API_KEY` есть в `.env.example` — а `build.py:177` явно пропускает
`*.serp.json`. Поиск собирается и выбрасывается, при том что у ~660 компаний из
1660 нет домена, а значит нет ни одного сигнала с сайта.
