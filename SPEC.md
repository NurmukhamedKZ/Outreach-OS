# SPEC — план реализации ARCHITECTURE v2

**Дата:** 12 августа 2026
**Основание:** [ARCHITECTURE_v2.md](ARCHITECTURE_v2.md)
**Цель:** довести проект до приёмки PRD — 30 компаний с каналом и `why_now`, с
которыми начата переписка.

---

## Правила исполнения

1. **Каждая фаза завершается работающей командой.** Не «написан модуль», а «команда
   запускается и выдаёт проверяемый результат».
2. **Каждая фаза оставляет ассерт в `check.py`.** Отдельной фазы «написать тесты» нет.
   Ассерт — минимальный: тот, который падает, если логика фазы сломается.
3. **Не переходить к следующей фазе, пока приёмка текущей не зелёная.**
4. Разведка источников уже сделана и проверена на живых данных. **Разбор не
   переписывается** — переносится из работающих скриптов.

~1,5 ГБ. Сжатие в Ф1 — не оптимизация, а условие того, что сырьё влезет на диск и
доедет до бэкапа.

# Ф1. Слой сырья

**Объём:** 2 часа. **Не откладывается:** данные, не записанные сегодня, задним
числом не появятся — вакансия закроется, страница исчезнет.

### Шаги

1. **Сайдкар становится полноценным.** Сейчас рядом с `<sha>.html` лежит `<sha>.url`
   с одним конечным адресом. Заменить на `<sha>.json`:

   ```json
   {"url": "...", "final_url": "...", "status": 200, "fetched_at": "2026-08-12T09:14:03Z"}
   ```

   `fetched_at` нужен для затухания `intent_score` (F16) и для решения, когда
   перекачивать. Без него эти вопросы не имеют ответа задним числом.

2. **Сжатие.** `<sha>.html` → `<sha>.html.gz` через `gzip` из stdlib. Читать
   `gzip.open(...).read().decode()`.

3. **Переименование `cache/` → `raw/`.** Имя «кэш» приглашает удалить папку, которую
   PRD N6 запрещает удалять когда-либо. Существующие `raw/*.jsonl` при этом
   переезжают в `raw_jsonl_legacy/` — они удаляются в Ф3, когда `build.py` докажет,
   что воспроизводит их из сырья.

4. **Миграция накопленного.** Одноразовый скрипт: 111 пар `.html`/`.url` →
   `.html.gz`/`.json`. `fetched_at` берётся из mtime файла — приблизительно, но
   честнее, чем пусто.

5. **`.gitignore`:** `raw/` остаётся игнорируемым (9 ГБ в git не кладут), но
   добавить `raw/.gitkeep` и строку в README о том, что папка невосстановима и
   бэкапится отдельно.

### Приёмка

```bash
uv run check.py raw
```

- 111 страниц читаются из `.gz`, кириллица цела
- у каждой есть `.json`-сайдкар с четырьмя полями
- `final_url` сохранён для всех 111 — проверка подмены не потеряна
- размер `raw/` упал не меньше чем в 4 раза
- все шесть `demo()` из Ф0 по-прежнему зелёные

### Чего не делать

Не хранить вместо HTML извлечённый `initialState` — это разбор на этапе сбора, а
разбор будет меняться. Сырьё остаётся сырьём.

```
# ponytail: gzip на файлах. zstd или один pack-файл — если 1.5 ГБ станет неудобно.
```

# Ф2. Конфиг

**Объём:** 30 минут работы + до часа ручного сбора slug'ов.

### Шаги

1. `config.toml`:

   ```toml
   cities = ["almaty", "astana"]

   [rubrics]
   include = [653, 339, 638, 1236, 1238, 22129]   # ветка «Бизнес-услуги»
   exclude = [110611]                              # «Реклама» — прямые конкуренты

   [hh]
   slugs = ["menedzher_po_prodazham", "buhgalter", ...]

   [scoring]
   half_life_days = 90
   # веса — гипотеза до первых 30 ответов
   ```

2. Полный список листовых рубрик ветки берётся из уже собранного
   `2gis_rubrics.jsonl` (135 строк), не из сети.

3. **Slug'и hh собираются вручную** — автоматически их получить нельзя: единственный
   механизм это `?text=`, запрещённый `robots.txt` (TRD, открытый вопрос №2).
   Открыть поиск hh.kz по нужной фразе в браузере, взять slug из адреса, куда
   перебросит. Десяти хватает для старта.

### Приёмка

`config.toml` читается через `tomllib`, содержит ≥ 20 рубрик и ≥ 10 slug'ов.

# Ф3. `build.py` — факты

**Объём:** полдня. Самая содержательная фаза.

Здесь появляется главная граница системы: `build.py` **не ходит в сеть никогда**.
Он чистая функция от `raw/` к `leads.db`.

### Шаги

1. **`schema.sql`** — восемь таблиц из ARCHITECTURE_v2 §4. На этой фазе наполняются
   четыре: `fetches`, `orgs`, `contacts`, `vacancies`.

2. **`sources.py`** — перенос разбора из рабочих скриптов. Функции, не классы:

   ```
   parse_initial_state(html) -> dict
   parse_org_list(state, city, rubric_id) -> list[dict]
   parse_firm_card(state, branch_id) -> list[dict]     # по строке на канал
   parse_job_posting(html) -> dict | None
   parse_serper(data, query) -> list[dict]
   ```

   Единственное содержательное изменение против нынешнего: `parse_firm_card`
   возвращает **плоские строки** `(branch_id, kind, handle, source_url)` вместо
   словаря с разнотипными полями. Сейчас `phones` список, `website` строка,
   `whatsapp` список, `instagram` строка — непоследовательно и мешает единому
   правилу «есть телефон → лид готов».

3. **`build.py`**: `DROP` всех таблиц → обход `raw/` → разбор → `INSERT`.
   Пересборка целиком, не инкрементально.

4. Удалить `raw_jsonl_legacy/` после того, как приёмка пройдёт.

### Приёмка

```bash
uv run build.py && uv run check.py build
```

- `orgs` ≥ 60 строк — не меньше, чем накоплено в старом `2gis_list.jsonl`
- `vacancies` ≥ 100, у каждой непустой `text` длиннее 200 символов
- `contacts` ≥ 15 карточек, среди них ≥ 3 телефона у первой
- кириллица цела в `orgs.name` и `vacancies.text`
- **повторный `build.py` даёт побайтово ту же базу** (PRD П5)
- время полной сборки < 30 секунд на текущем объёме

### Чего не делать

Не делать миграции схемы. Схема правится в `schema.sql`, база пересобирается.

# Ф4. `collect.py` — массовый сбор

**Объём:** 2 часа кода + 1,5 часа работы скрипта.

### Шаги

1. Построить список URL из `config.toml`: рубрики × города × страницы, slug'и ×
   города, карточки филиалов по собранным `branch_id`.

2. `ThreadPoolExecutor(8)` поверх `fetch.get`. Кэш делает повтор бесплатным, поэтому
   отдельного учёта «что уже скачано» не нужно — он и есть учёт.

3. **Проверки подмены переносятся дословно:**

   | Источник | Признак | Реакция |
   |---|---|---|
   | 2GIS | `currentPage` ≠ запрошенной | штатный конец пагинации, стоп на 60 |
   | hh | конечный URL не содержит slug | отказ с внятным сообщением оператору |

   Это главная содержательная находка проекта. Ни одна строка здесь не упрощается.

4. Прогресс печатает `collect.py` — в `sources.py` `print` не попадает.

### Приёмка

```bash
uv run collect.py && uv run build.py && uv run check.py collect
```

- `orgs` ≥ 1 000 после дедупа по `branch_id`
- ни одна рубрика не дала > 60 организаций на город — потолок ловится
- `vacancies` ≥ 500
- у ≥ 90 % организаций есть хотя бы один телефон
- второй запуск `collect.py` не делает **ни одного** сетевого запроса

Последний пункт — самый важный: он доказывает, что оркестратор не нужен.

# Ф5. `resolve.py` — склейка

**Объём:** 2 часа.

### Шаги

Пять правил из ARCHITECTURE.md §9.3, по убыванию надёжности. Модель не участвует —
правила точнее и дешевле.

| Правило | Реализация | Надёжность |
|---|---|---|
| Домен | нормализация URL, `link.2gis.ru` разворачивается | точно |
| Телефон в E.164 | `phonenumbers` | почти точно |
| Instagram username | сопоставление ссылок | точно |
| БИН | если найден | точно |
| Похожее имя в пределах города | `difflib.SequenceMatcher` > 0.8 | нечётко → в `company_links` с `confidence` |

Кандидаты для нечёткого правила сужаются городом и первой буквой `name_norm` —
иначе 1 500² сравнений, а так их сотни.

Отдельно: работодатель hh склеивается с организацией 2GIS **только по имени** и
только нечётко. Точный путь — `/employer/{id}` → сайт → домен — стоит лишнего GET
на вакансию и откладывается (TRD, открытый вопрос №1).

### Приёмка

- `companies` заметно меньше, чем `orgs` — филиалы схлопнулись в компании
- ни одна компания не склеена по имени без записи в `company_links`
- ассерт на известном дубле: организация из двух рубрик даёт одну компанию

# Ф6. `enrich.py` — сигналы

**Объём:** полдня. Модель здесь не вызывается.

### Шаги

1. **Сигналы из вакансий** — то, ради чего проект существует. Поиск по тексту:
   `LIKE '%продаж%'` по 2 000 вакансий отрабатывает за 50 мс.

   | Сигнал | Условие | Вес |
   |---|---|---|
   | Вакансия в продажах | текст или заголовок | высокий |
   | Вакансия висит 60+ дней | `published_at` | высокий |
   | Рост числа вакансий за квартал | счёт по `company_id` | высокий |

2. **Сигналы из HTML** — regex по сырью, детерминированно: Bitrix24, amoCRM,
   Google Ads, Яндекс.Метрика, формы заявки, WhatsApp-виджет.

3. **Каждый сигнал — строка в `signals` с `observed_at`, `quote` и `url`.** Не флаг
   в компании. `quote` и `url` — это готовый материал для `why_now` (PRD F20).

### Приёмка

- ≥ 100 компаний имеют сигнал «вакансия в продажах»
- у каждой строки `signals` непустые `observed_at`, `quote`, `url`
- ни одной булевой колонки-сигнала в `companies`

```
# ponytail: LIKE-скан по 2000 вакансий. FTS5 при 50k+.
```

# Ф7. `score.py`

**Объём:** 2 часа.

### Шаги

1. Две функции, обе возвращают `(score, breakdown)`, где `breakdown` — список
   сработавших сигналов с весами. Объяснимость (PRD F17) обеспечивается разбивкой,
   а не отдельной сущностью.

2. `fit_score` — соответствие ICP по правилам: рубрика в `include`, город, наличие
   сайта, не в `exclude`.

3. `intent_score = Σ(weight × exp(-days_since / half_life))` — одно выражение.

4. **Нет сигналов ≠ отрицательный вес.** Компания без рекламы, но с CRM и отделом
   продаж — лучший лид из возможных.

5. Веса — словарь в начале файла. Это гипотеза; калибруется после первых 30 ответов.

### Приёмка

- вакансия вчерашняя даёт заметно больший вклад, чем полугодовой давности
- у любого лида из топ-10 `breakdown` объясняет его позицию
- модель в скоринге не участвует нигде

# Ф8. `report.py` — ПРИЁМКА PRD

**Объём:** 2 часа.

### Шаги

1. `VIEW` поверх `companies` + `contacts` + `signals` + скоринг.

2. **Жёсткое правило: лид без канала из `[whatsapp, phone, email]` в выдачу не
   попадает** (PRD F19). Компания с прекрасным скорингом, но без канала — не лид.

3. `suppression` проверяется **до** выдачи, не после (PRD F21). Таблица не
   очищается никогда.

4. Экспорт CSV: компания, канал, `why_now`, разбивка скоринга, ссылки на источники.

5. **Статус переписки в CSV не возвращается.** Кто ответил и кому перезвонить —
   работа человека в его таблице. В систему приходит только `suppression`.

### Приёмка — это приёмка PRD

| # | Критерий | Проверка |
|---|---|---|
| П1 | 30 компаний, бизнес-услуги, Алматы или Астана | выгрузка |
| П2 | у каждой канал из `[whatsapp, phone, email]` | колонка канала |
| П3 | у каждой `why_now` с цитатой и ссылкой | ручной просмотр всех 30 |
| П5 | повторный прогон даёт тот же результат | `build.py` дважды |
| П6 | ни одной записи с подменённой страницы | проверки Ф4 зелёные |

П4 — начата переписка — выполняется руками. Это и есть цель проекта.

На этой фазе `why_now` собирается **шаблоном из `signals`**: цитата из вакансии плюс
ссылка. Этого достаточно для П3. Агент — следующая фаза, и она не блокирует приёмку.

# Ф9. Классификация и `why_now` агентом

**Объём:** день. **После первых тридцати ответов, не раньше.**

### Почему после

Живые ответы переопределят половину весов скоринга. Всё, что построено до них,
строится вслепую — включая промпт классификатора, который будет писаться под уже
понятные признаки, а не под угаданные.

### Шаги

1. `cache.llm(prompt) -> dict` — тот же content-addressed механизм, ключ `sha256`
   промпта. Делает перестройку `build.py` бесплатной: платится только за компании,
   увиденные впервые.

2. `classify.py` — один вызов Haiku на компанию, structured output. **Только по
   топу отсева**, не по всей базе: отрасль известна из рубрики, размер недостижим
   ни одним источником, отдел продаж виден по вакансии, CRM найден regex'ом.
   Модель добавляет только чтение текста сайта.

3. Агент `why_now` — на топ-50, тех, кому реально пишут в этом цикле.

### Приёмка

- ~$5 на классификацию вместо ~$54, ~$8 на агента вместо ~$40
- повторный `build.py` после классификации не тратит ни цента
- `why_now` от агента содержательнее шаблонного из Ф8 на ручном сравнении 10 лидов
